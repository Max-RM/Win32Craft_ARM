### F1. The game has NO runtime shader compiler: every shader is a precompiled ANGLE program binary selected by a SHA-1 of the GLSL source  [severity: major, confidence: high]
Claim: libGLESv2_phone.dll (ANGLE "1.2.0.2446", MS Open Tech WP8 port) contains the GLSL ES -> HLSL translator but imports nothing from any HLSL compiler; its only d3d11 import is D3D11CreateDevice. cocos2d-x (libcocos2d.dll) therefore ships 15 ready-made ANGLE program binaries (format GL_PROGRAM_BINARY_ANGLE 0x93A6) in a table CCPrecompiledShaders and feeds them to glProgramBinaryOES. In CCGLProgram::initWithVertexShaderByteArray the game first calls glGetBooleanv(GL_SHADER_COMPILER=0x8DFA); if the result is not 1 it takes the precompiled path (glCreateProgram -> CCPrecompiledShaders::loadProgram(program, vsSource, fsSource) -> key = SHA-1(vsSource + fsSource + glGetString(GL_SHADING_LANGUAGE_VERSION=0x8B8C)) -> table lookup -> glProgramBinaryOES(program, 0x93A6, blob, size)). If the key is not in the table nothing is loaded (loadProgram returns 0) and the program stays empty.
Evidence:
- libGLESv2_phone.dll imports (arm32re imports): d3d11.dll!D3D11CreateDevice at IAT RVA 0x61224; no d3dcompiler, no D3DCompile. Strings (my dump): 'OpenGL ES 2.0 (ANGLE 1.2.0.2446)' RVA 0x69E08, 'OpenGL ES GLSL ES 1.00 (ANGLE 1.2.0.2446)' RVA 0x69E2C, 'gl::Shader::compileToHLSL' RVA 0x6D264 (translator present), 'Invalid program binary format.' / 'Invalid program binary version.' / 'Mismatched compilation flags.' / 'Could not create pixel shader.' at RVAs 0x6A564..0x6A5FC (= ProgramBinary::load). Exports (my pe.py): #175 glProgramBinaryOES, #176 glGetProgramBinaryOES, #98 glShaderBinary.
- libcocos2d.dll imports libGLESv2_phone.dll!#175 (glProgramBinaryOES, IAT 0x10195668) and #176. CCGLProgram::initWithVertexShaderByteArray RVA 0xBCC30: 'movw r0,#0x8dfa ... blx IAT#59 (glGetBooleanv) ... cmp r3,#1 ... strb r3,[r4,#0x49] ... cbnz -> compile path, else bl 0xBCCE8'; sub_BCCE8 = glCreateProgram (#26) + bl 0x8701C; CCPrecompiledShaders::loadProgram RVA 0x8701C: 'movw r1,#0x93a6 ... blx [IAT 0x10195668]'.
- Key function sub_86E00 (RVA 0x86E00): SHA-1 init constants 0x67452301/0xEFCDAB89/0x98BADCFE/0x10325476/0xC3D2E1F0 (literal pool at 0x86F08..0x86F18); updates with strlen(vs), strlen(fs), then glGetString(0x8B8C) (movw r0,#0x8b8c at 0x86E8E, IAT #72).
- Table (CCPrecompiledShaders::loadPrecompiledPrograms, RVA 0x86F38): three parallel arrays of 15 entries: keys (40-hex-char SHA-1 strings) at .data RVA 0x2808CC, blob pointers at RVA 0x280908, blob sizes at .rdata RVA 0x1D1F9C (0x21ED, 0x101B, 0xCCA, ...). Blob 0 at RVA 0x1D1FD8 begins 'A6 93 00 00 8E 09 02 01 00 80 00 00 52 8B 00 00 0A 00 00 00 a_position' = format 0x93A6, ANGLE version dword 0x0102098E (1.2.2446), compile flags 0x8000 (D3DCOMPILE_OPTIMIZATION_LEVEL3), then the attribute list.
- I recomputed SHA-1(vs + fs + "OpenGL ES GLSL ES 1.00 (ANGLE 1.2.0.2446)") for the GLSL strings at the .data table RVA 0x280994 (keymatch.py): 9 of the 15 keys match exactly = the 9 stock cocos2d programs (PositionTextureColor, ...AlphaTest, PositionColor, PositionTexture, PositionTexture_uColor, PositionTextureA8Color, Position_uColor, PositionLengthTextureColor, ControlSwitch). So the precompiled path works for them ONLY while glGetString(GL_SHADING_LANGUAGE_VERSION) returns exactly that text, i.e. while the original ANGLE build is used.
- The other 6 keys (0794CAB8..., 0AB9DD04..., 9AC0A952..., 9C7D16D5..., B47702B4..., CBF43789...) match no source in the DLL. Their pixel shaders are heavy shader-toy style programs with uniforms _CC_Time/_center/_resolution/_blurSize (see F2). No .fsh/.vsh file exists in Assets, and GeometryJumpComponent.dll imports only reloadDefaultShaders, sharedShaderCache, setShaderProgram, getShaderProgram from CCShaderCache/CCGLProgram (no CCGLProgram constructor, no programForKey), so GD itself appears NOT to use them (unverified at run time; they look like cocos2d-x sample-app shaders left in the table).
Proposed fix: Keep this path untouched. Because the binaries are ANGLE-version-specific and the key depends on the version string, do not swap libGLESv2_phone.dll for a different ANGLE build unless the 15 blobs are regenerated (see F7).

### F2. All 30 embedded shader containers are Direct3D feature level 9_3 shaders (vs_2_x / ps_2_x), not level 9_1  [severity: blocker-risk for FL9_1, confidence: high that they are 9_3; medium on what a real FL9_1 GPU does with them]
Claim: libcocos2d.dll embeds 30 DXBC containers (15 vertex + 15 pixel; program n = pixel container 2n + vertex container 2n+1), all built by 'Microsoft (R) HLSL Shader Compiler 9.30.9200.16384' (Windows 8 SDK d3dcompiler_46). Each has chunks Aon9,SHDR,STAT,RDEF,ISGN,OSGN; SHDR is vs_4_0 / ps_4_0; the Aon9 chunk carries a Direct3D 9 token stream whose version token is 0xFFFE0201 (vs_2_x) / 0xFFFF0201 (ps_2_x) in ALL 30, i.e. they were compiled with the *_4_0_level_9_3 profile. (A 9_1 compile gives 0xFFFE0200 / 0xFFFF0200 at the same place.) The earlier note (gd-component F6) that the tokens are vs_2_0/ps_2_0 read the chunk's 2nd header dword, which is 0xFFFE0200/0xFFFF0200 for both levels and is not the discriminator.
Evidence: dxbc.py/aon9.py over libcocos2d.dll (containers at RVAs 0x1D22E1, 0x1D3D5D, 0x1D4473, ..., 0x1E133E; sizes 6780, 1128, 2196, ...). Aon9 layout decoded by comparison: dword0 = chunk size, dword1 = tag (FFFE0200/FFFF0200), dword2 = D3D9 bytecode length, dword3 = D3D9 bytecode offset (0x34 vs / 0x30 ps); the D3D9 version token is the first dword there. Control experiment with SDK fxc.exe 10.0.19041 on my own HLSL (work\t1.hlsl): vs_4_0_level_9_1 -> token FFFE0200, disassembly 'vs_2_0'; vs_4_0_level_9_3 -> token FFFE0201, 'vs_2_x'; ps likewise (FFFF0200/'ps_2_0' vs FFFF0201/'ps_2_x'). `fxc /dumpbin` of every game container prints 'Level9 shader bytecode: vs_2_x' or 'ps_2_x' (work\asm_cocos\*.asm); aon9.py summary: {'ps_2_x (level_9_3)': 15, 'vs_2_x (level_9_3)': 15}. The four heavy pixel shaders also declare 4 render-target outputs (SV_Target 0..3 in OSGN = the 9_3 MRT limit).
Proposed fix: See F7. The decisive unknown is whether a real FL9_1 driver (Surface RT Tegra 3, Surface 2) accepts ps_2_x/vs_2_x Aon9 payloads (F3).

### F3. Desktop test: 9_3 blobs ARE accepted by CreateVertexShader/CreatePixelShader on a *simulated* FL9_1 device - but that is NOT proof for real 9_1 hardware  [severity: major, confidence: high for the test result, low for the extrapolation]
Claim: With D3D11CreateDevice(levels={9_1}) on this Windows 11 x64 PC (HARDWARE and WARP drivers), all 30 game shader containers create successfully (30/30), also at requested 9_2 and 9_3. The project's earlier measurement (arm32/facts/fl91.md section 4b) found the same for level_9_1 blobs and E_INVALIDARG (0x80070057) for plain vs_4_0/ps_4_0 blobs. Why this cannot be extrapolated: on a FL11 desktop GPU driver the runtime hands the SHDR (SM4) bytecode to the driver; on genuine 9_x hardware (Tegra 3 etc.) the runtime must use the Aon9 D3D9 payload, and a ps_2_x token (needs PS 2.x caps) may be rejected by a PS 2.0-only part. No Surface RT / Surface 2 measurement of level_9_3 blobs exists in the repo (grep of arm32/*.md and games_recon/*.md found none): unverified.
Evidence: fltest.py output: 'HARDWARE requested 9_1 -> got 9_1 / shaders ok: 30/30', identical for 9_2, 9_3 and WARP. Files: work\dx_cocos\*.dxbc (extracted from libcocos2d.dll). arm32/facts/fl91.md: 'Device check on an FL9_1 device (hardware + WARP): all 394 compiled blobs -> CreateVertexShader/CreatePixelShader S_OK; plain vs_4_0/ps_4_0 blobs -> 0x80070057'.
Proposed fix: Run the same 30-blob CreateVertexShader/CreatePixelShader probe (tiny ARM32 test exe) once on the real Surface 2 and RT: cheap, and it decides F7.

### F4. The game tells ANGLE "feature level 9_3" no matter what device it really got (confirmed), and ANGLE trusts it  [severity: major, confidence: high]
Claim: In GeometryJumpComponent.dll the code that builds the EGL window (sub_36390) takes the real D3D feature level from the host device (ID3D11Device::GetFeatureLevel, stored at [this+0xC]) and then compares it with the small integers 1, 2, 3 (the ANGLE_D3D_FEATURE_LEVEL enum). The real values are 0x9100/0x9200/0x9300/..., so no comparison ever matches and the default r6 = 3 (= ANGLE_D3D_FEATURE_LEVEL_9_3) is always passed to libGLESv2_phone!CreateWinrtEglWindow. ANGLE then uses that requested value as ITS feature level (renderer+0x7F4) and never reads the real device level in the XAML path. This matches the Windows Phone 8 contract (all WP8 GPUs are 9_3) but is wrong for a 9_1 host device.
Evidence:
- GeometryJumpComponent.dll RVA 0x36040 'ldr.w r3,[r3,#0x94]; blx r3' (ID3D11Device vtable slot 37 = GetFeatureLevel) then 'str r0,[r5,#0xc]' at 0x3604A; sub_36390: 'ldr r3,[r5,#0xc]' 0x363F4, 'movs r6,#3' 0x363FC (bytes 03 26, file offset 0x357FC), 'cmp r3,#1' 0x363FE, 'cmp r3,#2' 0x36410, 'cmp r3,#3' 0x36414 (the beq/bne only select r6 = 1 / 2 / 3 for raw values 1/2/3). r6 is then passed as the 2nd argument of CreateWinrtEglWindow (IAT libGLESv2_phone.dll!#181).
- libGLESv2_phone.dll IWinrtEglWindow feature-level getter RVA 0x1E64: 'ldr r1,[r0,#0xc]; cmp r1,#6; tbb' -> 0:0xB000 1:0x9100 2:0x9200 3:0x9300 4:0xA000 5:0xA100 6:0xB000. Renderer11::createDevice (sub_1BCF8): XAML branch (RVA 0x1BD4E..0x1BDB0) takes device = window->vtable[3], context = window->vtable[4] and stores the IWinrtEglWindow's feature level at renderer+0x7F4 ('str.w r0,[r4,#0x7f4]' at 0x1BDAC); D3D11CreateDevice is only used in the non-XAML else-branch with the array {0xB000,0xA100,0xA000,0x9300,0x9200,0x9100} at .rdata RVA 0x64244.
- Public doc: 'On Windows Phone 8, all devices have GPUs that support feature level 9_3' and shader model 'vs_2_a/ps_2_b (4_0_level_9_3)', 4 simultaneous render targets, max texture 4096: https://learn.microsoft.com/en-us/previous-versions/windows/apps/jj714085(v=vs.105)
Proposed fix: (a) On a host device that really is 9_3 or higher (WARP or a Lumia GPU) leave it alone. (b) On a real 9_1 host device change the immediate at GeometryJumpComponent.dll file offset 0x357FC from 03 26 to 01 26 (ANGLE_D3D_FEATURE_LEVEL_9_1); ANGLE then takes its FL9_1 code paths (F5). Better: leave the DLL untouched and let the host choose by hooking CreateWinrtEglWindow (IAT) to rewrite the int argument - then no binary patch is needed and 9_3 devices keep the native path.

### F5. What ANGLE itself does differently at 9_1 / 9_2 / 9_3 (this build): it already supports 9_1 for everything except the precompiled game shaders  [severity: major, confidence: high]
Claim: libGLESv2_phone.dll switches on the feature level in a family of Renderer11 capability virtuals. In THIS build 9_1, 9_2 and 9_3 are identical except for the render-target count (1, 1, 4) and the scratch-index width/format used at exactly 9_1. All other limits are the 9_x values: max texture width/height 2048 (even at 9_3), max viewport 2048, no 32-bit indices, no instancing, non-power-of-two textures reported as supported, occlusion queries supported; >=10_0 gives 8192/16384, 8 render targets, 32-bit indices, instancing. Largest game texture is 2048x2048, so the 2048 cap fits both ANGLE and a real 9_1 device.
Evidence (libGLESv2_phone.dll, Renderer11 vtable RVA 0x94584, each function reads 'ldr.w r3,[r0,#0x7f4]'): getMaxTextureWidth sub_1F2DC and getMaxTextureHeight sub_1F34C and getMaxViewportDimension sub_1F26C: 9_1/9_2/9_3 -> 'mov.w r0,#0x800' (2048), 10_0/10_1 -> 0x2000, 11_0 -> 0x4000; getMaxRenderTargets sub_1F448: 9_1 -> 1 (0x1F49E), 9_2 -> 1, 9_3 -> 4 (0x1F46E 'movs r0,#4'), >=10 -> 8; get32BitIndexSupport sub_1F3BC: 9_x -> 0, >=10 -> 1; getInstancingSupport sub_1F0A4: 9_x -> 0; getNonPower2TextureSupport sub_1EFEC: all levels -> 1; getOcclusionQuerySupport sub_1F048: all -> 1; getMajorShaderModel sub_1F180: 9_x -> 2, 10_0/10_1 -> 4, 11_0 -> 5. FL9_1-only branches: IndexBuffer11::getIndexFormat sub_19A8C (GL_UNSIGNED_INT: 'cmp.w r3,#0x9100; ... movs r0,#0x39' = R16_UINT at 9_1, else 0x2A = R32_UINT), Renderer11::drawLineLoop sub_1D60C and drawTriangleFan sub_1D868 ('cmp.w r3,#0x9100; ble' at 0x1D7B4/0x1DA14 -> 16-bit scratch-index helpers sub_214A4/sub_21638 instead of the 32-bit sub_21380/sub_21568). Swap chain: SwapChain11::resetOffscreenTexture (RVA 0x23C44) creates the offscreen colour texture with BindFlags 0x28 (RENDER_TARGET|SHADER_RESOURCE) and the depth-stencil texture with BindFlags 0x40 (DEPTH_STENCIL only), both fine for 9_x. Largest PNG in Assets: GJ_GameSheet-hd.png 2048x2048 (200 PNGs measured; none above 2048; 111 have a non-power-of-two side, e.g. GJ_GameSheet03-hd.png 1682x1682). Public contract for 9_1/9_2: Texture2D max 2048, 9_3: 4096; index buffers R16_UINT only at 9_1; NPOT textures only with one mip level and no WRAP sampler: https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-device and the jj714085 page above.
Consequences if the game keeps asking for "9_3" on a real 9_1 device (F4): GL_LINE_LOOP and GL_TRIANGLE_FAN draws would use 32-bit scratch index buffers (not valid at 9_1; cocos2d uses these only in ccDrawPoly/ccDrawSolidPoly style debug/primitive drawing, so rarely); everything else behaves the same. Minor unverified risk: NPOT textures with GL_REPEAT (ANGLE reports NPOT as supported at all levels so it will not substitute; D3D 9_x says WRAP on NPOT is not allowed).
Proposed fix: none in ANGLE itself. Use F4's feature-level override so ANGLE selects the 9_1 branches on a 9_1 device.

### F6. ProgramBinary::load copies the DXBC bytes straight into CreateVertexShader/CreatePixelShader; there is no feature-level or adapter check  [severity: major, confidence: high]
Claim: glProgramBinaryOES -> ProgramBinary::load (libGLESv2_phone.dll sub_14A04) checks only: first dword == 0x93A6, second == 0x0102098E (hard-coded ANGLE 1.2.2446), third == 0x8000 (compile flags). It then reads attribute/uniform tables, three sizes (pixel, vertex, geometry), skips a 16-byte adapter-identifier block WITHOUT comparing it, and calls Renderer11::loadExecutable (vtable slot at +0x128 = sub_1FEDC) for the pixel shader (type 1) and the vertex shader (type 0). sub_1FEDC calls the host device's ID3D11Device vtable slot 15 (CreatePixelShader, offset 0x3C) / slot 12 (CreateVertexShader) with the unchanged bytes and keeps a memcpy of them (ShaderExecutable11) that is later used as the signature blob for CreateInputLayout. If the device refuses a shader the load fails with 'Could not create pixel shader.' / 'Could not create vertex shader.' and the program stays unusable (anything drawn with it is missing). No other FL logic is involved.
Evidence: sub_14A04: 'movw r5,#0x93a6; cmp r4,r5' 0x14A38/0x14A42, 'ldr r2,[pc,#0x580] = 0x0102098e; cmp' 0x14A56/0x14A62, 'cmp.w r3,#0x8000' 0x14A8E; after the sizes 'adds.w r1,r3,#0x10' 0x14EC4 (no memcmp of the 16 bytes); 'ldr.w r4,[r4,#0x128]; blx r4' 0x14EE4/0x14F0A; strings at 0x6A5DC/0x6A5FC. sub_1FEDC: 'ldr r4,[r4,#0x3c]' 0x1FF9A (type 1) and the type-0 branch at 0x1FFEE. Layout of a program binary in libcocos2d.dll (blob 0 at RVA 0x1D1FD8): ... dword 3, then sizes 0x1A7C (pixel container), 0x0468 (vertex container), 0 (geometry), 16 bytes adapter id (starts 'E8 67 00 00 ...'), then the pixel DXBC (container 0 at RVA 0x1D22E1) immediately followed by the vertex DXBC (container 1 at RVA 0x1D3D5D) - for every blob i the pixel container is container 2i and the vertex container 2i+1.
Proposed fix: See F7 - the cleanest interception point is the host's device vtable (CreateVertexShader/CreatePixelShader/CreateInputLayout), not the program binary.

### F7. Verdict for FL 9_1 and the minimal change set  [severity: major, confidence: medium-high; the only unmeasured link is real Tegra behaviour]
Claim: ANGLE (F5), the game's pixel formats/sizes (F5) and ANGLE's own internal blit/clear shaders (F8) are all compatible with a real FL9_1 device. The single thing that is built for 9_3 is the set of 9 shader programs the game really uses (F1, F2). Microsoft's 10Level9 contract says a 9_1/9_2 device 'Must use ps_4_0_level_9_1' / 'vs_4_0_level_9_1' (9_3 devices may use either). My x64 test shows the desktop runtime does not enforce it for a simulated 9_1 device (F3), so whether Tegra 3 / Surface 2 accept ps_2_x/vs_2_x payloads is open. Therefore: do NOT assume it works; test it (30-line probe), and have the fix ready. The fix is small because the 9 programs are tiny (pixel 4..12 slots, vertex 10..12 slots, at most 2 textures, no loops, one discard):
 | blob idx | program (key prefix) | pixel container (slots) | vertex container (slots) |
 | 2 | ShaderControlSwitch 403B8617 | 4 (8, 2 tex) | 5 (11) |
 | 3 | ShaderPositionTexture 5132957B | 6 (5) | 7 (10) |
 | 4 | ShaderPositionTextureColorAlphaTest 61ACD51E | 8 (12, discard) | 9 (11) |
 | 5 | ShaderPositionLengthTextureColor 6A3FEBEA | 10 (10) | 11 (12) |
 | 6 | ShaderPosition_uColor 6C80A531 | 12 (4) | 13 (10) |

 (container numbers = index in the order of DXBC containers inside libcocos2d.dll, first at RVA 0x1D22E1; names derived by matching the SHA-1 keys to the GLSL pairs, F1.) The other 6 programs (blob idx 0,1,8,9,10,12) have pixel shaders of 245/31/166/91/34(9 texture reads)/120 slots; four of them exceed the level_9_1 pixel limit of 64 arithmetic + 32 texture instructions (Microsoft table: https://learn.microsoft.com/en-us/windows/desktop/direct3dhlsl/specifying-compiler-targets), so they can never run on 9_1 - but nothing in GD references them (F1), so they can be ignored.
 PROOF OF CONCEPT (done): I hand-wrote HLSL for program 13 (ShaderPositionTextureColor; uniform float4x4 _CC_MVPMatrix; VS inputs TEXCOORD0=a_color, TEXCOORD1=a_position, TEXCOORD2=a_texCoord; outputs TEXCOORD0=v_fragmentColor, TEXCOORD1=v_texCoord, SV_Position; position = mul(transpose(M), p) then p.y=-p.y, p.z=(p.z+p.w)*0.5; PS = v_fragmentColor * tex.Sample(...), names texture__CC_Texture0 / sampler__CC_Texture0). Compiled with fxc 10.0.19041 at plain vs_4_0/ps_4_0 it gives EXACTLY the same SM4 instruction streams as the shipped containers 27 and 26 (dp4 cb0[i], v1 ... mov o2.y,-r0.x ... mul o2.z,r0.x,l(0.5)); compiled at vs_4_0_level_9_1 / ps_4_0_level_9_1 its Buffer Definitions, Resource Bindings, Input signature, Output signature and 'Constant buffer to DX9 shader constant mappings' sections are byte-for-byte identical to the shipped level_9_3 vertex shader (diff empty) and identical to the pixel shader except the output name case (SV_TARGET vs SV_Target - fix by writing SV_Target); the Aon9 payload becomes vs_2_0 (11 slots) and ps_2_0 (3 slots with one oC0, or 5 slots with the same four oC0..oC3 writes). So a level_9_1 replacement is drop-in compatible with the ANGLE program tables (same cbuffer layout, register mapping and semantics).
Evidence: work\poc_ptc.hlsl, work\poc\*.asm (fxc /dumpbin and /Fc outputs), interface diff run in the shell (empty for the VS). Original shaders: work\asm_cocos\libcocos2d_26_*.asm and _27_*.asm.
Proposed fix (recommended order):
 1. Probe first (ARM32 test exe, 30 lines): D3D11CreateDevice({9_1}) on the real Surface RT and Surface 2, then CreateVertexShader/CreatePixelShader on the 18 containers of the 9 used programs (bytes from libcocos2d.dll) and print HRESULTs; also log adapter description, GetFeatureLevel for a request list up to 11_1 (the true max level was never logged, see F9). If all 18 succeed the shaders need no change at all (then only F4 matters).
 2. If any fail: add ~18 replacement DXBC containers (hand-written HLSL as in the PoC, one pair per program, level_9_1, single SV_Target) to the host and intercept ID3D11Device::CreateVertexShader (slot 12), CreatePixelShader (slot 15) and CreateInputLayout (slot 11) on the host's device vtable: if the incoming container's header checksum (bytes 4..19 of the DXBC) matches one of the 18 originals, substitute the replacement. This needs no change to libcocos2d.dll/libGLESv2_phone.dll and keeps the original blobs valid for 9_3 devices (the shim is inactive when GetFeatureLevel() >= 9_3). The 0.10.4 host already wraps ten Create* entries of the device vtable (arm32/v0_10_4/INTEGRATION_NOTES.md), the same pattern as the Bad Piggies shim design (games_recon/bad_piggies_hw-design.md).
 3. Apply F4's feature-level override (1 on a 9_1 device) so ANGLE chooses 16-bit scratch indices and 1 render target.
 Not recommended: rebuilding all 15 ANGLE program binaries (ProgramBinary layout would have to be rewritten and the SHA-1 table in libcocos2d.dll patched) or building a different ANGLE (the keys include the ANGLE version string, F1).

### F8. ANGLE's own internal shaders (blit / clear / swap) are already level_9_1: ANGLE was built to run on 9_1 hardware  [severity: info, confidence: high]
Claim: libGLESv2_phone.dll embeds 10 DXBC containers (3 vertex + 7 pixel shaders: passthrough / clear / luminance / alpha variants) and ALL are level_9_1 (Aon9 tokens 0xFFFE0200 / 0xFFFF0200, disassembly vs_2_0 / ps_2_0, no STAT/RDEF chunks). One of them, the clear pixel shader (container 3, RVA 0x063CA8), writes oC0..oC3 even at ps_2_0, so a ps_2_0 shader writing four colour outputs is something this ANGLE build already ships for its own use. This lowers (does not remove) the risk that the 4-output game pixel shaders are what a 9_1 driver rejects: the open item is ps_2_x vs ps_2_0.
Evidence: dxbc.py on libGLESv2_phone.dll: containers at RVAs 0x0636D0 (vs), 0x0638C0 (ps), 0x063AA8 (vs), 0x063CA8 (ps), 0x063EB8, 0x0640B0, 0x064280, 0x064458 (ps), 0x0645A0 (vs), 0x0647A0 (ps); fxc /dumpbin: 'ps_2_0 dcl t0 / mov oC0,t0 / mov oC1,t0 / mov oC2,t0 / mov oC3,t0' for container 3 (work\asm_gles\libGLESv2_phone_03_ps_4_0_rva063ca8.asm). The 4-output form is what ANGLE emits for gl_FragColor at maxRenderTargets=4; all 15 game pixel shaders write oC0..oC3 identically (work\asm_cocos, e.g. libcocos2d_26 'mov oC0,r0 / mov oC1,r0 / mov oC2,r0 / mov oC3,r0'). fxc also compiles a four-SV_Target pixel shader at ps_4_0_level_9_1 without error (t2.hlsl), giving ps_2_0 with oC0..oC3.
Proposed fix: none; informational. A single-output level_9_1 replacement (F7) avoids the question entirely.

### F9. What the desktop host provides instead of the WP8 compositor: a device, a render-target texture and nothing else (no HWND, no CoreWindow, no swap chain for ANGLE)  [severity: major, confidence: high]
Claim: In this build ANGLE never creates a swap chain or window. The EGL "native window" is a pointer to a COM interface pointer: eglCreateWindowSurface(dpy, config, EGLNativeWindowType win, attribs) treats win as IUnknown** (loads *win, AddRef via vtable[1], passes it on, releases it afterwards). ## Summary
Geometry Dash draws everything through cocos2d-x on top of Microsoft's "ANGLE for Windows Phone 8" (libEGL_phone.dll + libGLESv2_phone.dll, ANGLE 1.2.0.2446). Answers to the five questions:

1. Feature level. ANGLE does not ask Windows for a level in this setup: the game hands it the Direct3D device from the compositor, and the game then tells ANGLE "feature level 9_3" in every case (it compares the real level 0x9100/0x9300 with the numbers 1/2/3, a comparison that can never match, so the default 3 always wins; GeometryJumpComponent.dll RVA 0x363FC, F4). ANGLE itself is not the problem at 9_1: its limits are texture 2048 (also at 9_3), no 32-bit indices, no instancing, one render target at 9_1/9_2 (four at 9_3), and it has explicit 9_1 code (16-bit index buffers); the biggest game texture is exactly 2048x2048 (F5). What is built for 9_3 is the shader code.

2. Shaders. There is no shader compiler anywhere in the process. cocos2d-x ships 15 pre-made ANGLE program binaries and loads them with glProgramBinaryOES, picking one by a SHA-1 of the GLSL text plus the ANGLE version string; I reproduced the hash and matched 9 of the 15 to cocos2d's 9 stock programs (the other 6 are heavy sample-style shaders GD never uses). The DirectX bytecode inside is all "level 9_3" (vs_2_x / ps_2_x, four colour outputs). That is the correction to the earlier component note, which read the wrong header field and called it 9_1-style (F1, F2). Microsoft's documentation says a 9_1 device must use level_9_1 shaders; my test on this PC accepted the 9_3 shaders on a simulated 9_1 device, but a desktop GPU driver is not the same as a Tegra 3 driver, so real behaviour is unknown (F3).

3. Window/surface. ANGLE needs no HWND, no CoreWindow, no swap chain: the game passes ANGLE the compositor's device, context and render-target view on every frame; the "native window" is a COM object ANGLE makes itself. The desktop host only has to supply a real D3D11 device and a BGRA render target and then put that texture on screen itself (with the 90-degree rotation described in gd-component F9) (F9).

4. WARP. Microsoft documents WARP (software D3D11, 9_1 to 11_1) for Windows 8, 10 and Windows RT, and for ARM64; nothing documents it for the ARM32 Windows 10 build on the Surface 2. A WARP device at 9_3 would run GD's shaders unchanged; the cost is CPU speed (unmeasured). Interesting lead from the project's own Surface 2 logs: the "hardware" adapter there is called "Software Adapter" (vendor 0, 0 MB), so that tablet may already be a software-class device where 9_3 is available, but the host always capped the level to 9_1 so nobody has seen the true maximum (F10).

5. Verdict for FL 9_1: possible, with a small and well-understood change. The change is to give the 9 used shader programs level_9_1 versions (18 tiny shaders, 4-12 instructions each; a hand-written HLSL proof of concept reproduces the shipped program exactly and its level_9_1 build has an identical interface, F7) and to let ANGLE believe it is at 9_1 on a 9_1 device (one immediate, or hook the call). Both can be done from the host without editing the game DLLs (swap the bytecode when CreateVertexShader/CreatePixelShader/CreateInputLayout see the original; the same pattern as the 0.10.4 host and the Bad Piggies design). Nothing here is a blocker, but it has not been proven on real Tegra hardware.

Recommended next step: before writing any shader code, build the tiny ARM32 probe described in F7 step 1 / F10 and run it on the Surface RT and the Surface 2: (a) create a {9_1} device and try CreateVertexShader/CreatePixelShader on the 18 original containers; (b) list adapters and the highest feature level HARDWARE and WARP give; (c) time a few hundred fullscreen quads. Its three answers choose between "nothing to change", "level_9_1 shader swap", and "WARP at 9_3". Then continue with the host skeleton of gd-component F11.
