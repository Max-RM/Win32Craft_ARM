### F7. Separate-alpha blend factors in 4 of the 5 blend states are the only construct that the FL 9_1 capability table marks as "No" (watch item; the per-method documentation does not list it as an error)  [severity: minor, confidence: medium-low]
Claim: all five blend states set SrcBlendAlpha=ONE, DestBlendAlpha=ZERO, BlendOpAlpha=ADD (sub_76304 stores at 0x76338-0x76340 into [r7+0x30], [r7+0x34], [r7+0x38]); only state (ONE,ZERO) has alpha factors equal to its colour factors, the other four - (ONE,ONE), (SRC_ALPHA,INV_SRC_ALPHA), (ONE,INV_SRC_ALPHA), (ZERO,SRC_COLOR) - need "separate alpha blend". Microsoft's feature-level table lists "Separate Alpha Blend: No" for 9_1 (Yes for 9_2 and 9_3), but the per-method 10Level9 page for CreateBlendState at 9_1 lists only AlphaToCoverage / BlendEnable consistency / SRC_ALPHASAT / dual-source as errors, so the documentation does not say that mismatching alpha factors make CreateBlendState fail. It is not proven either way for Tegra 3/4 drivers. If the runtime does reject, sub_76304 throws a Platform::Exception (CreateException + _CxxThrowException at 0x7636A) during sub_765B8, which runs from sub_6C808 at start-up, and the process dies (hard blocker but trivially avoidable). ## Summary
Plain-language verdict: Redcon's graphics side is a very good fit for the 9_1-only Surface RT and Surface 2. It was written in the style of an OpenGL-ES-2 game: all 10 shaders (5 vertex + 5 pixel) are precompiled Direct3D "level 9" shaders (shader model 2.0 payload, tiny: at most 7 pixel-shader and 58 vertex-shader instructions, one constant buffer, one texture) that sit in the 14 KB file res/shaders. That file is lightly encrypted with a fixed stream cipher which the game itself undoes in memory; I reproduced the cipher and the decrypted file is ten ordinary DXBC blobs. There is no runtime shader compiler, no depth buffer, no render-to-texture, no instancing, no 32-bit indices, no mipmaps, no multiple render targets, no geometry or compute work. The game asks Windows for a device with the level list 11_1 ... 9_1 and never looks at which level it received, so on the Surface it simply gets 9_1 and nothing has to be faked. All texture files are at most 2000 pixels on the longest edge (the 9_1 limit is 2048), every texture has one mip level and clamp addressing, and the two textures that are tiled are (by inference) power-of-two, which is the combination that 9_1 allows for non-power-of-two images. The swap chain is the standard composition chain (B8G8R8A8, 2 flip buffers, screen-sized, Present(1,0)), the same shape as the one the 0.10.4 host already replaces with an HWND chain. Two small unknowns remain that only a device run can settle: four of the five blend states use "separate alpha" factors, which the Microsoft capability table lists as not supported on 9_1 (the method documentation does not say it is rejected, the alpha channel is ignored anyway, and a ready 3-line fallback exists), and the game draws its text with Direct2D 1.2 / DirectWrite on the same device (should work on Windows RT 8.1 and Windows 10 ARM32, unverified). Compared with 0.10.4 this area is easier: no shader-profile patch, no feature-level lie, just pass the game's own level list through.
Recommended next step: build the 'redcon' host profile with the D3D11CreateDevice hook in pass-through mode (cap = game list), reuse the panel unit's swap-chain/HWND replacement and the always-on Create* failure logging, and do one Surface 2 and one Surface RT run; if the log shows CreateBlendState E_INVALIDARG, enable the alpha-factor fallback from F7. Nothing in this area blocks the port.

FEASIBILITY: good
