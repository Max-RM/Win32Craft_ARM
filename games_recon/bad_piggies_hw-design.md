## Findings

### F1. Gate zero: nobody has proven the Surface 2 "hardware" 9_1 device is the Tegra GPU  [severity: blocker (for the GPU goal on Surface 2), confidence: high that it is unproven, low on the answer]
Claim: every Surface 2 (Win10 15035) log prints the adapter behind the host's HARDWARE FL 9_1 device as `"Software Adapter" VendorId=0000 DeviceId=0000 ... DedicatedVideoMemory=0 MiB SharedSystemMemory=973 MiB`, together with `D3D11_FEATURE_D3D9_OPTIONS: FullNonPow2TextureSupport=1`. A Tegra driver would normally report the NVIDIA vendor id (0x10DE) and a name; Microsoft's Basic Render Driver (WARP as an adapter) reports 0x1414. Vendor 0 + "Software Adapter" fits neither. Full NPOT support at 9_1 is also what WARP reports, and is not typical for a D3D9-class GPU (unverified for Tegra 4). So the existing "hardware 9_1" device on the Surface 2 may already be a software renderer. If it is, there is no GPU path to win on that OS image, whatever is done to Unity. The Surface RT logs (RT 8.1) do not print the adapter at all. Every log is clamped to {0x9100} by the host, so the true maximum feature level of either device is not recorded anywhere.
Evidence: arm32/device_logs/surface2_win10_0104_1346dll_backbutton.log lines 240-248 (request `levels(5)=[B100 B000 A100 A000 9300] -> cap=0x9100`, `selected feature level 0x9100 ... driver HARDWARE`, adapter line 243, D3D9_OPTIONS line 247); same adapter line in surface2_win10_0104_r4dll.log:242 and win32craft_0104_gamestate_run.log:242/802/1656/2161; win32craft_surfacert_touch_legacy_singletouch.log lines 123-132 (RT 8.1: no adapter line). For contrast, the phone reports `"POCO X3 Pro Adreno 640 GPU" VendorId=4D4F4351` (win11_arm64_0104_friend.log:248). bp-app F11 and bp-render F9 raise the same question.
Proposed fix: milestone M0 (before any engine work) = a probe exe run once on Surface RT and Surface 2: (1) IDXGIFactory1::EnumAdapters loop, printing GetDesc1 for each adapter (Flags & DXGI_ADAPTER_FLAG_SOFTWARE, VendorId, LUID); (2) D3D11CreateDevice on each adapter with the full list [11_1..9_1] -> hr + chosen level; (3) after creating the HARDWARE 9_1 device, list the loaded modules (EnumProcessModules): d3d10warp.dll loaded = software, a vendor user-mode driver (NVIDIA Tegra UMD) loaded = GPU; (4) a fill-rate test: 200 blended full-screen quads at 1366x768 / 1920x1080, timed, HARDWARE vs WARP. If HARDWARE == WARP speed and d3d10warp.dll is loaded, stop the GPU plan for that device and tell the user.

### F3. The 9_1 caps row must claim shader mask 0xE3 ("target 3.0"), not 0x1 ("2.0") - otherwise Unity may drop most of the game's shaders  [severity: major, confidence: medium (requirement masks measured; the runtime filter itself not traced)]
Claim: every SerializedSubProgram carries m_ShaderRequirements (UnityPlayer transfers it in sub_a0708 @0x000a0ad8, field at +8 of the struct). Over all 1128 D3D11 sub-programs the masks are 0x1 x354, 0x21 x714, 0xE3 x1704 (counted per tier entry), 0xEEB x6, 0xFEB x138, 0x4021 x48, 0x10CEEB x12. The programs the game needs use only 0x1 (210), 0x21 (318) and 0xE3 (180): TextMeshPro distance-field, TextMeshPro/Sprite and the INShaders/* sets are "target 3.0" (0xE3), most _Custom/* and Spine/e2d shaders are "target 2.5" (0x21). These masks use the same bit layout as the caps field caps+0xBC that sub_8d7930 maps to shader levels (0x1 -> 20, 0x21 -> 25, 0xE3 -> 30; hw-unitygfx F4), and the player contains the self-test strings "CHECK_EQUAL(kShaderTarget25_93, GetApproximateShaderTargetLevelFromRequirements..." (0x01f805c8) and "... shader is not supported on this GPU (none of subshaders/fallbacks are suitable)" (0x01d5dcb0). Unity's own 2018.4 manual says FL 9.x devices are "treated as only capable of shader model 2.5" and target 3.0 is "Not supported on DX11 feature level 9.x GPUs". So if the 9_1 caps row used the honest 0x1 (or even Unity's old 9.x value 0x21), any requirement check would reject the 0xE3 programs (TMP text, INShaders) and most 0x21 programs, and Unity would fall back to the pink error shader. Every needed program was proven to compile at level_9_1 (hw-shaders F5, F2 above), so claiming 0xE3 is safe for this game: the bits are about the original HLSL target, not about what our replacements need. Bits that must stay OFF: 0x800 (instancing), 0x400 (2D arrays), 0x2000 (cube arrays), 0x4000 (compute).
Evidence: scratch script design\req2.py over the hw-shaders parse (out\shaders.pkl + auto\all_programs.csv): "needed-program requirement masks: {'0x1': 210, '0x21': 318, '0xe3': 180}"; `arm32re.py dis a0ac0 20` (`ldr.w r3,[r8,#8]` / "m_ShaderRequirements" @0x000a0ad4..0x000a0ad8); `arm32re.py strx GetApproximateShaderTargetLevel`; https://docs.unity3d.com/2018.4/Documentation/Manual/SL-ShaderCompileTargets.html ("WP8/WinRT platforms (DX11 feature level 9.x) are treated as only capable of shader model 2.5"; target 3.0 "Not supported on DX11 feature level 9.x GPUs"). Where the player compares requirements with caps+0xBC was NOT traced (unverified).
Proposed fix: patched caps row for 9_1 = {FL 0x9100, shaderCaps 0x000000E3, maxTex 2048, maxCube 512, UAV 0}. Log Unity's "not supported on this GPU" / "All passes removed" warnings in M3 to confirm.

### F4. End-to-end proof on this PC: Unity's own Sprites/Default bytecode -> checksum lookup -> level-9 replacement -> draw at FL 9_1 gives the right pixel; device interfaces allow a clean per-object hook  [severity: info, confidence: high (PC), medium (Tegra)]
Claim: the bench takes Unity's original Sprites/Default programs (orig/00_Sprites_Default_b000_vs_756ae2904e92.dxbc, b004_ps_3aa3dabc65f1.dxbc), looks them up by DXBC checksum in l9_replacements.bin (both hit), creates the replacements plus a Unity-style input layout (POSITION R32G32B32_FLOAT, COLOR R8G8B8A8_UNORM, TEXCOORD0 R32G32_FLOAT, stride 24), fills Unity's four cbuffers at Unity's byte offsets ($Globals _Color @32, unity_ObjectToWorld @0, unity_MatrixVP @272, _RendererColor/_Flip), and draws a quad with R16 indices, a D24S8 depth buffer cleared to 0, GREATER_EQUAL (Unity's reversed Z). The read-back pixel is exactly 200 100 50 255 (expected 200 100 50 255) on Intel HW (with and without the debug layer) and on WARP, all at FL 9_1. `VSSetShaderResources(NULL)` / `VSSetSamplers(NULL)` (engine-style unbinding; docs: "Not supported on any 9.* feature level") produced no error and no device removal. The two internal blit programs embedded in UnityPlayer.dll (file offsets 0x266ba38 / 0x266bc70) are keyed in the table (checksums 6e4f5026... and 5daf5b73... found), the VR array-blit pair (0x266bec8 / 0x266c1b0) is not, as expected.
Object identity: QueryInterface for ID3D11Device1 and ID3D11Device2 returns the SAME pointer and the same vtable as ID3D11Device, both with and without the debug layer. The device vtable sits in a read-only image page (protect 0x2, MEM_IMAGE). Without the debug layer, the immediate context's vtable is in a private read-write heap page (protect 0x4, MEM_PRIVATE): the runtime builds and rewrites it at run time, which matches the 0.10.4 HUD investigation ("the D3D runtime rewrites its draw/clear vtable cells"). Consequence: device methods can be hooked by giving the one device object a private copy of its vtable (no VirtualProtect, covers Device/Device1/Device2). Context methods should NOT be hooked by swapping the vtable pointer. The base design therefore needs no context hooks at all.
Also without the debug layer, `IASetIndexBuffer(R32_UINT)` removed the Intel device (0x887A0020).
Evidence: scratchpad design\bench_hw.txt, bench_warp.txt, bench_hw_nodebug.txt (lines "lookup Sprites/Default VS hit, PS hit", "read-back centre pixel RGBA = 200 100 50 255", "identity: device=... vtbl=00007FFD27299148 | Device1=<same> | Device2=<same>", "context vtable=... page protect=0x4 type=0x20000"); design\blitcheck.py output ("0x266ba38 ... in table: True", "0x266bc70 ... in table: True", "0x266bec8 ... False").
Proposed fix: use per-object vtable copies for the device. Hook the context (by patching cells in its RW table and re-patching, as the 0.10.4 host does) only if device logs show a need.

### F5. Recommended design ("S+"): a D3D11 shim that is active only below FL 10, plus a caps fix-up inside Unity's caps init  [severity: major, confidence: medium-high (anchors checked statically, nothing run on ARM)]
Claim:
 - Entry. UnityPlayer imports three functions from d3d11.dll by name. Appx route: put the shim DLL in the package folder and point UnityPlayer's d3d11 import descriptor at it, using the IMPORT_REDIRECTS code in tools/whatsapp/make_whatsapp_package.py (lines 453-468). The shim forwards all three exports. It resolves the two interop exports lazily, so a missing one only costs E_NOTIMPL, which also removes one RT 8.1 loader blocker (bp-app F5). Host route: the same C file is built into win32craft.dll and installed on UnityPlayer's IAT cell at RVA 0x01717894, like the existing D3D11CreateDevice hooks.
 - Policy. The shim first calls the real D3D11CreateDevice with Unity's arguments unchanged. On success (any FL 10+ GPU, the Adreno phone, Basic Render) it returns at once: no hooks, no caps changes. On DXGI_ERROR_UNSUPPORTED for a HARDWARE/UNKNOWN call it retries the same adapter with [9_3, 9_2, 9_1]; the runtime picks the highest, so a 9_3 Lumia gets 9_3. If that also fails, it returns the original error, and Unity's own WARP retry (@0x00ffc88a) runs untouched (route W). Config switches: l9=auto|off|force, warp=allow|deny. L9 mode also requires the expected bytes at every anchor RVA below; otherwise the shim logs and takes the error path.
 - Caps fix-up with data writes only, no code bytes changed:
   - GetFeatureLevel (device slot 37, +0x94) is called once by sub_1007434 (blx 0x010075a0, return address 0x010075a3). Two options: (i) return 0xA000 to that one caller, so sub_100ef64 picks row 0 and all row-index-derived flags (+0x3f8, +0xff, +0x394, +0x386, +0x3d9) stay off; or (ii) keep 0x9100 and rewrite row 0 of the .rdata table at 0x026767b8 in memory (a data page). Every other caller gets the true 0x9100.
   - The rest of sub_1007434 stores constants (verified: +0x104 @0x0100776c, +0x375/+0x376 @0x010077c2/c6, +0x378/+0x37c @0x010077e6, +0x36c @0x01007808, +0x107 @0x010078ec, +0x3d4/+0x3d5 @0x0100792e/32, +0xec @0x010079a2, +0xbc @0x0100763a, +0xdc/+0xe4 @0x010077b2/ba, +0xe0 @0x010077ca). Its last device calls are CheckFeatureSupport (slot 33, +0x84): OPTIONS1 via Device2 (blx 0x010079e2, return 0x010079e5; after it Unity only stores +0x3e0, +0xbc|0x40000 when tiled tier >= 2, +0x3e4, +0x3d9), and on Windows 10 OPTIONS3 (blx 0x01007a3e, return 0x01007a41; after it only +0x389). The CheckFeatureSupport hook recognises these two return addresses and overwrites the caps fields in the caps object (*(UnityPlayer+0x0298ed40)). Values: shaderCaps 0xE3 (F3), maxTex/maxRT 2048, maxCube 512, UAV 0, +0x104 32-bit indices 0, +0xec RT count 1, +0x378 NPOT = 2 if D3D9_OPTIONS FullNonPow2TextureSupport is 1 else 1, +0x375/+0x376 3D textures 0, +0xe8 256, +0x107 MSAA textures 0, +0x36c mirror-once 0, +0x3d4/+0x3d5 async readback 0, +0x3e4 copy support 0.
 - Device hooks, installed by giving the one device object a private copy of its vtable (Device/Device1/Device2 share it, F4):
   - CreateVertexShader (12), CreatePixelShader (15), CreateInputLayout (11): swap bytecode by checksum (bytes 4..19) from l9_replacements.bin; log and return E_FAIL on a miss (Unity then uses its error shader).
   - CreateTexture2D (5): map *_TYPELESS colour to the typed UNORM; map R32G8X24_TYPELESS / D32 depth to D24_UNORM_S8_UINT; drop SHADER_RESOURCE from depth textures unless D3D9_SHADOW_SUPPORT is set; force MipLevels=1 for A8_UNORM; log any size above 2048.
   - Views (7, 9, 10): rewrite the view formats to match. An SRV request on a depth texture that cannot be sampled gets a 1x1 dummy SRV.
   - CreateSamplerState (23): clamp anisotropy to 2, MIRROR_ONCE to MIRROR, drop comparison filters without shadow support, MaxLOD = FLT_MAX, integral MinLOD, border colour clamped to [0,1].
   - CreateRasterizerState (22): DepthClipEnable TRUE, DepthBiasClamp 0.
   - CreateBlendState (20) / CreateBlendState1 (45): AlphaToCoverage off, all RT entries equal to RT[0], alpha factors and op equal to the colour ones (the runtime accepts separate alpha, F2, but 9_1 hardware lacks it).
   - CreateDepthStencilState (21): BackFace = FrontFace.
   - No context hooks and no DXGI hooks are needed. The Unity-style swap chain (usage 0x30, flags 0x40, FLIP_SEQUENTIAL) worked at 9_1 (F2), and the caps keep Unity away from 32-bit indices, MRT and instancing.
Evidence: dis output in this session (`arm32re.py dis 1007590 14`, `dis 10079c4 16`, `dis 10079f0 50`, and the stores listed above); `xref 29b1540` -> only `mov32 00ffddfa in sub_ffdc74`, i.e. the FL out-pointer is never read again; `imm 0xa000 --range 0xff0000 0x1020000` -> only sub_ffcba4, so the D3D11 code has no other FL comparison; device slot numbers agree with Unity's own offsets (0x94 GetFeatureLevel, 0x84 CheckFeatureSupport, 0x50/0x54/0x58/0x5c state creators, 0xb4 CreateBlendState1).
Proposed fix: implement as tools/badpiggies/l9shim.c (shared), build x64 for the PC harness and ARM32 for the device.

### F6. The four routes compared  [severity: info, confidence: medium]
 - (S+) shim with the caps fix-up (F5). Work: shim core ~1.5-2.5k lines C (device policy, vtable copy, table loader, sanitizers, caps table, log); packager for the appx route (bp-app F7 plan + import redirect + table file). Unknowns: whether Unity really filters shaders by requirements (F3); whether Unity's NPOT round-up resamples the image (hw-content F5); Unity's handling of the one 2160x1080 texture; Tegra driver behaviour and FP20 pixel precision (Tegra 4 pixel units are FP20 per AnandTech, via search summary). Risks: draw-call cost of the 10Level9 layer on ARM; untraced Unity paths. Effort: 6-9 days to a first Surface 2 run, plus 3-10 days of device-log fixing. Unity runs unmodified on FL 10+ devices.
 - (S) pure shim that reports FL 10_0 and never touches Unity memory. Unity would believe 8192 textures, full NPOT, 32-bit indices and instancing (row 0xa000, F4 of hw-unitygfx), so the shim would also have to resize textures, drop mips on NPOT textures (needs a context hook if Unity uploads mips with UpdateSubresource), fix NPOT+WRAP at draw time, and convert 32-bit index buffers. Those draw-time hooks touch the RW context vtable that the runtime rewrites (F4). Effort +3-6 days over S+, with more fragile parts. Keep it only as the fallback if the caps fix-up fails on device.
 - (P) file patches only (UnityPlayer.dll code/data + the 7 asset files). The caps changes would apply to every device unless written as hand-made Thumb-2 code caves that test the FL. The shaders would have to be rewritten inside the asset files (48 MB resources.assets, LZ4 re-pack, an unexplained 6-byte prefix; hw-shaders F8), and the level-9 programs would then also run on FL 10+ devices (4 trimmed and 8 approximated programs differ there). There is no run-time log. Effort 8-12 days. Rejected because it changes behaviour on FL 10+ devices and is harder to debug.
 - (R) rebuild from source. The public project is Unity 2021.3 + DOTS Entities 0.51 (hw-priorart F4). Only Unity <= 5.6 has FL 9_1, and 2017.4 is 9_3 minimum (hw-priorart F1). That means months of back-porting, plus licensing questions. Rejected.
 - (W) WARP. Already built into Unity, and kept by the S+ policy as the automatic fallback. It needs d3d10warp.dll on the OS (unverified on 15035) and is CPU-bound (bp-render F13).
Evidence: sibling findings cited inline; F2-F5 of this file.
Proposed fix: S+ first; S as fallback; W automatic.

### F7. Performance expectation and the render-resolution knob  [severity: major, confidence: low (estimates, nothing measured on the tablets)]
Claim: published GPU data: Tegra 4 has 72 ALUs (48 pixel : 24 vertex : 4 texture units) at 672 MHz and a dual-channel 32-bit memory interface with up to 14.9 GB/s. Tegra 3 (T30) runs at 520 MHz, with a 32-bit single-channel interface of 4.3-6.0 GB/s (Wikipedia "Tegra" tables). Bad Piggies is a blended 2D sprite game, so fill and bandwidth dominate. A rough model: about 9 bytes per blended pixel (colour read + write + compressed texel) and an assumed overdraw of 6 (not measured).
 - Surface 2 at 1920x1080 and 60 fps needs about 2.07 MP x 6 x 9 B x 60 = 6.7 GB/s, roughly 45 % of the nominal peak. 30 fps looks safe; 60 fps is borderline. The texture rate (4 x 672 MHz = 2.7 GT/s) is not the limit.
 - Surface RT at 1366x768 and 60 fps needs about 3.4 GB/s, 57-79 % of its peak. 30 fps looks plausible; 60 fps is unlikely. At a 0.75 render scale about 1.9 GB/s is needed.
 - WARP, by bp-render F13's estimate: about 10 fps or less at 1080p on Tegra 4, and 8-15 fps at 768p on Tegra 3. WARP also uses the same CPU cores Unity needs, so the GPU route should be several times faster and frees the CPU.
 - Unknown: CPU cost per draw call of the 10Level9 runtime and the Tegra driver; the Unity main thread (IL2CPP + physics) on a Cortex-A9.
 - Back-buffer limit: both panels (1920x1080 and 1366x768) are below the 9_1 2048 limit, so no clamp is needed.
 - Resolution knob, host route: report smaller CoreWindow bounds and give the HWND swap chain the same size (bp-render F12).
 - Resolution knob, appx route: Unity renders at the CoreWindow size, so the only no-code knob is the Windows display resolution of the tablet. A shim cannot shrink the swap chain behind Unity's back.
Evidence: https://en.wikipedia.org/wiki/Tegra (T114 "72 (48:24:4)", "672 MHz", "up to 14.9 GB/s"; T30 "520 MHz", "4.3 GB/s"/"6.0 GB/s"); AnandTech "The Tegra 4 GPU..." (anandtech.com/show/6666, via search summary, page now redirects): FP20 pixel units; bp-render F12/F13.
Proposed fix: log frame time in the shim (count Present via the swap chain Unity creates, or Clear calls) and calibrate in M4.

## Summary
Plain language:
 - Today, on a 9_1-only tablet, Unity cannot use the GPU at all. It either falls back to WARP (software) on its own, or stops with "feature level 10.0 is required".
 - GPU rendering at feature level 9_1 is technically reachable without rebuilding the game: about 111 of 112 needed shaders already have working level-9 replacements. On this PC, a real 9_1-only device refused all 402 original Unity programs, accepted all 113 replacements, and drew a correct test pixel through the lookup.
 - The design is a small D3D11 shim. It does nothing on GPUs that already reach feature level 10, so Unity runs untouched there. Below level 10 it creates a 9_x device, swaps shaders by checksum, cleans up states and formats, and corrects Unity's capability record with data writes only. WARP stays as the automatic fallback.
 - The biggest open question comes first: on the Surface 2 (Windows 10 build 15035) the current "hardware" device reports itself as a vendor-0 "Software Adapter". If that is really software, no GPU route exists on that OS image. The Surface RT on 8.1 (NVIDIA driver) would then be the GPU target, through the Win32Craft host route.
