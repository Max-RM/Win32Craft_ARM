## Summary
Plain-language result. The two native game modules ask the operating system for very little. GeometryJumpComponent.dll (the game glue) activates no Windows class at all; libcocos2d.dll (the cocos2d-x engine) names 17 Windows classes but only 4 are reached while the game runs, and one more (Accelerometer) only if some layer turns tilt on. Because the game is hosted with the XAML-style "Create" call, the whole CoreWindow / DisplayProperties / InputPane part of the engine is switched off by one byte (CCEGLView+0x17C), so nothing there needs faking. What a desktop host must provide, in order of when it is needed:
 1. At start-up (inside the first Draw call): Package.Current.InstalledLocation.Path (the game folder; the engine builds "<folder>\Assets\Resources\" from it and narrows the string to 8 bits per character, so the folder path must be plain ASCII), then ApplicationData.Current.LocalFolder.Path (save/download folder; used early and often), then the ICallback answer for isLowMemoryDevice (called once while the game starts). Before the first Draw the host must also have registered the three Cocos2d delegates (keyboard/exit, message box, edit box), otherwise the engine falls back to a phone-only keyboard class that does not exist on Surface RT / Surface 2 and the game could never be closed from inside.
 2. On demand: Uri + Launcher.LaunchUriAsync (external links), ICallback isNetworkAvailable / getUniqueUserID / openEmail / rateApp, the keyboard / message box / edit box / exit delegates, Accelerometer (probably never).
 3. The phone-only parts that cannot be avoided are the "DrawingSurface" compositor contract (Connect / Disconnect / PrepareResources / Draw, one fake runtime-host object, one fake pointer host with fake pointer event objects; decoded in gd-component), plus two small shim DLLs named PhoneAppModelHost.dll and PhoneAudioSes.dll (gd-deps). Nothing else in the code is Windows-Phone-only: there is no in-app purchase, licensing, ads, vibration, web-browser control, WinRT networking, media library or tile/toast code in the native DLLs or in the managed shell.
Overall verdict: POSSIBLE. I found no hard blocker. The platform-API side is the smallest of the five areas and is already covered by fakes that exist in the project (Package, ApplicationData, Launcher, the activation-factory hook, which must now be applied to libcocos2d.dll itself). What can still go wrong, and can only be settled on the devices: (1) the game's 9 shader programs are Direct3D "level 9_3" shaders and the game always tells its OpenGL layer (ANGLE) that the GPU is 9_3, but Surface RT and Surface 2 are 9_1 (a probe exe and, if needed, 18 replacement shaders plus a feature-level override, or WARP, are the prepared answers); (2) the compositor emulation is new work with two inferred parts (portrait-shaped render target with a 90-degree rotation on present, and the pointer coordinate mapping); (3) the audio shim is written from inferred call signatures. The alternative of a native Windows 8.1 Store (ARM) or Windows Phone 8.1 Geometry Dash could not be verified: the Microsoft Store catalog lists a single Windows Phone 8 package (neutral architecture, minimum Windows Phone 8, released 12 June 2014), an Internet Archive uploader says v2.0.1 is the last version the developer published, and Wikipedia lists only Windows Phone and Steam among the Windows releases. So the WP8 Silverlight package of this run is the build to port, with the managed shell dropped.
Recommended next step: write and run a small ARM32 probe on the Surface RT and Surface 2 (device creation at 9_1 and the highest level HARDWARE/WARP give, CreateVertexShader/CreatePixelShader on the 18 shader containers of the used programs, a timing loop), extend tools/loadcheck with the GD DLLs, and in parallel build the headless host skeleton (activation, ICallback, delegates, fake compositor host, one Draw into an offscreen target) with a logging activation router; the first log must show exactly Package, ApplicationData, isLowMemoryDevice and nothing else before the main menu (F4).
