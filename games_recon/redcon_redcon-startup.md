### F15. Host-integration notes from reading the 0.10.4 units (what must change when Redcon reuses them)  [severity: major, confidence: medium-high]
Claim (each item checked against the named source line of the 0.10.4 host):
 1. `Window.put_Content` (win32_host_arm32_0104_app.inl lines ~782-799) raises the flag `f_content_set` ("the MainPage constructor has returned"), which the panel unit uses to release the first SizeChanged and the async unit uses to open the DispatcherTimer gate. In Redcon put_Content is the 5th action of OnLaunched, BEFORE the SetWindow block, so every gate keyed on f_content_set / AppMain / `client+0xC` (rule R2 and the 'ready tick') must be switched off or the panel unit will log 'first SizeChanged waiting ... / ERROR no swap chain was created' forever. It also tests whether the content is the Page inner it created (`is_page`), which will be false for the panel (log text only).
 2. `x104_ui_pass` (win32_host_arm32_0104_core.inl line 1577) is the single UI-thread pass (queue/timers, panel tick, input tick, app tick; also driven by a 10 ms WM_TIMER pump inside modal loops; re-entrancy guarded by x104_in_pass). The CompositionTarget tick belongs there as one more unit tick. A Rendering handler runs the whole game frame including Present(1,0) (blocks to vsync), so it will usually be called from the loop top, rarely from the WM_TIMER pump; the pump call must be a no-op while a frame is already running (guard exists).
 3. The panel unit's Present stub (win32_host_arm32_0104_panel.inl lines 1634-1653) calls the original Present directly on the calling thread and only does accounting/pacing (x104_present_pace sleeps only when intervals are under 3 ms), so presenting from the UI thread is fine; the pacing text says 'render thread' but nothing depends on that.
 4. Feature-level policy: the panel unit installs a cap/lie ('feature level 9_1 requested, 9_3 reported', shader profile digit patch for `_level_9_x`, ladder at panel.inl line 2169 which already equals Redcon's own list). For Redcon the hook should stay installed (it is also where the dxgi vtable cells are patched) but must pass the game's levels through unchanged and must not patch shader profile strings (none exist).
 5. Threading assumptions that no longer hold: the 0.10.4 async unit assumes a ThreadPool render loop and a CoreIndependentInputSource work item that blocks in ProcessEvents(2); Redcon has neither, so the host's 'work item' accounting, 'AppMain+0xC' guard in the exit path ('Suspending only when ready AND AppMain+0xC != NULL', INTEGRATION_NOTES section 1) and the watchdog ('a game frame call has not returned') need a Redcon variant: Suspending must be raised whenever the Redcon CoreApplication.Suspending handler is registered (handler list non-empty), not keyed to AppMain.
 6. CoreWindow fake: it already supports VisibilityChanged delivery 'only when the render loop exists' (INTEGRATION_NOTES hop 21) - for Redcon deliver it after Window.Activate regardless (the game's handler is idempotent: first call after SetWindow only sets [App+0x76], resume is a no-op while the Rendering token exists).

 8. ## Summary

Plain-language verdict (area: start-up flow and the XAML/WinRT surface of Redcon.exe 1.3.0.0, REDCON 1 by Hexage, ARM32, VS2013 compiler):

1. Redcon boots exactly like Minecraft PE 0.10.4 up to Application::Start: PE entry 0x13A445 -> CRT main 0x13A458 -> the call `bl 0x13A91C` at RVA 0x13A55A (this is the take-over point; the existing generic patcher's `probe` independently picks it as #1) -> WinMain wrapper 0x13AA7C -> user main sub_6EF88 -> Application::Start (statics slot 7 at 0x6F0AC) -> callback -> App ctor sub_6CDF0 -> IApplicationOverrides.OnLaunched sub_6EBD0.
2. After that it is much SIMPLER and different from 0.10.4: there is no MainPage, no XAML loader, no FindName, no DispatcherTimer, no ThreadPool and no render thread. OnLaunched builds one SwapChainPanel in code, makes it Window.Content, registers 17 events (CoreWindow x11, BackPressed, DisplayInformation x2, CoreApplication Suspending/Resuming, NetworkStatusChanged), runs the game's own init (Package/ApplicationData paths, languages, first-run udid), creates the D3D11 device with its own feature-level list 11_1..9_1 (so a 9_1-only Tegra is accepted without any clamp), creates the swap chain with CreateSwapChainForComposition, calls ISwapChainPanelNative.SetSwapChain synchronously, initialises audio, registers CompositionTarget.Rendering and only then calls Window.Activate.
3. Every frame (update, draw, Present(1,0)) runs on the UI thread inside the CompositionTarget.Rendering handler sub_6EE50 (about 35 fps limiter). The host therefore needs ONE new heart piece: a Rendering tick in its UI loop (x104_ui_pass), instead of 0.10.4's thread-pool render loop and ready-gate.
4. Activation inventory: exactly one choke point (sub_139FD4 -> IAT 0x142318), 44 call sites, 29 distinct classes. 12 of them are already faked by the 0.10.4 host, 17 are new (SwapChainPanel factory, CompositionTarget, CoreApplication, ApplicationView, CoreWindowResizeManager, ApplicationLanguages, Launcher, PropertyValue and a code-built dialog set Popup/TextBlock/Border/StackPanel/TextBox/Button/SolidColorBrush/ColorHelper/FontWeights). The slot-level diff is small: 60 slot rows reusable, 28 new (F9); the dialog set is lazy and can be replaced by a Win32 dialog.
5. Loader delta: same VC120 `_app` trio, same api-set contracts; the 0.10.4 shim set lacks 3 imported functions (CoCreateInstanceFromApp, StringFromGUID2, IsProcessorFeaturePresent); Redcon additionally imports d2d1, DWrite and MFPlat (not XAML; Media Foundation is initialised on the first-frame path via the audio init; other areas).
6. Alternative: because the XAML use is tiny and code-built, the re-package-as-appx route (WP81_APP_METHOD) may be even cheaper (3 phone-only classes to neutralise: StatusBar, HardwareButtons, VibrationDevice) - worth one experiment, but the fake-host route is the project's main road and everything for it is mapped here.

Recommended next step: add a 'redcon' profile (call site 0x13A55A, trampoline 0x1414B0, DllCharacteristics 0x9140 -> 0x8140, shims +3 functions), build the 'Redcon unit' for the 28 new slot rows + CompositionTarget tick (disable the f_content_set-gated first-SizeChanged/timer logic, keep the D3D hook pass-through), then run on the PC mock (like test_0104_all.c) and on the Surface 2 with logging at sub_3D60 to catch any failing fake. Parallel cheap experiment: the appx route with 4 call-site patches.
