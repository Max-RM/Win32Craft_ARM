### F2. The feature-level list never contains 9_x, and there is no other FL check  [severity: blocker, confidence: high]

### F3. The code ALREADY falls back from hardware to WARP automatically; -force-driver-type-warp only skips the hardware attempt  [severity: major, confidence: high]
Claim: in sub_ffc7b4, if the first D3D11CreateDevice (0xffc844, adapter = hardware GPU) leaves the device pointer 0x12b2dce0 NULL, the code releases the context/device (0xffc84e..0xffc86c) and calls D3D11CreateDevice(NULL, D3D_DRIVER_TYPE_WARP(5), NULL, flags, same feature-level vector, 7, ...) (0xffc88a), then stores (hr==0) in the byte 0x12b2dc9c. When the requested driver type is already 5 (the -force-driver-type-warp case: r2 = (r8==5)) the first attempt is skipped by "cbnz r2, 0xffc84e" at 0xffc7fe. So on a device whose GPU is FL 9_1 only, the shipped player will (a) fail the hardware call, (b) try WARP, (c) abort with "Failed to initialize Direct3D..." only if WARP also fails. If the user's devices show that message or a black screen, the cause is most likely that the WARP attempt fails or the later swap-chain / shader steps fail - NOT that nobody ever tries WARP. Which of these happens cannot be decided statically (I did not run anything): UNVERIFIED on device.
Why -force-driver-type-warp is still worth forcing: (1) it avoids driving the Tegra / Adreno D3D driver through a doomed D3D11CreateDevice with pAdapter set (a vendor driver that crashes or hangs instead of returning an error would otherwise kill the process before the fallback is reached - unverified, not seen), (2) it makes the choice deterministic and the log (0x12b2dc9c flag, FL out 0x129b1540) easier to read.
Evidence: "func ffc7b4" (cmp r8,#5 at 0xffc7e2; cbnz r2 at 0xffc7fe; second D3D11CreateDevice call at 0xffc88a with r0=0 pAdapter, r1=5 driver type; strb at 0xffc8a2).
Proposed fix: force WARP explicitly (F6, F11); keep the automatic fallback as the safety net.

### F11. Verdict: WARP route versus a hardware route  [severity: major, confidence: medium-high]

## Summary
Plain-language result (nothing was run; all device behaviour is UNVERIFIED, everything about the binaries is read from disassembly):
1. How Unity makes the device (F1-F3): UnityPlayer.dll calls D3D11CreateDevice from one wrapper (RVA 0xffc7b4). It asks for feature levels 11_1, 11_0, 10_1, 10_0 only (there is no 9_x entry anywhere, F2). First it tries the hardware adapter, and if that fails it ALREADY retries by itself with the WARP software rasterizer (F3). Only if WARP fails too does it show "Failed to initialize Direct3D. At least DirectX 11 feature level 10.0 is required". The switch -force-driver-type-warp only skips the hardware attempt. So an FL 9_1 GPU is not by itself fatal: the open question is whether WARP then works on the user's devices.
2. How to switch WARP on (F4-F6): the player has NO file or GetCommandLine route. Arguments can only come from the string[] constructor argument of UnityPlayer.AppCallbacks; the deprecated AddCommandLineArg / ParseCommandLineArgsFromFiles just throw. The shipped BadPiggiesRebooted.exe uses the default constructor, so argc is always 0. It is a CoreWindow (D3D) template, NOT XAML as the task header said (F5). Options: (a) no patch: host interposes on GetActivationFactoryByPCWSTR("UnityPlayer.AppCallbacks") and calls CreateInstance(1, {"-force-driver-type-warp"}) on IID {B67BDCCA-AD4C-38B4-8594-DAA2BCC3EDC4}; (b) one-byte file patch: UnityPlayer.dll file offset 0xffd0de (RVA 0xffdcde) 01 -> 05 (movs r5,#1 -> movs r5,#5); (c) same byte written in memory by the host after LoadLibrary, or - simplest and most robust, no Unity bytes touched - a host hook of UnityPlayer's d3d11!D3D11CreateDevice IAT cell (RVA 0x1717894) that forces pAdapter = NULL, DriverType = 5.
3. WARP availability (F8): Microsoft documents WARP (up to FL 11_1) for Windows 8, Windows 10 and Windows RT, so the Surface RT 8.1 should have it. NOT documented for the Windows 10 ARM32 build 15035 on the Surface 2 -> must be checked on the device.
