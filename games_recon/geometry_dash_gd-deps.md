### F12. SUPERSEDES the F4 CaptureUiThreadContext fix: E_NOTIMPL loses async asset-load completions (loading freezes at ~80%); the correct fix is a working UI-thread IContextCallback  [severity: major, confidence: high on the mechanism, pending device confirmation of the cure]
Claim: The F4 "return E_NOTIMPL always" stub is wrong at run time. GD loads its assets with C++/CX PPL `concurrency::task<byte>().then(lambda)` continuations. With CaptureUiThreadContext returning E_NOTIMPL, `_ContextCallback::_Capture` (sub_2ce94 / sub_8c628) stores a NULL context, so every continuation runs on whichever thread-pool thread completed the antecedent. cocos2d/GL completion work (texture upload / GL object creation) is thread-affine to the render thread, so those completions do nothing useful and the LoadingLayer counter freezes near 80% while the game keeps drawing (main thread never blocks). The fix is to return a REAL IContextCallback whose ContextCallback (slot 3) marshals the continuation onto the render thread, which drains a queue once per frame between Draws. The one subtlety that makes this safe: the two call sites differ by argument. _Capture passes a non-NULL ppContext (0x2CEEC 'mov r0,r4' / 0x8C67A 'mov r0,r4'); _IsCurrentOriginSTA (sub_2d8f8) passes ppContext==NULL (0x2D924 'movs r0,#0'). And if the STA test returns >= 0, task::_Wait (sub_2d324, which calls _IsCurrentOriginSTA at 0x2D342) THROWS Concurrency::invalid_operation "Illegal to wait on a task in a Windows Runtime STA" (string at 0x1018EE38) whenever a not-yet-complete task is waited on. So the hook must return S_OK + the host context ONLY for the capture (pp != NULL) and E_NOTIMPL for the STA test (pp == NULL): continuations marshal to the render thread, yet task waits stay legal. No deadlock in practice because GD's loading is polled per frame (Draws return) rather than blocking the main thread on `.get()`.
Evidence: device runs showed the loading bar filling 0->~80% then freezing while the game kept rendering (1200+ frames), music looping, input working; ruled out network (isNetworkAvailable not on the loading path). Static RE (arm32re): sub_2ce94/sub_8c628 = _ContextCallback::_Capture (MTA path -> CaptureUiThreadContext(&member), member=0 on failure); sub_2d8f8 = _IsCurrentOriginSTA (MTA path -> CaptureUiThreadContext(NULL), returns true iff hr>=0); sub_2d324 = task::_Wait: `bl _IsCurrentOriginSTA; cbz r0,skip; ldr r3,[r4,#0x54] (status); cmp 3/cmp 4 -> done; else ??0invalid_operation + _CxxThrowException` with the "Illegal to wait..." literal; libcocos2d sub_8c628 is byte-identical to sub_2ce94 and its only CaptureUiThreadContext caller. import scan: libcocos2d also imports CoMarshalInterThreadInterfaceInStream + CoGetApartmentType + CoGetObjectContext (the cross-thread marshaling machinery), corroborating async completion delivery.
Fix (implemented in tools/gd/gd_host.c, pending device confirmation): IAT-patch CaptureUiThreadContext in GeometryJumpComponent.dll + libcocos2d.dll to hook_CUTC { if (pp) { *pp = &g_ui_context; return S_OK; } return E_NOTIMPL; }. g_ui_context is an IContextCallback (QI answers IUnknown/IAgileObject/IContextCallback {000001DA-...}); its ContextCallback(pfn,param,...) runs pfn(param) inline if already on the render thread, else enqueues {pfn,param} to a 64-slot queue, signals, and blocks on a per-slot event until the render thread's disp_drain() (called twice per frame, before PrepareResources and after Draw) executes it and sets the event. The standalone shim PhoneAppModelHost.dll keeps returning E_NOTIMPL (only needed so the loader resolves the import before the IAT patch overrides it). If this does not clear the stall, the shipped build also traces fopen (per asset) and logs ctx-capture/marshal counts to localize the remaining blocker.

UPDATE (2026-10-25, adversarial review of the implementation, 5-agent workflow): the hook_CUTC / IContextCallback / dispatch-queue CODE is ABI-correct and race-free (verified by disassembling the built exe: vtable slot order QI/AddRef/Release/ContextCallback, 6-arg ContextCallback signature matching the PPL _CallInContext call site sub_2cf04, the pp!=NULL vs NULL split, the slot state machine 0/1/2 under the CS, the auto-reset events). BUT two independent lenses (deadlock + logic) concluded with "likely" confidence that this fix is probably a BEHAVIOURAL NO-OP: (1) RTTI "task<E>" is task<unsigned char> == task<void> (the create_async/.then plumbing), NOT an asset-loading task. (2) _Capture (really _ContextCallback::_Resolve(bool captureCurrent)) only calls CaptureUiThreadContext when captureCurrent (r1) != 0, and r1 = the antecedent task's _M_fFromAsync byte [task+0x58], set ONLY for tasks built from a WinRT IAsyncAction/IAsyncOperation. GD's loading tasks are not apartment-aware (that byte is zeroed at sub_31404+0x31414, ctor sub_2d14c+0x2d192; no site in the component stores 1 there). (3) The component's only PPL path is Direct3DInterop::OnSuspending (vtable slot 10 -> IAsyncAction, body just _Oversubscribe true/false), which the host never calls. (4) libcocos2d's only task<void> is the addImageAsync loader (sub_ddb34 <- CCTextureCache::addImageAsync sub_da2e0) which has NO .then continuation; its only .then chain (StorageFile->IRandomAccessStream->IBuffer, root sub_8d304) is DEAD CODE with no BL/vtable/literal callers. (5) GD's real background work is std::thread (component sub_183db0 launches std::thread entry sub_182ffc = a curl/CCHttpClient-style request-queue loop; libcocos2d imports _Thrd_join/_Thrd_detach/_Thrd_current), NOT PPL continuations. So the ~80% stall is most likely a std::thread worker that never runs / never completes on this host, or a main-thread poll waiting on such a worker, or a missing OS/WinRT service -- not a lost PPL continuation. The next device build keeps hook_CUTC (harmless; its counters say if the capture path ever fires) and adds a diagnostic dragnet: [tid] prefix on every log line, GeometryJumpComponent.dll added to the fopen/RoGAF/ODS trace list (it was the key untraced module -- it imports MSVCR110!fopen at IAT 0x18b1e0), fopen cap 600->3000, a counter summary at frame 300/900 (fopen/cutc_cap/cutc_sta/ctx_calls), and a bounded-withdraw safety in ctx_ContextCallback so the fix can't hang if it does fire. One run then settles it: zero cutc_cap/ctx_calls while stalling == PPL theory dead, pivot to the std::thread/addImageAsync path.

## Summary
Plain-language verdict: the native DLLs of Geometry Dash (WP8.0) are NOT blocked by their imports on a Windows RT 8.1 or Windows 10 ARM32 desktop. Every one of the 10 DLLs imports only (a) other DLLs of the same folder (all names and ordinals resolve, F2), (b) the VC++ 2012 runtime, (c) 16 ordinary Windows 8.0 api-set contracts, (d) WS2_32 and d3d11, and (e) exactly two phone-only DLLs. Nothing needs a binary rename.
1. The runtime: the task text assumed '*_app' DLLs; VC++ 2012 has none. The phone binaries import MSVCR110.dll / MSVCP110.dll / vccorlib110.DLL, and the Windows 8 Store package (VCLibs 110, D:\repo\armdeps) and the desktop redistributable (vcredist_arm_vs2012.exe, 11.0.61030) contain files with exactly these names. All 210 + 135 + 53 imported names exist in both builds (0 missing; vccorlib110 is byte-identical in both). So: copy msvcr110.dll, msvcp110.dll, vccorlib110.dll next to the game and change nothing in the game DLLs (F3). No AppContainer patch is needed for them (both builds have DllCharacteristics 0x0140).
2. PhoneAppModelHost.dll (phone only, 3 exports; 2 are used): CaptureUiThreadContext(IContextCallback**) is PPL plumbing (libcocos2d and GeometryJumpComponent call it when a thread is not STA); the shim must return a FAILED HRESULT and set *out = NULL (otherwise PPL thinks the thread is a UI thread). LoadPackagedLibrary is only reached from FMOD's plugin loader (System::loadPlugin), which GD never calls; map it to LoadLibraryExW, not to KERNELBASE (F4).
3. PhoneAudioSes.dll (fmod only, 3 exports): a thin WASAPI activation layer: GetDefaultAudioRenderId/CaptureId(role) -> CoTaskMem'ed device-id string, ActivateAudioInterface(id, riid, void**) -> IAudioClient2/IAudioClient (synchronously). A ~60-line shim over IMMDeviceEnumerator/IMMDevice::Activate (mmdevapi) replaces it; the fmod WASAPI output module then runs unchanged (F5).
4. API sets: all 16 contracts are Windows 8.0 contracts; 14 are proven natively on a real RT 8.1 (loadcheck 6.3.9600); the other two (libraryloader-l1-1-1, debug-l1-1-1) are very likely present by inference (the Windows 8.1 VCLibs120 framework package imports them, F6). Do not reuse the 0.10.4 shim files for these (they lack functions); generate or extend if loadcheck ever says missing (F6). ws2_32 (30 ordinals + 3 names), d3d11 and the OpenSSL/libcurl stack need nothing (F7, F8).
5. Small items: only the two fmod DLLs carry the AppContainer bit (one byte at file offset 0x15F, F9); libwebsockets.dll and fmodex_80L_arm.dll are referenced by nothing and can be left out (F2); a list of WinRT classes that the binaries name at run time (DisplayProperties, ApplicationData/Storage, Launcher, Accelerometer, InputPane, CoreWindow ...) is for the host design (F10).
Recommended next step: (1) write the two shim DLLs (PhoneAppModelHost.dll ~20 lines of C, PhoneAudioSes.dll ~60 lines), (2) assemble the folder (10 package DLLs minus the two unused + VC110 trio + shims), (3) extend tools\loadcheck module list and run it once on the Surface RT (8.1) and the Surface 2 (Win10); expected '0 problem(s)', (4) go on with the host bring-up of games_recon/geometry_dash_gd-component.md. The import side is therefore low-risk; the open risks are elsewhere (host-side DrawingSurface emulation, FL9_1 vs the 9_3 request, WinRT fakes).
