### F2. How the host picks the game today (SizeOfImage key) and what Redcon needs: a patched SizeOfImage of 0x001E1000, a game id instead of the boolean host_is_0104, and 6 touch points in win32_host.c  [severity: major, confidence: high]
Claim: (a) Detection is two-stage and purely header based: `Win32Bootstrap` (win32_host.c line 23101) sets `host_is_0104 = x104_image_matches(image)` (line 23114) BEFORE the log is opened; `x104_image_matches` (win32_host_arm32_0104_boot.inl lines 40-49) returns TRUE iff PE machine == 0x01C4, optional-header magic == 0x010B and SizeOfImage == `X104_IMAGE_SIZE_PATCHED` 0x00E6F000 (the stock 0x00E6E000 is deliberately rejected: "this exe was not patched"). If it matches, `return x104_bootstrap(image)` (line 23127); otherwise the 1.2.8 path runs `arm32_boot_identify_image`, which demands SizeOfImage 0x01731000 (`IMAGE_SIZE_128_ARM_PATCHED`, win32_host.c line 183). (b) The key is NOT a hash and not the entry point or timestamp; it is "the number the patcher writes", asserted by the patcher profile (`new_section.expect_size_of_image`, tools/arm32-patcher.py line 717). (c) For Redcon the same mechanism works unchanged: the patcher's own layout algorithm (`add_import_section`, lines 1164-1262) run read-only on Redcon.exe predicts the patched value (see F3): SizeOfImage 0x1E0000 -> 0x001E1000, which collides with neither 0x00E6F000 nor 0x01731000. Recommended hardening (cheap, header fields only): key = (machine 0x1C4, SizeOfImage 0x001E1000, AddressOfEntryPoint 0x0013A445, TimeDateStamp 0x57556C8F) in a small table {patched_size, entry, timestamp, game_id}. A hash of the exe at every start is possible but unnecessary (the patcher already pins the SHA-256 of the stock exe). (d) win32_host.c has exactly SIX places that know about the 0.10.4 host (grep `host_is_0104|x104_` in win32_host.c): line 237 the flag; lines 345-346 forward declarations of `x104_inputpane_raise` and `x104_activation_hook`; line 9448 `arm32_input_pane_raise` (TabTip controller callback -> input unit); line 9565 `win32_get_activation_factory` safety net (never hand out the 1.2.8 fakes); line 22823 banner text ("Minecraft PE 0.10.4.40"); lines 23098-23127 the `#include "win32_host_arm32_0104.inl"` + detection + dispatch. A second WP8.1 game therefore needs a flag generalisation, not a second set of hooks: keep `host_is_0104` meaning "the x104 host family is active" (rename `host_is_wp81`) and let a profile pointer (`x104.profile`) carry the game; all 6 places then work for both games.
Evidence: win32_host.c lines 183, 237, 345-346, 9448-9449, 9565, 22823, 23098-23127 (read); boot.inl lines 32-49 (`X104_IMAGE_SIZE_PATCHED 0x00E6F000u`, `x104_image_matches`); patcher lines 717, 1164-1262; `python -B predict_redcon.py` (my read-only run of the patcher's PE parser and layout code against Redcon.exe): `PREDICTED new section: rva 0x1E0000 raw 0x1DA000 vsize 0x1EC rsize 0x200 SizeOfImage 0x1E1000 IAT cell 0x1E01E4`; TimeDateStamp 0x57556C8F and entry 0x13A445 from pehdr.py.
Proposed fix: core gets `typedef struct X104Profile { const char *name; DWORD patched_size_of_image, entry_rva, timestamp; ... }` and `static const X104Profile *x104_profile_for_image(BYTE *image)` (replaces `x104_image_matches`); `Win32Bootstrap` stores the result; banner, window title and class name read the profile. UNVERIFIED: 0x1E1000 is a prediction - the first real `arm32-patcher.py patch --profile redcon` run confirms it (the engine raises PatchError if the profile's expect_size_of_image differs, so a wrong constant cannot slip through).

### F4. IAT hooks: the mechanism is generic (name based), but 3 call paths use raw 0.10.4 RVAs and would write into the wrong memory on Redcon unless they are switched to names or a per-profile list  [severity: major, confidence: high]
Claim: (a) `arm32_iat_hook_import(image, delay, name, fact_rva, hook, &orig, what)` (win32_host.c lines 3413-3447) calls `arm32_iat_resolve_cell` (lines 3385-3401), which finds the cell BY NAME in the live import directory and uses `fact_rva` only as a fallback when the name is missing (a disagreement is logged as WARNING, the live cell wins). So the hook list is portable: the activation router (`?GetActivationFactoryByPCWSTR@@YAJPAXAAVGuid@Platform@@PAPAX@Z`), `D3D11CreateDevice`, `?terminate@@YAXXZ`, `_purecall`, `_exit_app`, `_exit`, `?__abi_WinRTraiseCOMException@@YAXJ@Z` and the 14 typed `?__abi_WinRTraise<X>Exception@@YAXXZ` raisers all exist in Redcon's import table at other RVAs (activation 0x142318, D3D11CreateDevice 0x1420D0, _exit 0x1421A0, terminate 0x1421F4, _purecall 0x1422BC, _exit_app 0x1422F0, _CxxThrowException 0x1422F4, raisers 0x142314 and 0x142364-0x142398). (b) THREE paths are NOT safely name based and use the 0.10.4 constants: (1) `install_exception_trace(image, X104_RVA_IAT_CXXTHROW)` and (2) `install_d3d_compile_trace(image, X104_RVA_IAT_D3DCOMPILE)` (win32_host.c lines 12353-12367 and 12443-12457) do `slot = image + rva; VirtualProtect(slot, ...); *slot = hook` with NO check that the old value is what is expected - on Redcon `image + 0x20B5D4` and `image + 0x20B000` lie beyond the patched SizeOfImage 0x1E1000, i.e. in whatever else is mapped there (ASLR: another DLL or heap) - a silent corruption or an access violation; Redcon has NO D3DCompile import at all (`arm32re impcallers D3DCompile` = none, lead redcon-render F3). (3) In `x104_install_diagnostic_hooks` (boot.inl lines 253-274) every cell is hooked by name BUT with the 0.10.4 `fact_rva`; for a name that is missing in Redcon (`abort` is not imported by Redcon.exe; it imports `_amsg_exit` instead, `arm32re imports` output) `arm32_iat_resolve_cell` falls back to `image + 0x20B530`, and `arm32_iat_hook_import` then calls `arm32_patch_cell(cell, original = *cell, ...)` with expected == the cell's own content, so the "expected value" check cannot protect a wrong cell: the hook list must be a per-profile table of names (rva = 0 / skip when absent), or the fallback must be refused when `fact_rva >= SizeOfImage`. (c) The raw-RVA constants appear in these places of the units: core.inl lines 84-97 (14 IAT RVAs), boot.inl lines 233-246 and 266-270 (`X104_RAISE_HOOK(ObjectDisposed, "ObjectDisposed", 0x20B684)` ... 14 literals), panel.inl line 2670 (`X104_RVA_IAT_D3D11CREATEDEVICE`, by name + fact, safe), platform: none for IAT.
Evidence: win32_host.c 3342-3447 and 12353-12367, 12443-12457 (read); boot.inl 233-290; `arm32re imports` on Redcon.exe (output lines quoted above: no `abort`, no D3DCompile; `_amsg_exit` present); `arm32re impcallers D3D11CreateDevice` -> IAT 001420d0 thunk 00139c5c, sole caller sub_6df6c at 0x6dfee.
Proposed fix: one profile table `x104_iat_hooks[]` = { name, fallback_rva (0 = no fallback), kind } per game; `x104_install_iat_hooks` iterates it; for the two raw-RVA installers add a name based variant (`arm32_iat_find_cell(image, FALSE, "_CxxThrowException")`), skip D3DCompile when the profile says the game has none. Cost: about 60 changed lines, no behaviour change for MCPE when the table repeats today's names/RVAs (provable by the existing log lines `ARM32 hook ...: cell rva ... currently ...` being identical).

## Summary

Plain-language verdict (area: reuse of the Minecraft PE 0.10.4 host for REDCON 1 and the plan):

1. Same toolchain, same boot, different game shape. Redcon.exe and MCPE.Host.WindowsPhone.exe are both ARM32 C++/CX programs built with the VS2013 compiler (linker 12.0), both use the same C runtime start-up, and the WinMain thunk is byte-for-byte the same 12 bytes in both (Redcon 0x13A91C, MCPE 0x203EFC). Both follow "Application::Start -> ApplicationInitializationCallback -> App constructor -> IApplicationFactory.CreateInstance -> OnLaunched". But Redcon is NOT the "DirectX App (XAML)" pattern of Minecraft: it has no MainPage, no XAML files (no .xbf), no AppMain/DeviceResources classes, no DispatcherTimer, no thread-pool render loop. Its OnLaunched builds one SwapChainPanel in code, creates the Direct3D device and the swap chain synchronously, registers 17 events (the lead's count; I verified the 11 CoreWindow adders), and draws every frame on the UI thread inside CompositionTarget.Rendering. (I checked this myself in the disassembly of OnLaunched sub_6EBD0 up to Window.get_CoreWindow, and in the SetWindow block sub_6CF3C for the 11 CoreWindow adder slots; the rest of that flow is from the lead file.) So Redcon is a third host shape; roughly half of the 0.10.4 host's logic (everything about MainPage, AppMain, the ready flag, the timer gate, the hidden text box) does not apply, and the other half (Application/Window/CoreWindow/DisplayInformation/Package fakes, the dxgi swap-chain interception, the Present stub, the window and input plumbing, the activation router) applies as it is.

2. What is Minecraft-specific in the 0.10.4 host (F5, F13): about 55 live hard-coded constants (IAT cells, RVAs of AppPlatform/SoundSystemRT cells, the shader profile string and resolution float, the WinMain wrapper and call-site addresses, MainPage/AppMain/client object offsets, the SizeOfImage key, 14 exception-raiser IAT cells) plus roughly 15-25 percent of the code (MainPage/Page/Canvas fakes, the ready/timer/first-SizeChanged ordering rules, the hidden TextBox and InputPane model, the shader profile and "report 9_3" feature-level lie, the --trace-game-state debugging blocks). The toolkit (object/view/class model, checked vtable slots, events, HSTRING, guarded calls, activation router), the UI loop, the window procedure routing, the pointer/touch/key/TabTip code, the Present accounting and path B are generic.

3. Three places are dangerous if the host is simply pointed at Redcon (F4, F13): two IAT hook installers (`install_exception_trace`, `install_d3d_compile_trace`) write to raw 0.10.4 RVAs beyond Redcon's image, a by-name hook with a missing name (`abort`) falls back to a 0.10.4 RVA, and the shader-profile install step fails the boot (code 33). These must be profile-driven before any Redcon run. With the current SizeOfImage key the unmodified host refuses Redcon cleanly (it falls into the 1.2.8 path and stops at identification), so nothing is hooked by accident.

4. How to add Redcon (F2, F3, F7, F9): (a) patcher: a data-only `PROFILE_REDCON` (no engine change). Stock side measured: SHA-256 3aca1266..., SizeOfImage 0x1E0000, entry 0x13A445, call site 0x13A55A (`bl 0x13A91C`), trampoline slot 0x1414B0 (0x150 zero bytes, no reloc/pdata overlap), DllCharacteristics at file 0x15E, no byte patches, same three VC120 Phone DLLs. Output side predicted by running the patcher's own layout code read-only: new section at 0x1E0000, SizeOfImage 0x001E1000, call-site bytes 06f0a9ff, trampoline literal 0x9ED2C - the first real patch run confirms them (the engine asserts them). (b) host detection: the same SizeOfImage mechanism (0x001E1000), hardened with entry RVA and TimeDateStamp, in a small profile table; win32_host.c has only six touch points that name the 0.10.4 host, and all become profile-driven by turning the boolean into a profile pointer. (c) seven per-game tables (identity/take-over, IAT hook list, activation owner table, feature bits, platform cell table, panel install record, game-state callbacks) and ONE new unit file win32_host_arm32_0104_redcon.inl for the genuinely new classes: ApplicationView, SwapChainPanel factory, CompositionTarget (+ a Rendering tick in x104_ui_pass), CoreApplication Suspending/Resuming, CoreWindowResizeManager, five CoreWindow adders + CharacterReceived, IDisplayInformation2, ApplicationLanguages, a network stub; later Launcher, PropertyValue, a real settings map and the dialog widgets (or a dialog patch). All slot numbers were re-derived from the SDK headers and agree with the earlier lead file. One DLL, one detection point, no fork.

5. Effort versus the 0.10.4 port (F9): the 0.10.4 port was about 20,000 lines in total (12,180 host + 1,588 generated + 4,580 PC tests + 1,875 tooling), designed and integrated in about 18 hours of workflow wall-clock plus several days of device debugging. Redcon needs about 3-3.5k lines (0.9k S-phase classes, 0.6-1.2k lazy classes, 0.4-0.6k gating changes, 0.7k PC mock test, 0.3k tooling) = about 15-20 percent of the volume and, my estimate, about a quarter of the effort, because the hard 0.10.4 problems (AppMain lock, ready flag, init job racing SizeChanged, text box model, HLSL profile lie) do not exist in Redcon. The risk that remains is device-only: audio/Media Foundation/Direct2D/DirectWrite start-up on RT 8.1 and Win10 15035, how long OnLaunched blocks, the real HWND flip chain with ResizeBuffers/SetRotation/DiscardView, the settings map, the dialogs.

6. Recommended next step: do step 0 and step 1 of F9 first - they are mechanical and fully checkable on the PC: (0) introduce the profile record and the guards with only the MCPE profile and prove 0.10.4 unchanged (x86 identity, the 149-check mock + 43-check selftest, the patcher hash cb44c09a..., and a normalised old-vs-new diff of the mock's host log); (1) extend the interface list of gen_0104_iids.py (20 interfaces, all in the SDK) and add PROFILE_REDCON, run the patcher once to confirm the predicted constants. Then write the redcon unit, a Redcon mock test that replays the OnLaunched call order, and go to the Surface 2. In parallel, as a 1-2 day side experiment for the Surface 2 only, the appx re-package route (WP81_APP_METHOD) looks unusually cheap for Redcon (no XBF, no PhoneAppModelHost import, three phone-only classes to neutralise) but it cannot serve Windows RT 8.1, which the fake-host route does.
