### F2. What FL 9_1 demands from every shader (Microsoft docs)  [severity: info, confidence: high]
Claim: On a FL 9_1 device CreateVertexShader/CreatePixelShader accept ONLY vs_4_0_level_9_1 / ps_4_0_level_9_1 bytecode; plain vs_4_0/ps_4_0 (what Unity ships, F3) is rejected. Limits that matter for Unity shaders: PS = ps_2_0-class (64 arithmetic + 32 texture instructions, 12 temps, 4 dependent-read levels, no flow control, no gradient instructions i.e. no ddx/ddy, no tex2Dlod - fxc 10.0.19041 for ps_4_0_level_9_1: SampleLevel -> "error X4532: texlod not supported on this target", ddx -> "error X4532: cannot map expression to pixel shader instruction set"; the same ddx shader compiles for ps_4_0_level_9_3); PS may use at most 32 constant registers in total (only the cbuffer ranges actually read count - verified with fxc below); VS = vs_2_0-class (256 instructions, 12 temps, static flow control depth 1, at most 255 constants); no vertex texture fetch (VSSetShaderResources/VSSetSamplers not supported on 9.x); max 8 shader resources and 16 samplers bound to PS; 1 render target (no MRT -> no deferred); no comparison samplers (no hardware shadow maps); no instancing (no SV_InstanceID / per-instance input); no geometry/hull/domain shaders.
Evidence: https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-device (CreateVertexShader "Must use vs_4_0_level_9_1", CreatePixelShader "Must use ps_4_0_level_9_1", CreateSamplerState "Comparison filter is not supported", CreateInputLayout "Does not support D3D11_INPUT_PER_INSTANCE_DATA"); https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-context (PSSetConstantBuffers "total number of constants used by shader cannot exceed 32", VSSetConstantBuffers "...cannot exceed 255", PSSetShaderResources "No more than 8", PSSetSamplers "No more than 16", VSSetShaderResources/VSSetSamplers "Not supported on any 9.* feature level", OMSetRenderTargets "Only one render target supported"); https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/specifying-compiler-targets (ps_4_0_level_9_1: "64 arithmetic and 32 texture instructions, 12 temporary registers, 4 levels of dependent reads"; vs_4_0_level_9_1: "256 instructions, 12 temporary registers, Static flow control (max depth of 1)"; GRADIENTINSTRUCTIONS listed only for 9_3); https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-devices-downlevel-intro (9_1: shader model "2.0 (4_0_level_9_1)", 1 simultaneous render target, max texture 2048, no instancing).
fxc check (scratchpad fxtest/t1.hlsl, fxc 10.0.19041 -T vs_4_0_level_9_1): a VS with 4 cbuffers of 3/11/23/2 registers maps only the read ranges to D3D9 constants ("c1 cb0 start 2 x1; c2 cb1 start 0 x4; c6 cb2 start 17 x4; c10 cb3 start 0 x2", plus runtime c0 "Vertex Shader position offset"), so Unity's big shared cbuffers (UnityPerFrame 368 bytes etc.) are NOT a problem as long as only a few members are read.
Proposed fix: replacement shaders must be compiled with -T vs_4_0_level_9_1 / ps_4_0_level_9_1 and must avoid the features above.

### F8. Cleanest replacement mechanism: swap bytecode by DXBC checksum inside the host's D3D11 device hooks (not asset rewriting)  [severity: major, confidence: medium]
Claim: Recommended: in win32craft.dll, after creating the real FL 9_1 device (the feature-level spoof itself belongs to bp-render), patch the ID3D11Device vtable slots CreateInputLayout (#11), CreateVertexShader (#12) and CreatePixelShader (#15) (order verified in Windows Kits 10.0.19041 um/d3d11.h ID3D11DeviceVtbl). ## Summary

Plain language: the game's shaders CAN run on the GPU at Direct3D feature level 9_1 - no software (WARP) rendering is needed for the shader side.

- What is wrong today: Unity ships every shader only as Direct3D 10/11-class bytecode (SM 4.0/5.0). A FL 9_1 GPU refuses that bytecode. 82 shaders = 402 different programs, none in the needed "level_9_1" form (F1, F3). UnityPlayer.dll also carries its own small blit shaders (F7).
- How much the game really needs: about 112 programs (38 vertex + 74 pixel) from 57 reachable shaders, plus 2 internal blit programs. The game has no lights, no skinned meshes, orthographic cameras, HDR off, so shadow, deferred, instancing and similar programs (the ones that truly cannot work on 9_1) are never used (F4, F7).
- Do they fit 9_1: yes. 107 convert automatically (my converter turns Unity's bytecode back into HLSL with the exact same bindings; each result was proven to compute the same as Unity's original and compiles for level_9_1, biggest pixel shader 49 of 64 ALU slots) (F5). 4 lit pixel programs were too big for ps_2_0 and now have hand-trimmed versions that keep Unity's bindings and give identical output under the game's conditions (F9). 1 optional program (IMGUI rounded rectangles, needs ddx) is left. 0 needed programs are impossible.
- Prototype: readable level_9_1 HLSL for Sprites/Default, Unlit/Transparent (+ the _Custom color variant shared by 10 shaders), UI/Default (= TextMeshPro/Sprite), the trimmed lit shader, and an auto-converted TextMeshPro distance-field shader; 22 checks all OK: compile, same signatures, same cbuffer slots/offsets, same texture slots, same behaviour (F6, F9).
- Best way to plug them in: in win32craft.dll, hook CreateVertexShader / CreatePixelShader / CreateInputLayout on the real FL 9_1 device and swap Unity's bytecode for the level-9 one, looked up by the DXBC checksum. The lookup file is already built (auto/l9_replacements.bin, 113 entries, 295 KB). Asset-file rewriting is a worse plan B (big files, unknown prefix, cannot reach the DLL's blit shaders) (F8).
- Not verified: which graphics tier Unity picks (table covers both), anything on real hardware (nothing has run on the Surface yet), Tegra pixel precision.
- Outside this area but required for GPU rendering (bp-render): make Unity accept the FL 9_1 device (it demands FL 10.0), and keep it away from other non-9_1 features (32-bit index buffers, half-float vertex formats, NPOT+mips/wrap textures, MSAA, comparison samplers, sampler MaxLOD/MinLOD rules, DepthClipEnable).

Next step: implement the 3-slot device hook + table loader in the host (log every checksum miss), combine it with the bp-render feature-level work, and run on the Surface 2.
