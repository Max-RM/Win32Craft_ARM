## Findings

### F1. The planned CreateInputLayout hook would kill EVERY input layout: Unity passes a signature-only DXBC whose checksum is never in the table  [severity: blocker (as designed), confidence: high]
Claim: design F5 says CreateInputLayout (slot 11) swaps bytecode by checksum and "log and return E_FAIL on a miss". But Unity never passes a shader to CreateInputLayout. The only call (sub_100f468, `ldr r4,[r4,#0x2c]; blx r4` @0x0100f4e2/0x0100f4ec) passes the object returned by sub_100fa88 (called from the VS creator sub_100378c @0x0100380e, result kept at [prog+0x14]). sub_100fa88 looks up chunk 'ISGN' (literal 0x4e475349 @0x0100fb34) or 'ISG1' (0x31475349 @0x0100fb30) with sub_fff0f8, then sub_fff01c builds a NEW container: 'DXBC' (0x43425844 @0x00fff0f4), version 1, chunk count = 1, the one chunk copied, and a fresh checksum computed by sub_ffc8b8 over bytes 0x14.. into +4 (@0x00fff0e0..0x00fff0ea). Its checksum (bytes 4..19) is therefore different from every full-program checksum in l9_replacements.bin, so the hook as specified misses on 100 % of calls and Unity gets no input layout at all (nothing is drawn). The design's PC bench never exercised this because it fed the level-9 VS itself to CreateInputLayout (l9bench.c line 111/325).
Measured on this PC (critic\crit_il.c, x64, debug layer, FL {9_1} only, Intel HW and WARP give identical results): a signature-only blob made from Unity's Sprites/Default VS (D3DGetInputSignatureBlob = the same 1-chunk ISGN container Unity builds) -> "checksum in table: no"; CreateInputLayout(signature-only blob) hr=0x00000000; CreateInputLayout(original Unity vs_4_0 bytecode) hr=0x00000000; CreateInputLayout(level-9 VS) hr=0x00000000; same blob with a zeroed checksum -> 0x80070057 "Input Signature in bytecode could not be parsed" (so the runtime validates the checksum, and Unity's own sub_ffc8b8 checksum must be right - it is, since the same path works on FL 10+). A DrawIndexed with the layout from the signature-only blob + level-9 Sprites/Default VS/PS reads back 200 100 50 255 (expected 200 100 50 255) on both HW and WARP.
Evidence: `arm32re.py func 100f468`, `func 100378c`, `func 100fa88`, `func fff01c`; output in scratchpad critic\il_hw.txt and critic\il_warp.txt.
Proposed fix: do NOT hook CreateInputLayout (or hook it only to log and always pass through unchanged). At 9_1 the runtime accepts Unity's signature-only blob as is. Keep checksum swapping only for CreateVertexShader/CreatePixelShader. Add to the M2 harness: replay Unity's exact sub_fff01c container (byte-identical, including Unity's checksum routine) instead of D3DGetInputSignatureBlob, and a test that every needed VS's ISGN matches the replacement's ISGN (hw-shaders F6 says identical; keep it as a gate, because the layout is now validated only against Unity's original signature, not against the level-9 VS).

### F2. The "private vtable copy" must copy the WHOLE runtime vtable (174 slots on this PC), not the ID3D11Device2 interface (54) - a short copy crashes inside DXGI at swap-chain creation  [severity: major, confidence: high (PC), medium (ARM builds)]
Claim: design F4/F5 hooks device methods by giving the device object a private copy of its vtable, sized implicitly by the interfaces Unity uses (Device/Device1/Device2 = 54 slots). Measured on this PC at FL 9_1 (critic\crit_vt.c, no debug layer, SINGLETHREADED like Unity, Intel HW and WARP identical): ID3D11Device, Device1, Device2, Device3, Device4 and Device5 are ALL the same object with the same vtable; 174 consecutive vtable entries point into d3d11.dll (public interfaces end at 69, so the runtime keeps internal methods in the same table); DXGI calls QueryInterface 16 times through the object during CreateSwapChainForHwnd. With a FULL copy (174 slots) everything works: QI IDXGIDevice, CreateSwapChainForHwnd with Unity's desc (usage 0x30, FLIP_SEQUENTIAL, flags 0x40) S_OK, CreateRenderTargetView on the back buffer (hook fired), 30 Present S_OK, ResizeBuffers S_OK, GetDeviceRemovedReason S_OK. With a 54-slot copy (rest NULL) the process dies with 0xC0000005 right after "QI IDXGIDevice", i.e. inside CreateSwapChainForHwnd: DXGI/the runtime call slots beyond ID3D11Device2 through the swapped pointer. Also: ID3D11Device3::CreateTexture2D1 through the full copy succeeds but does NOT pass through the slot-5 CreateTexture2D hook (hook count 0) - any caller using the Device3+ creation methods bypasses the sanitizers (Unity does not QI Device3, so this is only a note).
Evidence: scratchpad critic\vt_hw.txt, vt_warp.txt (full copy: "device vtable: 174 consecutive entries point into d3d11.dll", "calls made by DXGI into the hooked slots during swap-chain creation: QI 16", "30 x Present hr=0x00000000"); critic\vt_hw_short.txt (54-slot copy: exit code -1073741819 after "QI IDXGIDevice through swapped vtable hr=0x00000000").
Proposed fix: in the shim, measure the vtable length at run time (count consecutive entries that point into the d3d11.dll image, cap e.g. 512) and copy all of it; never size it from the SDK header. Log the count on device (15035 and RT 8.1 d3d11.dll will differ from 174). Keep the copy alive for the device lifetime and restore the original pointer before the final Release. Add this exact test (full vs short copy, swap chain + Present + ResizeBuffers) to the M2 harness and run the ARM32 build of it in the M0 probe on both tablets.

### F3. The Unity splash screen is ON in this build, so Hidden/Internal-GUITexture + Hidden/BlitCopy (and their separate-alpha blend states) are drawn on EVERY start - not "IMGUI only"  [severity: major (first-frame critical path), confidence: high]
Claim: hw-content F14/F15 and hw-shaders F4 classify the Internal-GUI* shaders (and their illegal-at-9_1 separate alpha blend factors) as "only drawn by OnGUI (CheatsUtility, ProgressResetButton)", and the design treats IMGUI as optional. But PlayerSettings in Data/globalgamemanagers has m_ShowUnitySplashScreen = 1 and m_ShowUnitySplashLogo = 1 (bytes at file offsets 0x1074 / 0x1075; layout anchored by productName "Bad Piggies::Rebooted" at 0x1038 and by defaultScreenWidth = 800 landing exactly at 0x10ec as hw-content F8 found), background colour (0.137, 0.122, 0.125, 1) = Unity's dark default, 0 custom logos, no background images. The player's splash code uses exactly these shaders: sub_5768b8 references both "UnitySplash-cube.png" (0x01b72c9c, @0x00576950) and "Hidden/Internal-GUITexture" (0x01b72ab4, @0x005769aa); sub_579ce8 references "Hidden/BlitCopy" (0x01b72d7c, @0x00579d22); profiler markers "SplashScreenBegin/Fade/End/Render" (0x01b72cb4..0x01b72d68). So the first frames the user sees go through Internal-GUITexture's programs (in l9_replacements.bin, mechanical) and its blend states with separate alpha factors (hw-content F14 lists Internal-GUITexture among the 5 separate-alpha passes), plus the UnitySplash-cube texture (2048x1024 DXT5 12 mips, POT - legal).
Evidence: scratch script critic\ps_splash.py output "m_ShowUnitySplashScreen 1 m_ShowUnitySplashLogo 1 overlay 1.0 anim 1 logoStyle 1 drawMode 0 ... logos count 0"; `arm32re.py strx "Hidden/Internal-GUITexture"`, `strx UnitySplash-cube.png`, `strx Hidden/BlitCopy`, `strx SplashScreenRender`.
Proposed fix: (1) treat Internal-GUITexture and BlitCopy as startup-critical in M2: pixel-compare them through the shim, including the collapsed alpha blend (colour result must match; the back-buffer alpha is unused); (2) M3 "done" must include "splash logo visible" as the first visual checkpoint; (3) optional bring-up knob: set the byte at globalgamemanagers 0x1074 to 0 to skip the splash (content edit; the appx is re-signed anyway) if it ever blocks the first menu.

### F4. The device policy "first try Unity's FL10+ call unchanged, return at once on success" can silently pick a SOFTWARE adapter and never reach 9_1  [severity: major, confidence: medium (depends on what the Surface 2 adapter is)]
Claim: design F5 policy: call the real D3D11CreateDevice with Unity's arguments; "On success (any FL 10+ GPU, the Adreno phone, Basic Render) it returns at once: no hooks"; warp=deny only refuses DriverType=5. But Unity's first call is not a "GPU" call: sub_ffdc74 passes pAdapter = IDXGIFactory::EnumAdapters(index) with DriverType UNKNOWN (bp-render F1: `movs r5,#0` @0xffdd50/0xffddc8). Every Surface 2 log shows the device behind the default adapter as "Software Adapter" VendorId=0000 DeviceId=0000 DedicatedVideoMemory=0 MiB (13 log lines, all identical; the phone shows "POCO X3 Pro Adreno 640 GPU"). If that adapter is a software rasterizer it may well accept FL 10_0..11_1 (WARP does). Then Unity's unchanged call SUCCEEDS at FL 10+, the shim steps aside, Unity renders on the CPU, and the log says nothing about it - exactly the outcome the user does not want, and the M3 check "L9 mode in the log" would just never appear without explaining why. "Basic Render" is even listed in the design as a success case.
Evidence: design F5 "Policy" paragraph; arm32/device_logs/surface2_win10_0104_1346dll_backbutton.log line 243 and `grep -h 'adapter "' arm32/device_logs/*.log` (Software Adapter x13, Adreno x4); bp-render F1 (driver type UNKNOWN with an enumerated adapter).
Proposed fix: classify the adapter before deciding, not the driver type: IDXGIAdapter1::GetDesc1 -> Flags & DXGI_ADAPTER_FLAG_SOFTWARE, VendorId 0x1414 (Microsoft Basic Render), or the created device's driver = WARP/REFERENCE (and log module d3d10warp.dll if loaded). Policy: l9=auto -> if the FL10+ device is on a software adapter and a hardware adapter offers 9_x, use the hardware 9_x device; log "SOFTWARE adapter, FL x" loudly in every case; warp=deny must also refuse software adapters. Add to the M0 probe: Unity's exact first call (EnumAdapters(0), UNKNOWN, [11_1,11_0,10_1,10_0], flags 0x21) on both tablets - its hr tells what the stock game does today and whether the policy would even reach the 9_x branch.

### F5. Any CreateTexture2D rewrite must be mirrored in the view descs: Unity creates every texture SRV with an explicit desc copied from its own texture desc  [severity: minor (for this game's data), confidence: high]
Claim: design F5 lets CreateTexture2D change MipLevels (A8_UNORM forced to 1) and formats, and the view hooks "rewrite the view formats to match". In the 2D texture creator sub_10125a8 Unity fills the texture desc at r7+0x60 (Width r6, Height r5, MipLevels sl, ArraySize 1, Format [r7+0x70], Usage DEFAULT, BindFlags 8, MiscFlags = 2 = D3D11_RESOURCE_MISC_SHARED when a creation flag & 8 is set, @0x010126aa..0x010126d8, CreateTexture2D @0x0101270a) and then the SRV desc at r7+0xb8 with Format = the same [r7+0x70], ViewDimension 4 (TEXTURE2D), MostDetailedMip 0, MipLevels = sl again (@0x010127f0..0x01012808, CreateShaderResourceView slot 7 @0x01012814). So if the shim gives the texture 1 mip while Unity asks the SRV for 8, the SRV fails (E_INVALIDARG -> Unity logs "d3d11: failed to create 2D texture shader resource view" 0x026724e8) and the texture is unusable. Same for any format remap the view hook does not mirror. The SHARED misc flag is a second 9_x trap: the 10Level9 CreateTexture2D notes say "When using D3D10_DDI_RESOURCE_MISC_SHARED, Format cannot be DXGI_FORMAT_R8G8B8A8_UNORM or DXGI_FORMAT_R8G8B8A8_UNORM_SRGB" (which caller sets flag 8 is unverified; probably external/native textures only).
Evidence: `arm32re.py func 10125a8` (lines quoted); https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-device (CreateTexture2D bullet list; CreateShaderResourceView "MostDetailedMip plus MipLevels must include lowest LOD").
Proposed fix: implement the view hooks generically: on CreateShaderResourceView/RenderTargetView/DepthStencilView, read the real resource desc (ID3D11Texture2D::GetDesc), clamp MipLevels to the real count (or -1), map the view format to the real (possibly remapped) resource format, and keep a small map texture->original desc for logging. In the CreateTexture2D hook, drop MISC_SHARED for R8G8B8A8 at 9_x and log it. The game's own data has no mipped A8 texture (hw-content F3), so this is insurance, but it is cheap and belongs in M1.

### F6. Caps fix-up: the shader-requirement filter is now traced (design F3 holds, plus a tier match), but three details of the fix-up are wrong or missing  [severity: minor, confidence: high]
Claim: (a) CONFIRMED - design F3's untraced filter exists: sub_742580 (SerializedShader.cpp code, caller sub_741fe8) skips a sub-program unless its tier matches and its requirements are a subset of the caps mask: `ldr r4,[r0,#0xc0]` / `cmp r5,r4` (sub-program tier [r6] < 3 must equal caps+0xc0, @0x007425aa..0x007425b6) and `ldr r3,[r0,#0xbc]; ands r3,r2; cmp r3,r2; bne skip` (@0x007425da..0x007425e4). So 0xE3 is required (0x1 would drop all 0x21/0xE3 programs) and the table must keep both tier variants (it does). Same function bounds texture parameters by caps+0xd4 (=0x40, "Shader '%s' uses %d texture parameters, more than the %d sup..." 0x11d5d730 @0x00742bbe) and UAVs by caps+0xf0.
(b) RT 8.1 / host route: the design writes CopyTextureSupport +0x3e4 = 0 from the CheckFeatureSupport hook, but Unity stores `movs r3,#0x1f; str.w r3,[r6,#0x3e4]` at 0x01007a0a/0x01007a0c AFTER the OPTIONS1 call (blx 0x010079e2). Only the OPTIONS3 call (0x01007a3e) comes later, and it is made only when sub_2b2104() >= 0x3e8 (`cmp.w r0,#0x3e8` @0x01007a26, i.e. Windows 10). On RT 8.1 the value would silently stay 0x1f. Harmless for this game (no CopyTexture), but the "fix-up is complete" claim is false on RT 8.1.
(c) +0x101 OutputMergerLogicOp is set from D3D11_OPTIONS (@0x01007838) and, when set, GfxDeviceD3D11::vf11 creates blend states with logic ops through CreateBlendState1 (Device1 +0xb4 @0x01003b1a, guarded by blend op 5..0x14 and caps+0x101 @0x01003a9e). Microsoft lists CreateBlendState1 as "Unsupported" at 9_1/9_2/9_3, yet the design's bench (design\bench_warp.txt) shows WARP at FL 9_1 reporting OutputMergerLogicOp=1. Not reached by this game's content (BlendOp always Add, hw-content F14), but the fix-up should force +0x101 = 0 (it is written before the hook point, so it can).
(d) With option (i) (GetFeatureLevel returns 0xA000 to sub_1007434) the renderer string "Direct3D 11.0 [level %i.%i]" (0x12667394) is built from that same value (`and r3,r2,r4,asr #8` / `asr #12` @0x010075ce/0x010075d4) and will read "level 10.0" in Unity's log and SystemInfo.graphicsDeviceVersion - the shim's own log must state the true level, or a tester will think FL 10 worked.
Evidence: `arm32re.py func 742580` (saved tool output), `func 1007434` (critic\f1007434.txt lines 330-557), `func 1003c46` (critic\fn_vf11.txt lines 100-160); https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-device (CreateBlendState1: "Unsupported" for 9_1, 9_2, 9_3).
Proposed fix: in the fix-up value list add +0x101 = 0 and (optional) +0xd4 = 8 (9_1 PS limit "No more than 8 simultaneously bound shader resources"); on RT 8.1 accept CopyTextureSupport 0x1f or use option (ii) (in-memory caps row) plus a hook on a call that runs after 0x01007a0c (none exists in sub_1007434 on 8.1 - a later device call such as the first CreateBuffer from the GfxDeviceD3D11 constructor sub_1001154 could carry a one-shot "late fix-up"). Log "true FL 9_1, Unity told 10_0" once.

### F7. Unity will use constant-buffer OFFSETTING (VS/PSSetConstantBuffers1) at 9_1 because the runtime reports it there - works on PC, but the design never tested it and it is a CPU-cost path on Tegra  [severity: minor (correctness OK on PC), confidence: high (PC), low (Tegra cost)]
Claim: caps+0x3f9 = D3D11_OPTIONS.ConstantBufferOffsetting (CheckFeatureSupport(5) via the device @0x01007904, stored @0x01007916). GfxDeviceD3D11::vf78 (0x01005750, the only user of the Context1 getter sub_ffcb18) reads +0x3f9 (@0x010057b6) and then binds cbuffer windows with ID3D11DeviceContext1 slots 0x1dc VSSetConstantBuffers1, 0x1ec PSSetConstantBuffers1 (also 0x1e0/0x1e4) (@0x01005aba..0x01005b3e), with offsets rounded to 256 bytes (`bic sb,r3,#0xff` @0x010057a0). Microsoft: "The runtime will emulate this feature for feature level 9.1, 9.2, and 9.3; therefore, this feature is supported for feature level 9.1, 9.2, and 9.3." On this PC both Intel HW and WARP at FL 9_1 report ConstantBufferOffsetting=1, so Unity WILL take this path on a 9_1 device; the design's draw test only used VSSetConstantBuffers. Measured (critic\crit_il.c with CBOFF=1): one 64 KB DYNAMIC constant buffer filled with garbage except Unity's 4 cbuffers at 0x1000/0x2000/0x3000/0x4000, bound with VSSetConstantBuffers1(first 256/512/768/1024, num 32 each) + the level-9 Sprites/Default VS -> read-back 200 100 50 255 on Intel HW and WARP, no debug-layer message, device not removed. So the level-9 constant mapping (c# <- cb windows) honours the offsets. Open: emulation means the runtime copies the window into D3D9 constant registers on the CPU for each draw; with Unity's large shared cbuffers this is per-draw CPU work on a Cortex-A9/A15 (not measured).
Evidence: `arm32re.py func 1007434` (0x01007904..0x01007916), critic\fn_vf78.txt (lines 30-60, 313-364); https://learn.microsoft.com/en-us/windows/win32/api/d3d11_1/nf-d3d11_1-id3d11devicecontext1-vssetconstantbuffers1 (Remarks); critic\cboff_hw.txt, cboff_warp.txt.
Proposed fix: keep the path (it works), but (1) add the CBOFF draw to the M2 harness for every needed VS/PS pair, (2) give the fix-up a switch "cboffset=on|off" (off = write caps+0x3f9 = 0 so Unity falls back to per-buffer updates) and (3) add a CPU micro-benchmark to the M0 probe on both tablets: 500 draws/frame of a level-9 sprite quad with 3 cbuffer windows changing per draw, HW 9_1, measure ms/frame for both cboffset modes. That number decides whether the Tegra 3 can reach 30 fps with this game's draw-call count, before any Unity work.

### F8. "No DXGI hooks needed" leaves the bring-up blind: no frame time, no Present error, no device-removed reason, and no fallback if the 9_x swap chain refuses SHADER_INPUT  [severity: major (diagnosability), confidence: high]
Claim: design F5 says "No context hooks and no DXGI hooks are needed", yet design F7 wants frame time "count Present via the swap chain Unity creates, or Clear calls" (Present needs a DXGI hook, Clear a context hook - both excluded). When the device is lost Unity only prints "Skipped rendering frame because GfxDevice is in invalid state (device lost)" (string 0x01cf9880) and keeps going with a frozen/black screen; the design's own bench shows one stray R32_UINT index bind removes the Intel device (0x887A0020). Without a Present hook the shim cannot log DXGI_ERROR_DEVICE_REMOVED + GetDeviceRemovedReason, cannot report fps (the user's M4 acceptance metric), and cannot tell a GPU frame rate from a software one. The swap-chain desc risk from hw-unitygfx F8 (BufferUsage 0x30 = SHADER_INPUT on a 9_x back buffer vs the 10Level9 rule "When using D3D11_BIND_PRESENT, resource cannot have D3D11_BIND_SHADER_RESOURCE") was only cleared on the PC runtime with CreateSwapChainForHwnd; the appx route uses CreateSwapChainForCoreWindow (IDXGIFactory2 +0x40, sub_2f458c @0x002f45fe) on a Tegra driver, with no plan B if it fails.
Evidence: design F5/F7 text; `arm32re.py strx "device lost"`; `arm32re.py imports dxgi` (CreateDXGIFactory1 IAT 0x017178b8, CreateDXGIFactory2 IAT 0x017178b4; callers sub_ffdc74 @0x00ffdcba, sub_297178, sub_fd58c8); surface2_win10_0104_1346dll_backbutton.log line 244 (the 0.10.4 host already patches the game's IDXGIFactory2 vtable on device, so the technique is proven there).
Proposed fix: add a small DXGI part to M1: redirect UnityPlayer's dxgi.dll import the same way as d3d11.dll (or patch the factory vtable cell like the 0.10.4 host), hook CreateSwapChainForCoreWindow (log desc + hr; on failure retry once with BufferUsage 0x20) and give the returned swap chain a per-object vtable copy (full length, F2) with Present/Present1/ResizeBuffers hooks: count frames, log fps every 5 s, log any failing hr with GetDeviceRemovedReason. Only in L9 mode, so FL10+ devices stay untouched.

### F9. Shader swap: Unity parses nothing but ISGN, so the swap itself is safe - but a table MISS gives an invisible object (not the pink error shader), so the table should carry every compilable program of the reachable shaders, not only the 112 predicted ones  [severity: minor, confidence: medium]
Claim: (a) Safe: a literal-pool scan of all of UnityPlayer's .text for DXBC chunk tags finds only 'ISGN' and 'ISG1' (both in sub_100fa88) and 'DXBC' (sub_fff01c, sub_fff0f8); no 'SHDR', 'SHEX', 'RDEF', 'OSGN', 'SFI0' or 'Aon9'. So apart from the input signature (F1) Unity never inspects the bytecode it hands to CreateVertexShader/CreatePixelShader, and swapping the blob inside the hook is invisible to it. (b) Miss behaviour: on a failed CreateVertexShader Unity logs "D3D shader create error for vertex shader [0x%08x]" (0x02668520, @0x0100383a..0x01003846) and the D3D11VertexShader constructor sub_10010f8 just sets its "not supported" byte (`strb.w r4,[sb,#8]` @0x01001144). The pink Hidden/InternalErrorShader only replaces shaders that are rejected at LOAD by the caps/requirement filter (F6a); a program that fails at creation time most likely just does not draw (unverified at draw time). So the design's "Unity then uses its error shader" (design F5) is probably wrong: a miss = silently invisible sprite/text. (c) The 112-program "needed" set is a static prediction (FORWARDBASE DIRECTIONAL [+LIGHTPROBE_SH], tiers, keywords from materials). all_programs.csv shows 114 more unique programs belonging to reachable shaders (A/B/C use) that are not in the table; 74 of them are "mechanical" (already translatable and level_9_1-compilable by the existing tool chain), e.g. FORWARDBASE "DIRECTIONAL LIGHTPROBE_SH VERTEXLIGHT_ON" VS of INShaders/*, Hidden/BlitCopyHDRTonemap and Legacy Shaders/Diffuse, and Particles/Standard Unlit PS variants.
Evidence: critic\magic.py output ("SHDR 0", "RDEF 0", "OSGN 0", "Aon9 0", "ISGN 1 100fb34(sub_100fa88)", "DXBC 2 fff0f4(sub_fff01c) fff138(sub_fff0f8)"); `arm32re.py func 100378c`, `func 10010f8`; games_recon/bad_piggies_shader_proto/auto/all_programs.csv (script output "programs of reachable shaders NOT in needed set: 114 Counter({'mechanical': 74, 'impossible': 21, 'hand': 19})").
Proposed fix: build l9_replacements.bin from ALL level_9_1-compilable programs of the 57 reachable shaders (about 107 + 74 + the 4 hand ones + 2 blits), store shader name/pass/keywords per entry in a side file, and make the shim log every miss with the 16-byte checksum so the side file (generated from all_programs.csv for all 402 programs) names the shader/variant. Optional: on a VS miss, return a level-9 "magenta" program with the same input signature instead of E_FAIL, so a missing variant is visible on screen during M3/M4 instead of silently absent.

### F10. The PC harness cannot stand in for the Tegra D3D9-class drivers - run an ARM32 build of the bench itself on both tablets in M0, before writing the shim  [severity: major (schedule risk), confidence: high]
Claim: every "works at 9_1" statement in the design (shader replacements, input layouts, Unity's swap-chain desc incl. SHADER_INPUT, separate-alpha blend accepted at creation, A8/B4G4R4A4/BC formats, 368-byte cbuffers, timestamp queries, NPOT with mips, vtable copy, cbuffer offsetting) was measured on an Intel UHD 620 driver and WARP, both reporting FullNonPow2TextureSupport=1, D3D9_SHADOW_SUPPORT=1, OutputMergerLogicOp=1 and SimpleInstancing=1 at FL 9_1 (design\bench_warp.txt / bench_hw.txt). The 10Level9 runtime forwards 9_x devices to the driver's D3D9-class path, so draw-time and creation-time behaviour that the runtime does not validate is driver-specific - exactly the part the PC cannot show (the design admits this for NPOT+WRAP, separate alpha and FP20 precision). The design's M0 probe only measures adapters, max FL, driver DLL and fill rate; the first time a replacement shader, a Unity-style blend/sampler/format or the vtable trick meets the Tegra driver is M3 - after the shim, harness and appx packaging are all built (design estimate 6-9 days).
Evidence: design F2/F4/F8 and M0..M3 text; bench outputs in design\; critic\crit_il.c and crit_vt.c (already standalone C, no Unity needed).
Proposed fix: extend M0: build l9bench.c + crit_il.c + crit_vt.c for ARM32 (repo clang-rt toolchain), with a "no debug layer" mode and a log file, and run them on Surface RT and Surface 2 together with the adapter probe. Gate: all 113 (later ~190, F9) replacements create, the Sprites draw reads back the right pixel, the full-vtable copy survives swap chain + Present, cbuffer offsetting draw is right, and the format/state table (A8, B4G4R4A4, BC1/BC3 NPOT 1-mip, D24S8, Unity's swap-chain usage 0x30) is recorded per device. Also record D3D9_OPTIONS/D3D9_SHADOW/OutputMergerLogicOp/ConstantBufferOffsetting per tablet: these drive the caps fix-up values. One user session per tablet answers most of the device unknowns before any Unity work.

### F11. Sanitizer gaps: CreateBuffer has no hook, and some 9_1 rules live on the context side where the design deliberately has no hooks  [severity: minor, confidence: medium]
Claim: Microsoft's 10Level9 device page says for CreateBuffer at 9_1: "Buffers must have exactly one of D3D11_BIND_VERTEX_BUFFER, D3D11_BIND_INDEX_BUFFER, or D3D11_BIND_CONSTANT_BUFFER", and the design's own bench confirms "VB|IB combined -> E_INVALIDARG"; CreateRenderTargetView: "Can only support render target views of Texture2D objects" (no cube-face or array RTVs). Unity's buffer creator sub_ffd830 (only caller GfxDeviceD3D11::vf69 @0x010080aa) builds BindFlags from its target bits: &1 -> VB, &2 -> IB, &0x200 -> CB, &0x1f0 -> SRV (|0x80 raw/unordered when allowed), stream-out for type 3 (@0x00ffd90a..0x00ffd948) - so a combined-target GfxBuffer becomes a multi-bind D3D buffer. Whether this game creates one is not traced (Unity's mesh and dynamic VBOs normally use one target each); compute-type buffers are refused by Unity itself when caps mask has no 0x4000 (@0x00ffd868, message 0x02665b48). Context-side 9_1 rules the shim cannot see without context hooks (10Level9 context page): IASetIndexBuffer "Only allows index buffers with the DXGI_FORMAT_R16_UINT format" (one violation removed the Intel device in the design bench), DrawIndexed "Index values cannot exceed 65534", OMSetBlendState "SampleMask cannot be zero", RSSetViewports fails for a negative top-left corner at 9_x, "Textures cannot repeat over one primitive more than 128 times". The design's caps keep Unity inside most of these, but nothing would report a violation. Also untraced: whether the player builds a default reflection cubemap at run time for the 4 scenes that have Skybox/Procedural (reflection-probe code sub_3a2e8c is gated by caps mask bit 0x40 @0x003a307c, which the 0xE3 claim turns on) - a cube render target would hit the RTV rule above.
Evidence: https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-device (CreateBuffer, CreateRenderTargetView); https://learn.microsoft.com/en-us/windows/win32/direct3d11/d3d11-graphics-reference-10level9-context (IASetIndexBuffer, DrawIndexed, OMSetBlendState, RSSetViewports); `arm32re.py func ffd830`, `callers ffd830`; design\bench_hw.txt ("buffer VB|IB combined ... as-expected" failure).
Proposed fix: add a CreateBuffer hook to M1 that logs every BindFlags combination once and refuses/logs multi-bind buffers loudly; log CreateRenderTargetView/CreateTexture2D calls with MISC_TEXTURECUBE or ArraySize>1. For the context-side rules, add an optional "diagnostic" build that patches the few context cells (IASetIndexBuffer, OMSetBlendState, RSSetViewports) the way the 0.10.4 host already does on device (it re-patches the runtime-rewritten cells), to be used only in M3/M4 debugging sessions, never in the release build.

### F13. The depth rule in the design contradicts its own bench: "map to D24_UNORM_S8_UINT, keep SHADER_RESOURCE when D3D9_SHADOW_SUPPORT" fails  [severity: minor, confidence: high]
Claim: design F5 says CreateTexture2D maps R32G8X24_TYPELESS / D32 depth to D24_UNORM_S8_UINT and drops SHADER_RESOURCE "unless D3D9_SHADOW_SUPPORT is set". But Unity's back-buffer depth asks for SHADER_RESOURCE at every start (hw-unitygfx F6: `mov.w r8,#1` @0x01007ebc -> `orr r3,#8` @0x01007f38), and the design's bench shows D24_UNORM_S8_UINT with DEPTH_STENCIL|SHADER_RESOURCE returns E_INVALIDARG on both Intel HW and WARP ("The format (0x2d, D24_UNORM_S8_UINT) cannot be bound as a ShaderResource"), while R24G8_TYPELESS DS|SR succeeds on drivers that report D3D9_SHADOW_SUPPORT=1. So on a shadow-capable 9_1 driver the rule as written makes the back-buffer depth creation fail -> Unity has no depth buffer (and UI Mask stencil, hw-content F14, needs it).
Evidence: design\bench_hw.txt and bench_warp.txt lines 48-51; design F5 CreateTexture2D bullet.
Proposed fix: for this game always drop SHADER_RESOURCE on depth textures and create D24_UNORM_S8_UINT (Unity never samples the camera depth here: no depth textures, no shadows, hw-content F10), and answer Unity's depth SRV request with the 1x1 dummy SRV. If a future game needs sampled depth on a shadow-capable driver, use R24G8_TYPELESS + DSV D24_UNORM_S8_UINT + SRV R24_UNORM_X8_TYPELESS instead.

## Summary
Plain language:
 - I tried to break the recommended plan (a small D3D11 shim that, only on GPUs below feature level 10, makes a 9_x device, swaps Unity's shaders for level-9 versions, cleans up states/formats and corrects Unity's capability record). The plan survives: nothing found makes GPU rendering at 9_1 impossible, and several of its key claims are now confirmed (Unity filters shaders by a requirement mask exactly as feared, so the 0xE3 value is right; GetFeatureLevel is used once; all hook addresses are right; the game is D3D11-only; Unity never inspects shader bytecode except the input signature; no deferred contexts).
 - But two parts would have failed on the first run if built exactly as written, both found by testing on this PC with a real FL 9_1 device:
   1. The input-layout hook (F1): Unity does not pass a shader to CreateInputLayout but a small signature-only blob it builds itself, so a checksum lookup misses every time and "return E_FAIL" would leave the game with no geometry. Fix: do not touch CreateInputLayout - the 9_1 runtime accepts Unity's blob as is (tested, correct pixel).
   2. The vtable copy (F2): the device's method table is 174 entries long on this PC and DXGI uses entries far beyond the interfaces Unity knows; a copy sized like the SDK interface (54) crashes inside swap-chain creation. Fix: copy the full length, measured at run time.
 - Other gaps: the Unity splash screen is on, so the "IMGUI-only" GUITexture shader and its blend states are on the first-frame path (F3); the device policy could silently accept a software adapter at FL 10+ and never reach 9_1 - and the Surface 2's adapter calls itself "Software Adapter" (F4); view descriptors must mirror any texture change (F5); a few caps values are wrong or incomplete (F6, F13); Unity will use cbuffer offsetting at 9_1 (works, but costs CPU - measure it) (F7); without a swap-chain hook there is no fps, no Present error and no device-lost reason (F8); a table miss makes objects invisible, so ship every compilable variant (F9); PC drivers are more permissive than the Tegras, so run the bench itself on the tablets first (F10); CreateBuffer and some context-side rules are unguarded (F11).
 - Effort: the shim needs about 3-5 more days than planned, and if the Surface 2 turns out to be software-only, the only GPU target is the Surface RT through the Win32Craft host - that is weeks of extra work, not an appendix (F12).
Verdict: possible. The design is sound after the fixes above; the decisive unknowns are on the devices, not in Unity.
