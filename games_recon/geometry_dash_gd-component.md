## Summary
The native side of Geometry Dash is small and fully decodable. The WinMD defines two classes: Direct3DInterop (a free-threaded WRL/C++CX object created through DllGetActivationFactory with CreateInstance(int orientation)) and BroswerEventHelper (static SetCallback plus five service methods the managed shell used to provide), plus four delegates and two enums; every interface method, slot number and IID is listed in F1 and cross-checked against the real vtables in F3. Direct3DInterop.CreateContentProvider returns a native Direct3DContentProvider that implements the Windows Phone 8 interface IDrawingSurfaceBackgroundContentProviderNative (IID {262C1892-975A-45AA-8FE7-F25C2C4088E3}) with exactly four methods: Connect(host, device), Disconnect(), PrepareResources(time, &desiredSize) and Draw(device, context, renderTargetView). The only thing the component ever calls back on the compositor's runtime-host object is slot 3 = RequestAdditionalFrame(), once at the end of each Draw. It never creates its own D3D device: the device, context and render-target view given to Draw are handed straight to the bundled ANGLE (libGLESv2_phone.dll), which uses them as-is; the first Draw also initialises EGL/GLES and launches the cocos2d game. Pointer input comes through three TypedEventHandler delegates that Direct3DInterop registers on a host object (slots 6/8/10); keyboard, back button and edit-box results are plain method calls. So a Win32 host needs: a D3D11 device and a portrait-shaped render target, a presenter that rotates that target by 90 degrees, one fake runtime-host object (IUnknown + RequestAdditionalFrame), one fake manipulation host with fake pointer-event objects, an ICallback object, three delegate objects and a loop that calls PrepareResources then Draw once per display frame on one thread (F11 has the exact order). Two corrections to the earlier unverified shell recon: the six-slot vtable at 0x223FB4 is IMarshal (not the drawing interface), and the pointer position is NOT scaled by ResolutionScale in the XAML build. Main risks: on Surface RT / Surface 2 (FL9_1 only) the game always asks ANGLE for feature level 9_3 even though the shaders are SM2.0 level-9_1 style (F6, F12); the portrait render target / rotation is inferred from code, not from a running game (F9); and the component imports the Windows Phone 8 builds of the C++ runtime and PhoneAppModelHost, which other areas must solve. The recommended next step is to build the headless host skeleton (F11 steps 1-6) with logging on all fake objects and render one frame into an offscreen texture.
