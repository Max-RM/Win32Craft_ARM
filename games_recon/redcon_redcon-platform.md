### F2. Pointers: up to 16 simultaneous pointer slots, mouse and touch are indistinguishable, pressed/released/capture-lost must be delivered in matched pairs  [severity: minor, confidence: high]
Claim: sub_6D854 maps the PointerId to a slot index 0..15 using a 16-entry id table at 0x5C8710 and the in-use bit masks [0x5C87F8]/[0x5C8838] (an existing id is found first, otherwise the first free hole, otherwise the index after the highest used one; with all 16 slots used this is index 16 = one past the table). Pressed sets the bit, Released AND CaptureLost clear it (same handler sub_6D99C), then the position/slot bookkeeping sub_6C69C runs. A pointer that is pressed and never released/capture-lost stays allocated forever (after 16 such leaks new pointers collide on index 16). The game does not look at the device kind, so a Win32 mouse can be delivered as one pointer with a fixed id (for example 1) and touch as WM_POINTER/WM_TOUCH ids. The position goes through sub_6C69C, which applies an affine transform (a 2x2 matrix plus offset kept in the globals 0x5C883C, 0x5C8700, 0x5C8834 and 0x5C85AC, 0x5C8798, 0x5C882C) and floors the result to integers, so the game maps the event position to its own pixel space itself; the matrix is set by the swap-chain/orientation code (sub_6E1D8), which works from CoreWindow.Bounds * RawPixelsPerViewPixel (render recon), so the consistent choice is CoreWindow (view/DIP) coordinates of the client area (the exact scale convention was not traced, UNVERIFIED).
Evidence: `arm32re func 6d854` (table 0x5C8710, "movs r4,#0x10" default, masks 0x5C87F8/0x5C8838); `func 6d99c` (the "bics r3,r1" clear of the mask bit at 0x6DA2C, then sub_6C69C at 0x6DA3A); `func 6d8bc` (the "orrs r3,r2" set at 0x6D93C); `func 6c69c` (vmul/vmla by the matrix globals, floorf via IAT thunk 0x13AC20, vcvt.s32.f32 results stored to the two output pointers).
Proposed fix: on WM_LBUTTONUP, focus loss, capture loss and window deactivation always raise PointerReleased or PointerCaptureLost for every pressed pointer; keep ids stable per touch contact.

PPL is used for the store and network completions; the PPL code in the exe calls CoGetApartmentType (sub_78FD0, sub_796F4) and CoGetObjectContext (sub_78FA0, sub_79008) to implement continuation contexts and refuses waiting on an STA ("Illegal to wait on a task in a Windows Runtime STA", string RVA 0x144A40). A real Windows Phone UI thread is an ASTA, so PPL continuations created with the default context return to the UI thread there; in an MTA host they run on pool threads. The game has its own mutex-protected main-thread queue (F14), presumably how network results reach the UI thread, but that was not traced for HTTP nor for the Store continuations (F11) (UNVERIFIED): the Store fake should complete its operations from the UI loop (not from an arbitrary thread) to stay close to the original timing.
Evidence: `func 13a360`, `callers 13a360`; `impcallers CoGetApartmentType` (sub_78fd0, sub_796f4) and `CoGetObjectContext` (sub_78fa0, sub_78fd0); wide strings dump RVA 0x144A40 (ASCII 'Illegal to wait on a task in a Windows Runtime STA'); win32_host_arm32_0104_platform.inl 443-513; startup recon F16 ("RoInitialize is not called by the CRT").
Proposed fix: boot sequence RoInitialize(MTA) on the UI thread before Application::Start's callback; complete fake IAsyncOperation objects (store, PropertyValue-free) on the UI thread by queuing the Completed handler into the Rendering/UI pass.

### F18. Lifecycle hooks the host must raise because audio and rendering depend on them  [severity: minor, confidence: high]
Claim: audio pause/resume is not tied to Suspending directly but to the game's Rendering pause/resume pair: sub_6CA34 (pause; called from VisibilityChanged(false), Suspending and while the XAML dialog is open) calls sub_8B760 (MediaEngine.Pause + IXAudio2::StopEngine) and sub_6CA90 (resume; VisibilityChanged(true), Resuming) calls sub_8B7BC (MediaEngine SetVolume+Play + IXAudio2::StartEngine). So a host that never raises VisibilityChanged(false)/Suspending on minimise keeps music and effects playing in the background, and a host that never raises VisibilityChanged(true) after restore leaves the game paused (the startup recon's lifecycle table applies unchanged). The engine-callback object registered with RegisterForCallbacks gets IXAudio2EngineCallback::OnCriticalError from XAudio2's thread when the audio device disappears (for example USB headset unplug); the game's handler path sets [0x5C889C] and the next resume re-creates nothing (not traced further, UNVERIFIED), so audio may stay silent until restart after a device loss.

## Summary

Plain-language verdict for the area "input, audio, storage, phone-only and platform APIs" of REDCON 1 (Redcon.exe 1.3.0.0, Hexage, WP8.1 XAML game, Java-to-C++ translated engine "Mojo"):

1. Input is small and clean. Everything comes from 11 CoreWindow events (pointer pressed/moved/released/capture-lost, key down/up, character, visibility, size, activated, closed) plus one HardwareButtons.BackPressed handler; touch and mouse look the same to the game (position + pointer id, up to 16 pointers), the keyboard is only Enter/Esc/arrows/letters/digits, and Back is always "handled". No sensors, no gestures, no mouse wheel, no CoreIndependentInputSource, no on-screen-keyboard API. Most fakes already exist in the 0.10.4 host; the new ones are tiny.
2. Audio is native code plus two OS engines: effects = 148 OGG files decoded by the game itself and played through XAudio2_8 (mono 22.05 kHz voices on a mono mastering voice), music = 6 WMA files played through the Media Foundation Media Engine (IMFMediaEngine, created with CoCreateInstanceFromApp). No Windows.Media.* WinRT classes at all. Both are optional (the game continues silently if either creation fails). They need COM initialised on the UI thread and the OS DLLs (XAudio2_8, MFPlat, mfmediaengine, a WMA decoder); XAudio2 is proven on the project's Win10 / Win11 devices through 0.10.4, Media Engine on RT 8.1 / Win10 ARM32 is unmeasured.
3. Storage is plain C file I/O: assets from <InstalledLocation>\res\assetNNN.* and the data files, saves as <LocalFolder>\save<N> (written via .tmp + MoveFileExW), a "settings" file, and string key/values in the ROAMING settings container (the startup recon wrongly said Local). Two traps: the install folder path is narrowed to ASCII and copied into a 256-byte heap buffer with no length check (ASCII-only, short paths required), and the LocalFolder path goes into a 256-wchar buffer.
4. Phone-only classes: StatusBar (HideAsync at the very start), HardwareButtons.BackPressed, VibrationDevice. The vibration object is stored without a problem but Vibrate() later dereferences it with no NULL check, so the fake must return a non-NULL object.
5. Network / internetClient: Hexage's opt-in online leaderboard and cloud-save sync via an IXMLHTTPRequest2 HTTP+JSON client (msxml6, free-threaded), connectivity probes (NetworkInformation) and a device id derived from the network adapter GUID; URL launching (Launcher) and the Store. No ads, no Xbox, no sockets. The server endpoint is not readable (unverified) and is probably dead; the UI has a "Service Unavailable" path.
6. In-app purchases: the game is a free edition plus three premium tiers (REDCON 3 / 2 / 1) sold as in-app products; ownership is tested per product with CurrentApp.LicenseInformation.ProductLicenses.Lookup(id).IsActive (no IsTrial call). The 0.10.4 CurrentApp fake would crash Redcon (it returns a NULL ProductLicenses map and lacks LoadListingInformationAsync, GetAppReceiptAsync and the consumables interface). The Windows Phone Store is closed, so purchases cannot succeed; which products to report as owned is a policy choice for the project owner.
7. Imports: nothing is missing on a Windows 10 desktop; the three VC120 `_app` DLLs resolve completely against the 0.10.4 copies; the 12 API-set contracts are already proven natively on a real RT 8.1; open items are the debug-l1-1-1 contract and the functions CoCreateInstanceFromApp / StringFromGUID2 / IsProcessorFeaturePresent on RT 8.1, and the new desktop DLL dependencies d2d1, DWrite, MFPlat, mfmediaengine, msxml6 (device check, loadcheck.exe).

Recommended next step: build the "Redcon unit" for the platform area in this order: (a) ApplicationData (Roaming + Local settings with IMap), Package, ApplicationLanguages, with the ASCII/length guard; (b) StatusBar / HardwareButtons / VibrationDevice (non-NULL) / NetworkInformation additions; (c) a CurrentApp fake with a ProductLicenses map that answers any key (default: nothing owned) and completed async operations; (d) Launcher via ShellExecute; (e) test XAudio2 + Media Engine on the Surface 2 first (log the HRESULTs of CoCreateInstanceFromApp for both CLSIDs), then RT 8.1 with loadcheck.exe; (f) decide the dialog strategy (F19).
