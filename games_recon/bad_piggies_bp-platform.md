### F13. Hazards for a host: hangs, throwing helpers, and one thread  [severity: major, confidence: medium-high]
Claim:
 1. ## Summary
Verdict (platform-API area only; the Direct3D feature-level problem is a separate area): the platform side of Bad Piggies Rebooted is small and mostly already solved by the existing Win32Craft hosts. The game's own code (IL2CPP, 50,884 methods, symbolized here) only asks the engine for: file saves under the app-data folder, PlayerPrefs strings, touch/mouse/keyboard polling, window/fullscreen/sleep control, HTTPS to PlayFab and Rovio, and clipboard/URL opening. It does NOT use Store/IAP (NullIAP), Xbox Live, an ad SDK (local state machines), vibration, sensors input, tiles/toasts, a webview, or any native plugin. UnityPlayer.dll runs in plain CoreWindow mode (no XAML), on ONE thread (the exe's view thread), and before the first frame it needs: LoadPackagedLibrary for GameAssembly.dll (shim to LoadLibraryW already exists in api_compat.c), ApplicationData.Current with LocalFolder AND TemporaryFolder (PlayerPrefs file read, log file, persistentDataPath; failure throws), CoreApplication/CoreWindow/CoreDispatcher/ApplicationView/DisplayInformation, ApiInformation/AnalyticsInfo (must not say Holographic), SystemNavigationManager, MouseDevice and pointer/touch/mouse capability classes, a Clipboard.ContentChanged hook and SimpleOrientationSensor. Gamepad/HID, device identity, language, hostnames and the audio stack are real Windows classes that should work unpackaged (to be confirmed on a device). Audio is FMOD built into UnityPlayer.dll with a Metro WASAPI output: it falls back to "no sound" if the device cannot be opened, but it contains five verified INFINITE waits on ActivateAudioInterfaceAsync completions, so a half-working fake can hang the game at start-up. If the appx is installed normally on Windows 10 15035 nothing has to be faked, but the stock manifest has no capabilities at all (no internet, no HID), asks for VCLibs 14.0.33519 and for D3D feature level 10.0.
Recommended next step: build the host list from the "F" rows of the F11 table (almost all exist in win32_host.c / the 0.10.4 .inl files; the new ones are TemporaryFolder, Clipboard, MessageDialog, the Unity-specific CoreWindow event set and one-thread dispatcher semantics), forward every other class to the real OS with the existing "WinRT fallback" logging, then do ONE logged run on the Surface 2 and read: (1) whether the log stops right after "Init FMOD" (if so make ActivateAudioInterfaceAsync fail fast or apply the nosound patch of F5), (2) which "WinRT fallback" classes returned errors, (3) whether UnityPlayer.log appears in TempState and boot.config takes effect (open question F4 item 3), (4) that the process current directory is the game folder (relative il2cpp data dir).
Not verified (needs a device or deeper decoding): behaviour of real MediaDevice/DeviceInformation/EasClientDeviceInformation/Clipboard in an unpackaged ARM32 process; the BackRequested handler body; how the two start-up jobs are ordered; whether the null/failed results of SimpleOrientationSensor and Gamepad activation are tolerated; which key triggers fullscreen/quit in the game; file:// request use; Windows RT 8.1 api-set availability of the imports (measured elsewhere in the repo, not re-measured).
