### F3. Every texture format used is a legal FL 9_1 format; RGB24 and Alpha8 have footnotes  [severity: info, confidence: high]
Claim: At FL 9_1 the doc [D3] lists as required for Texture2D + sampling + mipmaps: BC1/BC2/BC3 (UNORM and UNORM_SRGB), R8G8B8A8_UNORM(_SRGB), B8G8R8A8_UNORM(_SRGB), B5G6R5, B5G5R5A1, B4G4R4A4, R8_UNORM; the BC4_UNORM/BC5_UNORM and R9G9B9E5 rows are all "-" (not supported), BC6H/BC7 are not listed on the page and [D1] says "No" for BC4/BC5 and BC6H/BC7 at 9_1. So DXT1 (=BC1), DXT5 (=BC3) and RGBA32 (R8G8B8A8) are fine. Footnotes: (a) RGB24 has no DXGI/GraphicsFormat equivalent; Unity's graphics-format table (UnityPlayer.dll file offset 0x2675288, rows {sRGB,linear,typeless,flags}, indexed by GraphicsFormat) has only R8G8B8A8 / B8G8R8A8 for 8-bit-per-channel colour, so the 4 RGB24 textures are expanded to RGBA32 at load (the 2160x1080 one: about 11.9 MB GPU with its 12 mips, but 4096x2048 RGBA32 + mips = about 45 MB if NPOT rounding makes it 4096x2048, see F4/F5): inference from the table, the expansion code itself was not traced. (b) Alpha8 maps to GraphicsFormat row 54 = DXGI A8_UNORM (65): [D3] lists A8_UNORM Texture2D / sample / RenderTarget as required but NOT "Mipmap"; the 3 Alpha8 textures all have 1 mip so this is not hit by the game's own data (Unity's built-in 'Soft' 128x128 Alpha8 with 8 mips in "unity default resources" is the only mipped Alpha8; not referenced by game materials as far as found, unverified). (c) The Gamma/Linear question is irrelevant here (F8): even if an sRGB-flagged texture used the _SRGB variant, BC1/BC3/R8G8B8A8 _SRGB are required formats at 9_1 too.
Evidence: format table dump (decode script in scratchpad: row 4 = R8G8B8A8_SRGB/UNORM/TYPELESS, row 54 = A8_UNORM, rows 96..101 = BC1/BC2/BC3, 102..109 = BC4..BC7); [D3] sections DXGI_FORMAT_BC1/BC2/BC3 (71..78), BC4/BC5 (79..84, all '-'), A8_UNORM (65), B4G4R4A4_UNORM (115).
Proposed fix: none. Optional: convert the 4 RGB24 textures to DXT1 offline to cut ~12-20 MB (not required).

### F5. NPOT textures: 18, of which 3 break FL 9_1 rules (NPOT + mip chain, NPOT + Repeat); one of them is loaded with EVERY level  [severity: major, confidence: high]
Claim: FL 9_1 allows non-power-of-2 2D textures only with ONE mip level and no WRAP sampler mode [D1 footnote 3]; CreateTexture2D requires power-of-two dimensions whenever MipLevels > 1 [D2 CreateTexture2D table: "If MipCount > 1, Dimensions must be integral power of two: Yes" for 9_1/9_2/9_3]. Data has 18 NPOT textures (15 in Data + 3 in bundles). 15 of them are legal as-is (1 mip and clamp wrap): UI_EnterButton/UI_MenuButton/UI_BackButton/UI_Button_Background 200x200 DXT5, PartSliderButton_Up/Down 35x16, UI_SettingsInterface_Toggle 50x50, hd_icon 122x122, Light_Gradient 1x200, coin_background 580x534, PurpleCoin_background 284x530, Wheel 595x593, Comic_CakeRace 1024x739 (RGB24), bundle Comic_Maya_mid_01 1024x544 DXT1, bundle Comic_Maya_Intro_01 1024x725 RGB24. The 3 that violate:
 (a) 'loading' 124x124 RGBA32, 7 mips, Repeat (sharedassets0.assets #70). Used by Materials 'Loading' (#26) and 'loading_0' (#41) and listed in the PreloadData of every sharedassetsN.assets (ref1.py: 30+ PreloadData objects reference it) - it is part of the loading screen (AtlasMaterials.loadingScreen field) = on the critical path of every level load.
 (b) 'Comic_DailyChallenge' 1024x652 RGB24, 11 mips, Repeat (sharedassets30 #3, Material 'Comic_DailyChallenge') = daily challenge intro scene.
 (c) 'Innovation_VersionSelector_Background' 2160x1080 (F4).
Unity already has the logic to cope IF its caps say "NPOT restricted": function sub_5d8b04 (RVA 0x005d8b04, called from Texture2D::vf49 @0x005d9afc/0x005d9b08 and Texture2D::vf40 @0x005dcf0e..0x005dd006): it rounds a dimension up to the block size, then returns it unchanged only if (hasMips ? caps.NPOT == 2 : caps.NPOT >= 1), otherwise to the NEXT power of two (bit-smear sequence orr r3,r3,r3,lsr #16/#8/#4/#2/#1 then adds r0,r3,#1 @0x005d8b6a..0x005d8b7e). caps.NPOT is the field at caps+0x378 that UnityPlayer currently hard-codes to 2 ("Full") for every feature level (hw-unitygfx F5). sub_5de9a4 (TextureSettings.cpp, RVA 0x005de9a4): if a boolean stack argument (apparently "texture is NPOT"; not traced to its caller) is set and caps.NPOT <= 1 and the dimension argument equals 2, wrapU/V/W are forced to 1 (Clamp) (@0x005de9f2..0x005dea04); and if caps+0x36c (SupportsTextureWrapMirrorOnce) == 0, MirrorOnce(3) is converted to Mirror(2) after logging (@0x005dea06..0x005dea68). sub_5da6a4 (@0x005da6a4) is the boolean helper "NPOT allowed for hasMips". So the engine side of the fix is: caps.NPOT = 1 (Restricted) and caps+0x36c = 0 at FL 9_1 (both already proposed in hw-unitygfx F5). With that: 'loading' becomes 128x128 + 8 mips + clamp, 'Comic_DailyChallenge' becomes 1024x1024 + clamp, and 'Innovation_VersionSelector_Background' becomes 4096x2048 (round UP, > 2048, F4). Texture2D::vf40 (RVA 0x005dccf8) is the function that fills the texture-upload descriptor: it stores the source width/height at desc+0x38/+0x3c and the conformed dimensions (through sub_5d8b04) at desc+0x80/+0x84 (full chain) and desc+0x64/+0x68, computes the sizes of both with sub_5920d0/sub_592120 and later compares conformed vs source width (@0x005dcff0), so the upload code is built to upload a resized image. UNVERIFIED: the resample itself (for the uncompressed RGBA32/RGB24 textures it is possible; the 3 offenders are all uncompressed, and no NPOT DXT texture has mips, so no compressed re-scaling is ever needed).
Evidence: tex2.py NPOT list; mat1.py (materials -> textures); disassembly of sub_5d8b04 / sub_5da6a4 / sub_5de9a4 / Texture2D::vf49 (tools/arm32/arm32re.py func, ARM32_EXE=UnityPlayer.dll).
Proposed fix: engine: caps NPOT=1 + MirrorOnce=0 (4 bytes in the patched cap-init code). Content alternative that needs no code: edit 'loading' to 128x128 (or remove its mips and set Clamp), edit 'Comic_DailyChallenge' to 1024x1024 (or 1024x652 without mips + Clamp). Both are single-texture edits in sharedassets0.assets / sharedassets30.assets (the texture objects are 36 and 1 per file; image data lives in the .resS files, so the Texture2D header fields m_MipCount/m_WrapU/m_WrapV are in the .assets, the pixels in sharedassets0.assets.resS).

## Summary
Plain language: the game's DATA is almost entirely compatible with Direct3D 11 feature level 9_1 - it is a 2D-style game built from small quad meshes. What I checked and found fine: all 907 meshes use 16-bit indices and have at most 126 vertices (the runtime mesh combiner is capped at 65,534 vertices, exactly the 9_1 limit; the code never asks for 32-bit meshes); every texture is DXT1, DXT5, RGBA32, RGB24 or Alpha8 (all legal 9_1 formats, no float/BC4-BC7/ETC/ASTC); 203 of 204 sized textures are 2048 or smaller; the project colour space is Gamma (no sRGB render-target requirement); all 48 cameras are orthographic, render straight to the back buffer, without HDR, MSAA, render textures or depth textures; no lights, shadows, fog, cubemaps, 3D/array textures or skinned meshes exist; quality settings are one level "Fast" (no shadows, no anisotropy, no AA, no soft particles); the 169 shader passes use only 9_1-legal blend/depth/stencil state (the only separate-alpha blends are in the Unity IMGUI shaders, used only by two debug OnGUI scripts).
The content-side conflicts, in order of importance:
 1. NPOT: 3 textures are non-power-of-2 AND have mip maps and/or Repeat wrap, which 9_1 forbids. One of them, 'loading' (124x124, 7 mips) is part of the loading screen and is preloaded with every level; the others are the daily-challenge comic (1024x652) and a UI background. UnityPlayer already contains the logic that rounds such textures up to a power of two and forces clamp wrap, but only when its capability field says "NPOT restricted"; today the player hard-codes "full NPOT" for every device, so a 9_1 device would be asked for illegal textures. Fix = the caps patch (hw-unitygfx F5: NPOT = 1, MirrorOnce = 0). Content alternative: edit 'loading' to 128x128 and 'Comic_DailyChallenge' to 1024x1024 (2 textures).
 2. One texture is bigger than 2048: 'Innovation_VersionSelector_Background' (2160x1080 RGB24, 12 mips) in a rarely used UI. Re-export it at 2048x1024 or less (1 texture) or ignore it.
 3. The only render-texture path is the in-game "snapshot" photo effect (disabled until the player presses the snapshot button); it will hit the depth/typeless-format engine fixes of hw-unitygfx F6/F7.
 4. Runtime-created textures (daily challenge image via LoadImage, dynamic fonts) take whatever size the data says, so the caps patch (max texture 2048, NPOT restricted) must be in place.
Knobs that need no code: QualitySettings textureQuality (masterTextureLimit) at globalgamemanagers file offset 0x18824 (0 = full; 1 = half) - but it only affects the 46 textures that have mip maps, not the 2048x2048 atlases (1 mip), so it is not a general fix. Everything else needs either the engine caps patch or an edit of 2-3 textures.
Relation to the user's question: nothing in the game DATA forces software (WARP) rendering. WARP only enters through the engine's feature-level gate and its hidden automatic fallback (hw-unitygfx F1/F2). Once the engine accepts FL 9_1 (device-creation list + caps table + a few constants) and the shaders are swapped for level_9_1 bytecode (hw-shaders, feasibility good), the content here needs at most the 2 small texture edits (or none, with the NPOT caps fix).
Next step: apply the caps patch (NPOT=1, MirrorOnce=0, maxTexture 2048, 16-bit indices only, 1 render target) together with the unitygfx/shaders work; on first run on a Surface, watch the log for CreateTexture2D failures for 'loading' / 'Comic_DailyChallenge' / 'Innovation_VersionSelector_Background'; if they appear, edit those 2-3 textures as above.
