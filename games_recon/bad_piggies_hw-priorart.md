### F7. Hard facts from Microsoft docs that bound every FL 9_1 route (what 9_1 hardware simply cannot do)  [severity: major, confidence: high]
Claim: (a) Surface RT and Surface 2 are the textbook 9_1 devices: Chuck Walbourn's "Direct3D Feature Levels" page lists "Intel G965 Express Chipset, Surface RT, and Surface 2" under 9_1 (and "Windows phone 8 devices are Feature Level 9.3"); the ANGLE wiki says Surface RT does not reach 9.3. (b) Microsoft's feature-level table for 9_1: shader model "2.0 (4_0_level_9_1)"; no geometry shader / stream-out / compute; no instancing; no separate alpha blend ("Separate Alpha Blend ... No" for 9_1; Yes for 9_2/9_3); no independent write masks (No for 9_1 and 9_2); no mirror-once; no occlusion queries; 1 simultaneous render target (9_2: 1, 9_3: 4); max texture 2048, cubemap 512, texture repeat 128, anisotropy 2; max primitive count 65535 / max vertex index 65534 (so 16-bit indices only); NPOT textures only with 1 mip level and no wrap addressing. (c) "A 4_0_level_9_? profile is compiled twice, so Shader Model 2.0 limits apply" (Walbourn). (d) Microsoft's older RT guidance: "Support for Direct3D feature level 9_1 is required for DirectX Windows Store apps that publish an ARM package. Some Windows RT devices support feature level 9_3" and "you can use the dxcpl.exe tool included in Microsoft Visual Studio to emulate Direct3D feature levels lower than what a system supports" => the whole 9_1 pipeline (device shim + level_9_1 shader table) can be exercised on the x64 dev PC with a small D3D11 test app / fxc, which is also how to test before touching the tablets. (e) WARP: "On systems with the DirectX 11.0 runtime, it supports Feature Levels 9.1, 9.2, 9.3, 10, and 10.1" (Walbourn) - i.e. a WARP device can also be created AT 9_1, which is a good software reference for correctness while the GPU path is brought up.

## Summary
Plain-language answers to the user's questions (prior-art / alternative-route area):

1. Will it render in software? Out of the box on a 9_1-only tablet the game does NOT use the GPU. Unity 2018.4's player only asks for feature levels 10.0 to 11.1; when that fails it quietly tries a WARP (CPU) device, and only if that also fails does it print "Failed to initialize Direct3D ... feature level 10.0 is required" (sibling unitygfx F2). So you get either slow software rendering (if WARP exists on that OS) or the error. GPU rendering at 9_1 will never happen by itself.

2. Why can't a newer/older Unity just do it? Unity history (release notes read directly): FL 9_1 was supported only up to Unity 5.6 (Windows 8.1 / Universal 8.1 builds, `-force-feature-level-9-1` switch); Unity 2017.1 raised the UWP minimum to FL 9_3 and dropped 8.1; Unity 2018.2 dropped every pre-DX10 GPU (FL 9_x) entirely. The game's UnityPlayer.dll (2018.4.36f1) matches this exactly: its list ends at 10_0 and it has no 9_x strings, although Unity's 2018.4 manual still (wrongly) documents the 9-1/9-3 switches. The package even ships StoreManifest.xml with D3D11_HWFL_10_0.

3. Who makes the game, and can it be rebuilt in an older Unity? "Bad Piggies::Rebooted" is a community mod (BP::RE, led by Goggs; successor of the Chinese BPLE mod, built on a decompile of Rovio's Bad Piggies 2.3.6), not Rovio's. The Unity project IS public (github.com/Goggs77/bp-rebooted, Unity 2021.3.45f2, DOTS Entities 0.51, README "not open source", no license file, builds via their Discord). The 2018.4.36f1 UWP ARM appx in your folder was built by someone else from a different/stripped revision. Rebuilding with a Unity that still has FL 9.x is not realistic: only <= 5.6 has 9_1 (and 2017.4 has 9_3 minimum, which a 9_1 tablet fails), the project needs 2020.3.30+/2021.3.4+, and a one-person Vita port shows backporting even the old 2.3.6 base to 2017.4 was a big job.

4. Original Rovio Bad Piggies on Windows: a desktop PC build (Oct 2012, Focus Multimedia, x86) and a Windows Phone 8/8.1 build (Apr 2014); a Windows 8/RT Store app was announced but I could not confirm it ever shipped; the WP 8.1 Store closed 2019-12-16. Nothing officially obtainable, and it would be a different game anyway.

5. Prior art: I found none. No community patch, wrapper or shader converter for running post-removal Unity UWP games on FL 9_x, and no D3D11 FL10-to-FL9 translation layer for ARM32 Windows (DXVK/WineD3D need Vulkan/OpenGL; ANGLE needs FL 9_3+ and Microsoft says Surface RT must use WARP; DirectXTK retired 9.x in Aug 2026). Caveat: reddit and XDA could not be read by my tools.

VERDICT / ranked routes (details in F11): the only route that gives GPU rendering at FL 9_1 for THIS game on Surface RT/2 is to keep the shipped package and make the engine run on a real 9_1 device: (a) feature-level list patch/hook + stop the silent WARP fallback, (b) fix the caps table, typeless depth/RT formats and swap-chain flags, (c) replace all 402 DXBC programs by vs/ps_4_0_level_9_1 blobs in the host's D3D11 hooks (sibling prototype table already covers 113 programs), (d) clamp state objects to 9_1 rules (no separate alpha blend, no instancing, 1 render target, 2048 textures, 16-bit indices).
