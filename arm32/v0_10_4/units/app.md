# Unit brief: APP  (file `win32_host_arm32_0104_app.inl`)

Read first: `../HOST_DESIGN.md` (rules R1-R14), `SLOTS.md`, `../facts/startup_flow.md` (sections 1, 1b, 1c, 2a), then this brief. Compile check:
`python tools/arm32/try_0104.py --unit app`. You own the application lifecycle: the fake `Application` (including the `Start` that drives the whole game), the Page the game's MainPage
aggregates, Window, StatusBar, Canvas, HardwareButtons, DisplayInformation, Uri, and the window-level lifecycle (close, minimise/restore). The panel, CoreWindow and the XAML elements come
from other units: you only fetch them (`x104_panel_object`, `x104_input_core_window`, `x104_input_element_*`).

## 1. Contract functions you must define (exact signatures, see the stub)
| function | thread | semantics |
|---|---|---|
| `BOOL x104_app_install(BYTE *image)` | UI (boot) | nothing to patch; TRUE |
| `BOOL x104_app_init(HWND window)` | UI | async, input and panel are initialised; create nothing the game does not ask for lazily (objects are created on first activation); record `window` |
| `void x104_app_shutdown(void)` | UI | idempotent |
| `HRESULT x104_app_activate(class, iid, out)` | any | the 8 classes in 2.x via `x104_activate_from_table` (Application, Page, Window, Canvas, StatusBar, HardwareButtons, DisplayInformation, Uri) |
| `void x104_app_ui_tick(void)` | UI | every loop pass (<= 10 ms): deliver pending lifecycle changes (visibility) and keep the Page's size in sync with `x104_panel_client_size` |
| `BOOL x104_app_window_message(hwnd, msg, wparam, lparam, LRESULT *result)` | UI | WM_CLOSE -> `x104_app_request_exit(0)`, return TRUE/0; WM_SIZE minimise (wparam 1) / restore (0, 2) and WM_SHOWWINDOW -> set a pending visibility (R1b: NEVER call the game here); WM_SYSCOMMAND SC_CLOSE falls through to WM_CLOSE. **WM_DISPLAYCHANGE and WM_DPICHANGED are yours** (review: nobody owned them): log `X104 app: WM_DISPLAYCHANGE %dx%d bpp %d` / `WM_DPICHANGED dpi %u` (the process is system-DPI-aware, so WM_DPICHANGED is not expected; if one arrives log it loudly), set a pending flag and let `x104_app_ui_tick` call `x104_display_raise_orientation_changed()` for a changed monitor size (never `DisplayContentsInvalidated`, see 2.7); return FALSE so the others and DefWindowProc also see them. Not yours (the boot owns them, `x104_window_proc` step 1): WM_TIMER pump, X104_WM_QUIT, WM_SYSCOMMAND/SC_KEYMENU, WM_SYSKEYDOWN default. Broadcast messages: return TRUE only if you fully consumed it (a broadcast WM_SIZE must stay FALSE so the panel/DefWindowProc also see it). Only called after `x104.f_units_ready`; keep your state zero-safe anyway |
| `void x104_app_request_exit(int code)` | any | **idempotent on `x104.f_exit_requested` (the APP unit's flag: set it with `x104_flag_set`-style compare-and-swap on the first call; `x104.f_quit` is the ASYNC unit's "loop is leaving" flag - never test or set it, try_0104.py lints this; review finding: one flag with two meanings made `x104_ui_post` refuse the exit proc and clicking X did nothing)**. Post `x104_app_exit_proc` with `x104_ui_post` (it runs at the loop's top level). If `x104_ui_post` returns FALSE (the loop is already quitting) and the caller is the UI thread, run `x104_app_exit_proc` inline (it is safe: it only calls exported steps and each step is idempotent); from another thread just log `exit request ignored: loop already quitting`. The exit proc: (1) **raise `Suspending` ONLY when `x104.f_launched` AND `x104_game_is_ready()`** (guarded: `x104_event_invoke_guarded`; the game's handler 0x1E3DA0 ignores the args, takes the `AppMain` lock, runs `DR::Trim`, `StopRenderLoop` and the client suspend helpers (0x4743C and following), which dereference `client+0x118` (textures) and `+0x11C` (font): both are NULL while the init job is still compiling shaders, so a close during the first seconds would CRASH instead of exiting). When the game is not ready log `X104 app: exit before ready: Suspending skipped (AppMain+0x3C == 0)` and skip it - the process is going away anyway; (2) `x104_async_shutdown()` (waits at most the existing 2 s for workers, it does NOT wait for the init job beyond that); (3) `x104_ui_quit(code)`; then `Application::Start` returns |
| `BOOL x104_app_raise_back_pressed(void)` | UI | invoke every handler registered with `HardwareButtons.add_BackPressed` with `(sender = NULL, args = BackPressedEventArgs view)`; return the `Handled` the game set (see 2.6) |
| `void x104_display_raise_dpi_changed/_orientation_changed/_contents_invalidated(void)` | UI | raise the DisplayInformation events (sender = DisplayInformation IInspectable view, args = NULL); the host never calls them by itself except on WM_DPICHANGED / WM_DISPLAYCHANGE if you choose to |

## 2. Objects and every vtable slot (IID, slot, ABI, behaviour, who calls)
All objects agile, IInspectable-based. Unlisted slots stay holes.
### 2.1 Application - class `Windows.UI.Xaml.Application` (one factory object, two interfaces)
`IApplicationStatics {06499997-F7B4-45FE-B763-7577D1D3CB4A}`
* 6 `get_Current(void **value)` - return the inner application's IApplication if created else E_FAIL (not called by the game).
* **7 `Start(void *self, void *callback)`** - caller: user main -> `sub_1EECBC` 0x1EECBC (call 0x1EED1A/0x1EED30). The callback is an `ApplicationInitializationCallback` (C++/CX delegate, vptr 0xDC96C8, `Invoke` = vtable slot 3 `(callback, params)`; `params` unused, pass NULL). Algorithm (UI thread, no locks held):
  1. log `X104 app: Application::Start entered`, AddRef the callback, remember it.
  2. `hr = callback->Invoke(NULL)` guarded (R5). The game's lambda 0x1EE380 builds `App2` (0x34-byte object) whose ctor calls `IApplicationFactory.CreateInstance` (below) and registers `Suspending`/`Resuming`; the lambda then releases its handle (the runtime must keep `outer` alive: you AddRef it in CreateInstance).
  3. verify CreateInstance happened (`outer` recorded); else log FATAL `App2 was not created` and return E_FAIL.
  4. `QI(outer, IApplicationOverrides {25F99FF7-9347-459A-9FAC-B2D0E11C1A0F})` through `x104_raw_qi` (answered by App2+0x10, its QI is 0x1E4C84); call **slot 7 `OnLaunched(void *self, void *args)`** with the `ILaunchActivatedEventArgs` view (views[0]) of a `LaunchActivatedEventArgs` host object (2.2), guarded; log hr; `x104_flag_set(&x104.f_launched, ...)`; release the overrides pointer.
  5. `int rc = x104_ui_run_loop();` (async unit; returns after `x104_ui_quit`). Log `Start: UI loop returned %d`.
  6. return S_OK (the real Start returns when the app ends). Release the callback.
  OnLaunched (rva 0x1E3A30) then does: `StatusBar.GetForCurrentView().HideAsync()`; if `App2+0x30` (MainPage) is NULL: `Heap::Allocate(0x88,0x94)` + MainPage ctor 0x1DCF5C (everything in HOST_DESIGN section 10 happens inside it); `QI(args, IActivatedEventArgs {CF651713-CD08-4FD8-B697-A281B6544E2E})->get_PreviousExecutionState` (slot 7; **args must NOT be NULL**; return 0 = NotRunning; value 3 = Terminated would run `MainPage::vf11` LoadState); `QI(page, IUIElement {676D0BE9-...})`; `Window.Current.put_Content(page)`; `Window.Current.Activate()`.
* 8 `LoadComponent(component, uri)` / **9 `LoadComponentWithResourceLocation(void *self, void *component, void *uri, int location)`** - caller `InitializeComponent` 0x1EDDD8 (helper 0x1EE424) with the Uri `ms-appx:///MainPage.xaml`. No-op: log the URI (read it from your Uri object) and return S_OK. (MainPage.xbf is never parsed: FindName supplies the four elements.)

`IApplicationFactory {93BBE361-BE5A-4EE3-B4A3-95118DC97A89}`
* **6 `CreateInstance(void *self, void *outer, void **inner, void **instance)`** - caller helper 0x1E3228 from `App2::App2` 0x1E2B48 (`sub_1E2CF0`): `outer` = `App2+8` (a C++/CX sub-object; `inner` out = `App2+0x14`). Do it with the toolkit helper (review: the units hand-rolled the inner/instance/outer protocol): `x104_aggregate_create(&x104_app_class, sizeof(...), outer, &X104_IID_IApplication, inner, instance, &obj, "IApplicationFactory.CreateInstance")` - it creates the application object (class with `IApplication` as views[0]), AddRefs `outer` ONCE and never releases it (the runtime would keep it alive; `startup_flow.verdicts` m9), returns `*inner = views[0]` AddRef'd and `*instance = IApplication view` AddRef'd (the same object here) and logs all pointers. `inner` and `instance` are non-NULL in the game; `outer` is non-NULL.
`IApplication {74B861A1-7487-46A9-9A6E-C78B512726C5}` (the object the game gets back; the game QIs `inner` for it in wrappers 0x1E5F50/0x1E5EDC):
* **13 `add_Suspending(void *self, void *handler, LONGLONG *token)`** (SuspendingEventHandler, delegate lambda -> 0x1E3DA0) and **15 `add_Resuming`** (`EventHandler<Object>` -> 0x1E3C34): `x104_event_add`. 14/16 `remove_*` via `x104_event_remove`. 17 `Exit()` - `x104_app_request_exit(0)`. Raising: `Suspending(sender = IApplication view, args = SuspendingEventArgs view)`: host object with `ISuspendingEventArgs` (6 `get_SuspendingOperation(void **)` -> operation object with `ISuspendingOperation` 6 `GetDeferral(void **)` -> a deferral object with `ISuspendingDeferral` 6 `Complete()`; 7 `get_Deadline(LONGLONG *)` = FILETIME now + 5 s) - all optional because the game's handler ignores its arguments, but never pass NULL. `Resuming(sender, NULL)` is not raised by the host in M1 (no suspend while minimised on a desktop).

## 3. Lifecycle (window -> game)
* Close (WM_CLOSE) -> `x104_app_request_exit`. Alt+F4 / X are the only ways to leave.
* Minimise (WM_SIZE wparam SIZE_MINIMIZED) -> pending visible=FALSE; restore -> visible=TRUE. In `x104_app_ui_tick` (top level, only when `x104.f_content_set`): if the pending value differs from the last delivered one: `x104_input_release_all_pointers("visibility")`, then `x104_input_raise_visibility_changed(v)`. The game's handler (0x1DF9AC) reads `args->get_Visible` (slot 6, direct call), stores it at MainPage+0x80 and, when `AppMain+0x3C` is set, starts (`StartRenderLoop` 0x1DA8A8) or stops (`StopRenderLoop` 0x1DA9D4, under the AppMain lock) the render loop. This also stops the busy loop while Present would return DXGI_STATUS_OCCLUDED.
* No Suspending/Resuming on minimise; Suspending only on exit and ONLY when the game is ready (see `x104_app_request_exit`; early-exit rule: before `AppMain+0x3C == 1` the process just shuts down).
* WM_DPICHANGED / WM_DISPLAYCHANGE: log; optional `x104_display_raise_*` (not required in M1).

## 5. Ordering, threads, traps
* Everything of OnLaunched runs on the UI thread INSIDE `Start`; the MainPage constructor makes ~25 calls into your fakes (HOST_DESIGN section 10 lists them in order): none may block, none may invoke game delegates (R1), all return S_OK.
* `Start` must not return before the app ends; it must return (S_OK) after the loop ends so the game's `main` returns and the CRT exit runs.
* `outer`/`inner`/`instance` rules: AddRef outer once, never release; `inner`/`instance` AddRef'd; never free; QI on the inner for IIDs it does not implement returns E_NOINTERFACE (logged).
* The MainPage constructor calls `FindName` through `QI(this, IFrameworkElement)`: the OUTER's QI forwards to your inner; check the QI MISS log if the forwarding fails.
* Cases the facts mark uncertain: slot 6 of `IHardwareButtonsStatics` (medium), exact use of `IApplication` slots beyond 13/15 (none seen), `IDisplayInformation2`.
* `facts`: `startup_flow.*` (all), `startup_flow.verdicts` m5 (QI matrix) and m9 (refcounts), `input_text.back_button`, `frame_render.verdicts` ordering paragraph.

## 7. Acceptance criteria
1. `try_0104.py --unit app` OK.
2. Device log: `aggregate:` lines for Application and Page show outer AddRef'd once, inner = identity view, instance = IApplication / IPage; OnLaunched receives the ILaunchActivatedEventArgs view; the window is shown by `Window.Activate`; no `UNIMPLEMENTED` for IApplicationStatics/Factory, IApplication, IPage, IFrameworkElement(51), IWindow, IStatusBar(+Statics), ICanvasStatics, IDisplayInformation(+Statics), IUriRuntimeClassFactory, IHardwareButtonsStatics, IActivatedEventArgs; the OnLaunched line returns hr 0 and `Window.Activate` is logged before `UI loop entered`.
3. Window X after the game is running: Suspending raised, render loop stopped, process ends in < 3 s with exit code 0. Window X during the first seconds (shader compile): `exit before ready: Suspending skipped`, no crash, process ends. Closing twice / from two threads: the second request is ignored (f_exit_requested) and the first one still completes (x104_ui_post is not refused by the guard).
