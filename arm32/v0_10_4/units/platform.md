# Unit brief: PLATFORM  (file `win32_host_arm32_0104_platform.inl`)

Read first: `../HOST_DESIGN.md`, `SLOTS.md`, `../facts/platform_services.md` + `platform_services.verdicts.json` (the "MISSING" paragraphs M1-M9 are part of your spec), then this brief.
Compile check: `python tools/arm32/try_0104.py --unit platform`. You own the "phone services" the game's `AppPlatform_Winrt` uses plus the file-system roots: Package, ApplicationData
(+ LocalSettings container), MemoryManager, VibrationDevice, NetworkInformation, CurrentAppSimulator, AsyncCausalityTracer, the Windows.Web.Http decision, the AppPlatform data-cell
patches and the XAudio2 fallback. Almost all of it is needed BEFORE the main menu: `AppMain::createApp` (0x1D9DD4) reads Package + ApplicationData during the MainPage constructor and the init
job needs the folders, MemoryManager and the assets. Everything file/network/audio the game does afterwards is native Win32/CRT/Winsock/XAudio2 and needs no fake.

## 2. Roots: game folder and data folder
* `x104.game_root` (set by the boot from `package_path` = the exe directory) is the **Package.InstalledLocation.Path**; assets are read as `<path>/data/<name>` (`readAssetFile` 0x4F780, `getImagePath` 0x4EB90), shader sources `data/shaders/dx11/*.hlsl`. It is also the current directory.
* The game narrows BOTH paths into `std::string` by **truncating each UTF-16 unit to its low byte** (`sub_480D8`, `platform_services.assets.narrow_ctor`): a non-ASCII character corrupts every path silently. In `install`: if any character of `x104.game_root` is >= 0x80, try `GetShortPathNameW` (declare it; 8.3 names are ASCII when enabled) and, if the short path is ASCII, use it for the fake `Package` path (log a WARNING with both); otherwise log FATAL `X104 platform: the game folder path contains non-ASCII characters: %s - move the game to an ASCII-only path` and return FALSE (the boot shows it in a message box).
* **ApplicationData.LocalFolder.Path** = `x104.data_root` (you fill it; no trailing slash; ASCII; the folder must exist and be writable): the game creates `<root>/games/com.mojang/minecraftpe` (options.txt, clientId.txt, minecraftWorlds = LevelDB) below it with `_mkdir`. Selection order, each step logged: (a) command line `--data-dir=<path>` (parse `GetCommandLineW` with `host_next_argument`/`arm32_iat_argument_value`), (b) `<%APPDATA%>\MinecraftPE\0.10.4` (SHGetFolderPathW CSIDL_APPDATA|CSIDL_FLAG_CREATE; the `0.10.4` subfolder keeps this game's worlds apart from the 1.2.8 host which uses `%APPDATA%\MinecraftPE`), (c) `<game_root>\LocalState`. Pick the first that is ASCII, can be created (`CreateDirectoryW` level by level) and passes a write test (create + delete a temp file). Never call `create_user_data()` (it writes a 1.2.8 options.txt).
* Log: `X104 platform: game root=%s data root=%s (source ...) writable=1`.

## 3. Objects and every vtable slot
All objects agile, IInspectable-based, built with the toolkit. HSTRING results are created with `x104_hstring_create` (R8). Unlisted slots stay holes. HRESULTs are S_OK (R6).

### 3.4 MemoryManager - class `Windows.System.MemoryManager`, `IMemoryManagerStatics {5C6C279C-D7CA-4779-9188-4057219CE64C}`
**6 `get_AppMemoryUsage(void *self, ULONGLONG *value)`**, **7 `get_AppMemoryUsageLimit(void *self, ULONGLONG *value)`** (helpers 0x4E69C / 0x4E740; only user `AppPlatform_Winrt::getFreeMemory` vf40 0x4EAF8 = limit - usage, 64-bit in r0:r1). Consumers: `Options::init` (3 calls at 0xA25EC/0xA260C/0xA263A in the init job) and `sub_1A673C`: `sub_A040C` picks one of three global vectors (0xDDED14/0xDDED20/0xDDED2C) by free memory **> 0x1EA00000 (~490 MiB) = best tier, > 0xE600000 (~230 MiB) = middle, else lowest**. Report: usage = 256 MiB constant and limit = 1 GiB when the machine has >= 1.5 GiB physical RAM, else limit = 512 MiB (use `GlobalMemoryStatusEx`, declare it; log the tier you chose). 8-14 holes.

### 3.7 CurrentAppSimulator / CurrentApp and AsyncCausalityTracer
* `Windows.ApplicationModel.Store.CurrentAppSimulator` (and `CurrentApp`): statics `ICurrentAppSimulator {F17F9DB1-74CD-4787-9787-19866E9A5559}` (6 `get_LicenseInformation(void **)` -> `ILicenseInformation` object: 6 `get_ProductLicenses` S_OK+NULL, **7 `get_IsActive` TRUE**, 8 `get_IsTrial` FALSE; 9/10/13 `Request*Async/GetProductReceiptAsync` -> E_NOTIMPL), `ICurrentAppSimulatorWithConsumables {4E51F0AB-20E7-4412-9B85-59BB78388667}` (holes). ### 3.8 Windows.Web.Http (decision)
Dead code (`IHttpClient` at job+0xD8 is never assigned: the Realms request job would null-deref even on a phone). Leave `HttpRequestMessage/HttpMethod/HttpStringContent/HttpClient` to the real runtime (return REGDB_E_CLASSNOTREG; the core logs `WinRT FALLBACK` if they are ever requested). Do not fake them. The only visible effect: tapping "Play on Realms" crashes at `WinRTRestRequestJob::vf2` 0x10E9D4 (load at 0x10ED56) - note it in the final report, no patch required for M1.

## 4. Data-cell patches (verified, PAGE_READWRITE only, `arm32_patch_cell`)
Cells hold `image + fn_rva + 1` (VA|1 relocated). Pattern for each: `arm32_patch_cell((void **)X104_DATA(cell), X104_CODE(expected_fn_rva), replacement, NULL, "name")` - it refuses with a logged mismatch if the cell holds anything else (M6: write the RELOCATED absolute address `X104_CODE(rva)`, not the literal from the facts).
| cell rva | slot | expected function | action |
|---|---|---|---|
| 0x33FB7C | AppPlatform_Winrt vf23 buy | 0x4E350 | replace by the shared "return 0" function `X104_CODE(0x29BA0)` (log) - the store would otherwise run PPL tasks that activate the REAL runtime (M4) |
| 0x33FB6C vf19 isNetworkEnabled (0x4EF14), 0x33FB94 vf29 vibrate (0x50FF0), 0x33FBC0 vf40 getFreeMemory (0x4EAF8) | | | NOT patched: served by the fakes above. (Fallbacks if a fake misbehaves on a device: `--bypass-network` -> `X104_CODE(0x29BA0)`, `--bypass-vibrate` -> `X104_CODE(X104_RVA_NOOP_FUNCTION)` 0xBF60.) |
| 0x33FB88 vf26 | touch-only (`return 1` stub 0x17FD40) | | leave: the game is touch-only (`useTouchscreen` always true); the mouse works as a touch contact |
Verify the surrounding function bytes before patching where `ARM0104_*_EXPECTED` exists. Log every patch via the helper's own lines.

## 5. XAudio2 fallback
`SoundSystemRT` ctor (0x1062D8 via `SoundEngine` ctor 0xEFA00, in the init job AFTER the first screen exists) calls `XAudio2_8!XAudio2Create` (IAT 0x20B05C, ordinal 1; the DLL is a load-time import, so it exists) and `CreateMasteringVoice`; failure is tolerated but `play` (vf9 at 0xDB804C) then dereferences a NULL engine. Probe in `install`: `LoadLibraryW(L"XAudio2_8.dll")`, `GetProcAddress(h, (LPCSTR)1)` -> `HRESULT XAudio2Create(void **ppXAudio2, UINT32 flags, UINT32 processor)` with (0, 1) = `XAUDIO2_DEFAULT_PROCESSOR`... use the same arguments as the game (`Flags 0, Processor 1`); on success call `IXAudio2` vtable **slot 7 `CreateMasteringVoice(void *self, void **voice, UINT32 channels = 2, UINT32 rate = 44100, UINT32 flags = 0, const wchar_t *device = NULL, const void *chain = NULL, int category = 6)`** (facts: `CreateMasteringVoice(&this[2], 2, 44100, 0, NULL, NULL, 6)`), then destroy the voice (`IXAudio2Voice::DestroyVoice` = slot 18 of the voice object, which is NOT IUnknown) and Release the engine (slot 2). If any step fails (no audio endpoint, RT 8.1 audio service down): log `X104 platform: XAudio2 probe FAILED hr=%08lx - sound disabled` and patch the two `SoundSystemRT` vtable cells (vtable 0xDB8028; on-disk values `0xDB804C -> 0x00506689` = function rva 0x106688 = vf9 `play`, `0xDB8050 -> 0x00506631` = function rva 0x106630 = vf10 `init`) with `arm32_patch_cell((void **)X104_DATA(0xDB804C), X104_CODE(0x106688), X104_CODE(X104_RVA_NOOP_FUNCTION), NULL, "SoundSystemRT::play")` and the same for 0xDB8050 / 0x106630. Success: log `XAudio2 probe ok`. (vf9/vf10 would otherwise re-run `XAudio2Create` on the same object and leak the first engine, `platform_services.verdicts` M8.)

## 5b. Package and path warnings (review)
The 0.10.4 package README warns that the game folder and the data path must be ASCII-only; your `x104_platform_install` is the enforcement (FATAL line + message box, exit code 31) and the `--selftest-fakes` check compares `Package.InstalledLocation.Path` with `x104.game_root` and `LocalFolder.Path` with `x104.data_root` (so keep those two fields exactly equal to what the fakes return, short-path substitution included: set `x104.game_root` to the substituted path). Platform has no window messages and no tick; all its functions must be callable on zero state (R15).

## 6. Things deliberately NOT done here
* No `ThreadPool` (async unit), no `Window`/`DisplayInformation`/`InputPane`/`HardwareButtons` (app/input units).
* GUI-scale globals (0xDDE814 / 0x340D40) and `AppPlatform_Winrt+0x30..0x40` are written by the game itself from DisplayInformation/panel values (`client_init.size.*`): no host patch is required; the app unit reports 96 dpi.
* No world/file I/O fakes: LevelDB `WinRTEnv`, `fopen`, `CreateFile2` etc. are native (REAL-ON-RT); non-ASCII is the only path hazard.
