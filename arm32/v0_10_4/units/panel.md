## 3. D3D11CreateDevice hook (IAT cell 0x20B1A4)
Game call (only site 0x1DB028 in `DeviceResources::CreateDeviceResources` 0x1DAFC0, run on the UI thread inside the MainPage ctor via `make_shared<DR>`): `D3D11CreateDevice(adapter NULL, DriverType HARDWARE=1, software NULL, Flags 0, levels {0xB100,0xB000,0xA100,0xA000,0x9300}, count 5, SDK 7, &device, &featureLevel (-> DR+0x38), &context)`; the HRESULT is **ignored** and the very next QI dereferences the device: a failed creation = crash at once, so the hook must never return failure to the game.
Install with `arm32_iat_hook_import(image, FALSE, "D3D11CreateDevice", X104_RVA_IAT_D3D11CREATEDEVICE, hook, &original, "D3D11CreateDevice")` (the cell value is the real d3d11 function). The hook stays installed for the whole process (device re-creation on loss re-enters it). Behaviour:
1. `cap = arm32_feature_level_cap` (shared option `--feature-level=`, default `0x9100`; `0` = "game": no clamp, no lie). Levels given to the real function: the game's list filtered to `<= cap` (empty -> `{cap}`) => by default exactly `{0x9100}` (`frame_render.create_device.host_hook`). `flags |= 0x20` (BGRA; harmless, optional). Log request and effective values (`D3D11CreateDevice request ... -> ...`, same format as the 1.2.8 hook `win32_d3d11_create_device`, which you may read as a template).
2. Call the original. If it FAILED and `driver_type == 1`: log the HRESULT loudly and retry once with `D3D_DRIVER_TYPE_WARP` (5) and the same levels; if that fails too: `MessageBoxA` with the HRESULTs + `ExitProcess`-style termination (use `TerminateProcess(GetCurrentProcess(), 33)` after logging); never return a failure to the game.
3. On success with a REAL level `actual`: if `actual` is 0x9100 or 0x9200 -> **write `0x9300` into `*selected_level`** (the game then takes its `_level_9_3` shader path; the other FL consumers 0xCB1D6/0xD8E6A/0xD116E only test `< 0xA000`) and make sure the profile patch of section 4 matches `actual`. If `actual >= 0xA000` or `== 0x9300`: report the truth, no patch. Log `selected feature level 0x%04X, reported to the game 0x%04X`.
4. Keep one AddRef'd reference to the device for the loss poll (replace and Release the old one on re-creation).
5. **Device diagnostics (review: Tegra 9_1 behaviour and the 2048 texture cap were open risks that nothing mitigated in code).** After a successful creation log, once: the adapter (`device -> IDXGIDevice -> GetAdapter -> GetDesc`: description, VendorId, DeviceId, DedicatedVideoMemory, SharedSystemMemory), the actual feature level, `D3D11_FEATURE_D3D9_OPTIONS` / `D3D11_FEATURE_THREADING` when `CheckFeatureSupport` answers, and the driver type used (HARDWARE / WARP fallback). Then patch two slots of the d3d11 DEVICE vtable (DATA cells, RW only, expected value verified, logged like every other patch): `ID3D11Device::CreateBuffer` (slot 3) and `CreateTexture2D` (slot 5) with wrappers that call the original and log (first 40 occurrences each) every FAILED result with HRESULT, size, format, bind flags, mip count, array size, usage; `CreateTexture2D` additionally logs a WARNING line BEFORE the call when width or height > 2048 (the 9_1 limit) and `CreateBuffer` when `BindFlags & D3D11_BIND_INDEX_BUFFER` and the byte width is not a multiple of 4 (32-bit indices; the game maps element size 4 to R32_UINT). They never change an argument or a result - they only make a Tegra-specific failure show up in the log. Expected old values come from the first device object (`*(void***)device`); if the vtable cell no longer holds the same value on a later device, log it and skip.
Why the lie (verified): `getShaderModelSuffix` (0xD73FC) accepts only 0x9300 (-> "_level_9_3") and >= 0xA000; for 0x9100/0x9200 it throws `std::runtime_error("Unkonwn feature level")` inside the init job, `AppMain+0x3C` is then never set (`startup_flow.verdicts` m1).

## 4. Shader profile patch (the only game-code patch)
**Ownership (review: the byte had two owners):** the exe PATCHER writes `0x33 -> 0x31` at file 0x2339F9 by default (profile group `fl91`, default ON, `--no-fl91` leaves it out), so in the normal package the string already reads `_level_9_1` when the host starts. The panel unit is the RUNTIME owner: it verifies the 11 bytes at 0x2351F0 in BOTH states (`_level_9_3` -> patch it; `_level_9_1` -> log `profile string already patched by the exe patcher (0x31)` and keep it; anything else -> ERROR + exit 33) and adapts the digit to the ACTUAL device level ('1' for 9_1, '2' for 9_2, '3' only when the device really is 9_3 - the hook patches again if the level differs from the cap). Both owners write the same value, the panel's write is idempotent.
String at rva 0x2351F0 must read `5F 6C 65 76 65 6C 5F 39 5F 33 00` (`_level_9_3\0`, exactly one xref 0xD7458: safe to patch; `x104_check_game_bytes(0x2351F0, ARM0104_FRAME_RENDER_SHADER_FEATURE_LEVEL_LIE_EXPECTED, 11, ...)`). Patch the byte at **rva 0x2351F9** with `arm32_patch_byte(X104_DATA(0x2351F9), 0x33, '1', ...)` (`'2'` for a 9_2 device). Do it in `x104_panel_install` when `cap` is 0x9100/0x9200 and again from the hook if the actual level differs from the cap (a repeated patch to the same value is a no-op; if the byte already holds the wanted value just log). The compile happens on the init thread long after the device exists. All 76 shader variants compile at `vs/ps_4_0_level_9_1` (0 failures; `frame_render` shader table). Also verify `getShaderModelSuffix` bytes (`ARM0104_FRAME_RENDER_SHADER_PROFILE_SELECTION_EXPECTED` at 0xD73FC) and log the result (warning only).

## 5. Half-resolution option
`LoadDeviceProfile` (0x1DB858) picks a row of the GPU table at rva 0xDC8850 (stride 0x18 for row 0, then 0x14; `{wchar* name, float scale, minW, minH, byte flag}`); an unknown adapter (every desktop GPU, probably Tegra) falls on the Default row: scale **0.5 at >= 1280x720**: the swap chain (and `DR+0x60/0x64` composition scale) is HALF size and the game stretches it with `SetMatrixTransform(2x)`. Default of the host: full resolution = patch the float at rva 0xDC8854 (`00 00 00 3F` -> `00 00 80 3F`: `arm32_patch_byte(X104_DATA(0xDC8854 + 2), 0x00, 0x80, ...)` after verifying all four bytes); `--half-res` (`x104.opt_half_res`) leaves the game's own behaviour. With half-res the pointer coordinates the game computes (`Position * DR composition scale`) stay consistent automatically (positions are in DIPs).

## 6. Shader sources, cwd, include
Shaders are files `data/shaders/dx11/*.hlsl` + `ShaderConstants.fxh`; `D3DCompile(..., pSourceName = "data/<path>", pInclude = D3D_COMPILE_STANDARD_FILE_INCLUDE (1), "main", profile, 0x8000, ...)` resolves the include relative to `cwd + dirname(pSourceName)`. The boot already made `x104.game_root` the cwd; in `install`: `GetCurrentDirectoryW` must equal it (else `SetCurrentDirectoryW(x104.game_root)` + log) and `<game_root>\data\shaders\dx11\ShaderConstants.fxh` must exist (`GetFileAttributesExW`): log an ERROR line naming the missing file if not. The boot already installs a pass-through D3DCompile logger (`D3DCompile #n ok/FAILED` with the HLSL error text); you add nothing there.

## 7. Presentation (the hard part)
`DX::DeviceResources::CreateWindowSizeDependentResources` (0x1DB158, runs on the UI thread inside the SizeChanged handler under the AppMain lock) does, in this order (verified order, `frame_render.verdicts`): create the swap chain with `IDXGIFactory2::CreateSwapChainForComposition(device, &desc, NULL, &DR+0xC)` (vtable slot 24, call at 0x1DB3FE/0x1DB400; desc = W,H = lroundf(render-target size), `B8G8R8A8_UNORM` (0x57), no stereo, 1 sample, usage RENDER_TARGET_OUTPUT (0x20), **2 buffers, SCALING_STRETCH (0), SWAP_EFFECT_FLIP_SEQUENTIAL (3), ALPHA_MODE_IGNORE (3)**, flags 0); queue `panel.Dispatcher.RunAsync(High, lambda 0x1DAF04)` (the lambda QIs the panel for ISwapChainPanelNative and calls `SetSwapChain`); `IDXGIDevice1::SetMaximumFrameLatency(1)`; QI `IDXGISwapChain2` and call **`SetMatrixTransform({1/scaleX,0,0,1/scaleY})` (slot 34 at 0x1DB57C)**; GetBuffer(0) -> RTV; D24S8 DSV; viewport; for an existing chain: `ResizeBuffers(2, W, H, 0x57, 0)`. A desktop HWND swap chain makes `SetMatrixTransform` fail with 0x887A0001 and `CreateSwapChainForComposition` needs a composition surface.
**Path B (default, `X104_PRESENT_HWND`)** - patch DATA cells (PORT_RULES 4: `arm32_patch_cell`, RW only, verify the old value, flush icache, log; NO code patch):
1. Find the dxgi vtable cells at runtime. Factory: `CreateDXGIFactory1` (from dxgi.dll via GetProcAddress) -> QI `IDXGIFactory2` -> `vtbl = *(void***)factory`; remember `orig_for_hwnd = vtbl[15]` (`CreateSwapChainForHwnd`) and `orig_for_composition = vtbl[24]`; patch **`vtbl[24]`** to `x104_panel_create_swapchain_for_composition(void *factory, void *device, const DXGI_SWAP_CHAIN_DESC1 *desc, void *restrict_to_output, void **swapchain)` (this=r0, device r1, desc r2, output r3, out pointer on the stack - a plain 5-argument C function). Release the throw-away factory. **Log the vtable pointer that was patched** (`X104 panel: dxgi Factory2 vtable %p: cell 24 %p -> stub`). The vtable of the dxgi factory class is shared by all factories of the process IN PRACTICE, so the game's own factory (obtained through `device -> IDXGIDevice3 -> GetAdapter -> GetParent`) is covered - but this is an ASSUMPTION that cannot be proven offline, therefore steps 4 and 5 below make a failure of it LOUD instead of a silent black window.
2. The stub: copy `*desc` (48 bytes: Width, Height, Format, Stereo, SampleDesc{Count,Quality}, BufferUsage, BufferCount, Scaling, SwapEffect, AlphaMode, Flags) and call `orig_for_hwnd(factory, device, x104.window, &desc, NULL /*fullscreen desc*/, NULL, swapchain)`. Fallback chain on failure (log each attempt with HRESULT and the desc): (a) as requested (FLIP_SEQUENTIAL + STRETCH; accepted on Win11, UNVERIFIED on Win8.1/RT), (b) SCALING_NONE (then the buffer size must equal the client size: only valid with full resolution; log an ERROR if `opt_half_res`), (c) SWAP_EFFECT_DISCARD (blt model) + STRETCH. After success: `factory->MakeWindowAssociation(window, DXGI_MWA_NO_WINDOW_CHANGES|DXGI_MWA_NO_ALT_ENTER = 3)` (slot 8; no Alt-Enter, no DXGI subclassing of our window proc). **The stub RECORDS what it created**: `x104_panel.stub_chain` (the AddRef'd `IDXGISwapChain1*` it returned), `created_by_stub = TRUE`, `x104_flag_set(&x104.f_swapchain_created, ...)`, the vtable pointer of that chain and which attempt (a|b|c) worked.
3. Right after the swap chain exists: QI it for `IDXGISwapChain2` (IID `A8BE2AC4-199F-4946-B331-79599FB98DE7`; the game QIs it at rva 0x2DF288) and patch in the SAME step, on the vtable(s) of that chain (`*(void***)sc1` and, if it differs, `*(void***)sc2`), each cell individually through `arm32_patch_cell` (a cell may sit on another page):
   * **`vtbl[34]`** (`SetMatrixTransform`, +0x88) -> `x104_panel_set_matrix_transform_ok(void *self, const void *matrix) { return S_OK; }` (expected old value: whatever it holds - log it; skip if it already equals the stub);
   * **`vtbl[8]`** (`IDXGISwapChain::Present`) -> `x104_panel_present_stub(void *self, UINT sync, UINT flags)`: `x104_present_begin(); sync = x104_present_sync(sync); x104_present_pace(); hr = orig_present(self, sync, flags); x104_present_end(hr, sync, flags); return hr;` (core section 13b: counts the frames for the 30 s heartbeat and the watchdog, logs the first 20 results and every non-S_OK result, `--vsync` / `--max-fps=N` / the automatic anti-spin sleep). Present is called by the game on its render thread while the UI thread may sit in the AppMain lock: because `begin` is counted before and `end` after the real call, a Present that never returns shows up in the watchdog line as "a game frame call has not returned" (the theoretical DXGI-needs-the-window-thread deadlock of HOST_DESIGN 12.2).
   Do all of it inside the factory stub, before the game can call slots 34 / 8.
4. **`SetSwapChain` (ISwapChainPanelNative slot 3) is the path-B WATCHDOG, not a no-op (review finding "silent black window").** It runs on the UI thread right after the SizeChanged handler returned (queued by the game). Compare `swapchain` (QI it to `IDXGISwapChain` and compare identity pointers) with `x104_panel.stub_chain`:
   * equal and `created_by_stub`: log `SetSwapChain(%p): the chain created by the HWND stub - nothing to attach (path B ok)`;
   * different, or the stub never ran: log an **ERROR** `X104 panel: dxgi vtable mismatch: the game's swap chain %p was NOT created by the HWND stub (stub ran=%d, stub chain=%p, game factory vtable=%p, patched vtable=%p) - path B did not take effect, falling back to path A (DirectComposition)`; then run the path-A attach for THIS chain (section 7 path A: `SetContent`; if DirectComposition is unavailable log that too and show a message box once: "no way to present on this system"). The game's own `SetMatrixTransform` call on a composition chain already succeeded, so nothing else is needed. Set `x104.f_swapchain_created` when the attach worked.
5. **The "3 s rule"** (in `x104_panel_ui_tick`): 3 s after `x104.f_size_changed_done`, if `x104.f_swapchain_created` is still 0 (path B: the stub never ran and SetSwapChain never reported; path A: SetSwapChain never ran) log ONCE `X104 panel: ERROR first SizeChanged returned %lu ms ago but no swap chain was created/attached (created_by_stub=%d) - the window will stay black; see the lines above (CreateSwapChainForComposition / SetSwapChain)`. Include the last HRESULT the stub saw. Together with 4 this makes every failure of path B diagnosable from win32craft.log.
Present pacing: the game's `Present(0,0)` plus `SetMaximumFrameLatency(1)` on a flip chain is NOT assumed to pace the loop (it was never measured): the Present stub of step 3 does it (core `x104_present_pace`: automatic 1 ms sleep after 60 frames under 3 ms, `--max-fps=N`, `--vsync`). Minimised/occluded windows return DXGI_STATUS_OCCLUDED (counted, rate-limited): the app unit stops the render loop on minimise.
**Path A (optional, `--present=dcomp`)**: no cell patches; `SetSwapChain(sc)` = on the UI thread `DCompositionCreateDevice(NULL, IID_IDCompositionDevice, &dev)` (load `dcomp.dll` with LoadLibraryW/GetProcAddress; if it is missing log it and FALL BACK to path B), `CreateTargetForHwnd(window, TRUE, &target)`, `CreateVisual`, `visual->SetContent(sc)`, `target->SetRoot(visual)`, `dev->Commit()`. `CreateSwapChainForComposition` and `SetMatrixTransform` then run unmodified. Implement B first.

## 8. Size pipeline and ordering (R2/R3 are your responsibility)
(`x104_panel_ui_tick` runs from `x104_ui_pass()`, which the window proc also calls on every 10 ms WM_TIMER, so the ticks keep running inside the modal move/size loop and the `in_size_move` branch below is LIVE: a live resize raises coalesced SizeChanged events while the user drags.)
State: `client_w/client_h` (pixels from WM_SIZE lparam / GetClientRect), `pending_resize`, `first_done`, `last_change_tick`, `in_size_move`.
`x104_panel_ui_tick`:
* before `first_done`: the FIRST SizeChanged is raised only when **all** hold: `x104.f_content_set`, `x104_game_appmain() != NULL`, `x104_game_client_has_holder()`, client size > 0; otherwise (at most every 2 s) log `X104 panel: first SizeChanged waiting: content_set=%d appmain=%p holder=%d size=%dx%d`. When allowed: refresh panel sizes from the CURRENT client rect, then raise (below), then `x104_flag_set(&x104.f_size_changed_done, "first SizeChanged returned")`. The async unit's timer starts ticking only after that flag (R3).
* after `first_done`: if `pending_resize` and (`!in_size_move` and 30 ms since the last change, or `in_size_move` and 100 ms since the last raise) -> refresh sizes and raise. Never while minimised.
* device-loss poll every ~500 ms (section 9).
Raising (UI thread, top level only - R1): `x104_element_set_sizes(panel, w, h)`; build args (previous, new); `x104_event_invoke_guarded(&panel->base.size_changed, panel_view, args_view)` (`panel_view` = the panel's IInspectable view, `args_view` = the ISizeChangedEventArgs view); log `X104 panel: SizeChanged raised %dx%d (prev %dx%d) handlers=%u` (every raise for the first 20, then every 10th). The game's handler 0x1DF808 takes the AppMain lock, runs `DR::SetSwapChainPanel` (ActualWidth/Height, orientations [IDisplayInformation 7/6], composition scale, dpi [11]), `DR::SetLogicalSize` -> `CreateWindowSizeDependentResources` (your path-B stub runs inside it), then `AppMain::OnWindowSizeChanged` 0x1DA32C -> `client->setSize((w+0.5)*platform+0x3C, (h+0.5)*platform+0x40, 0.0f)` (platform scale is still 0.0 on the first call: the 240x140 fallback is harmless, rendering has not started). The values must be `>= 0` (checker 0x1DAED0 rejects negatives only).
During the first call the swap chain does not exist yet; the dispatcher queue item that calls `SetSwapChain` runs right after the handler returns (async unit).

## 9. Device loss
Poll `ID3D11Device::GetDeviceRemovedReason` (vtable slot 39) on the device kept in section 3 every ~500 ms (UI tick). Non-zero (`0x887A0005` removed, `0x887A0007` reset, ...): log `X104 panel: DEVICE LOST reason=%08lx`, show a message box ("The graphics device was lost. Restart the game."), `x104_app_request_exit(3)`. The game does NOT rebuild its GPU resources after `HandleDeviceLost` (AppMain's IDeviceNotify slots are empty), so a loss is unrecoverable (`frame_render.device_lost.handling`); if the game re-enters the D3D11CreateDevice hook after a loss, log it and keep working (do not crash in the hook).
