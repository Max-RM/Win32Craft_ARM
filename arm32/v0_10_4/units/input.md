# Unit brief: INPUT  (file `win32_host_arm32_0104_input.inl`)

Read first: `../HOST_DESIGN.md` (rules R1, R7, R9, R10, R13, R14 are yours), `SLOTS.md`, `../facts/input_text.md` (all of it) + `input_text.verdicts.json` (its MISSING paragraphs are part of your spec),
`../../OSK_NOTES.md` (the device-proven TabTip controller you reuse), then this brief. Compile check: `python tools/arm32/try_0104.py --unit input`.
You own everything between the Windows window and the game's HIDController: the fake CoreWindow (+ its statics), CoreCursor, CoreIndependentInputSource, the pointer/key/visibility event args,
the three XAML elements the game gets from `FindName` (Logo, EditBox, Button), the InputPane, the Windows touch keyboard integration and the translation of Win32 messages into delegate calls.
The game is **touch-only** (`useTouchscreen` cell 0x33FB88 = true): a mouse click works as a touch contact; the on-screen keyboard is driven by focusing a hidden XAML TextBox.

## 2. Important facts about the game side (verified)
* Nothing is registered until the first ready Tick runs `AttachToPanel` -> `AppPlatform_Winrt::initialize` 0x4B55C -> `HID::Initialize` 0x111C1C (r1 = CoreWindow from `Window.Current.CoreWindow`, r2 = the panel, r3 = EditBox, [sp] = Button). Messages arriving earlier have no handlers: drop them (counted, logged once).
* Registrations you must accept (each: store with `x104_event_add`, return a token, S_OK): CoreWindow `KeyDown` (slot 34) -> `HID::onKeyDown` 0x1128B8, `KeyUp` (36) -> 0x112A30; pointer `Pressed/Moved/Released` on a CoreIndependentInputSource (ICorePointerInputSource 20/18/22) -> 0x113010/0x112B10/0x1136D0 (thread path, because the panel is passed); CoreWindow `VisibilityChanged` (56) from the MainPage ctor (0x1DF9AC); `ITextBox.TextChanged` (slot 30) -> 0x113D8C; InputPane `Showing` (6) / `Hiding` (8) from the MainPage ctor (0x1DF714/0x1DF700). CoreWindow pointer events (46/44/48) are the alternative path (r2 == NULL): accept them too and deliver to them as well.
* Delegate convention: `handler->vtbl[3](handler, sender, args)`; the handlers ignore `sender`; they read the args by calling slots straight on the pointer (R10): pass the matching interface VIEW.
* `HID::Initialize` also calls `ITextBox2.put_PreventKeyboardDisplayOnProgrammaticFocus(false)`, `ITextBox.put_AcceptsReturn(true)`, `add_TextChanged`, and `ThreadPool.RunWithPriorityAndOptionsAsync` (the input item, async unit). The independent input source handlers run `HID::onPointer*` which compute `x = (int16)(Position.X * HID[0x50])`, `y = (int16)(Position.Y * HID[0x54])` (scale = DR composition scale +0x60/+0x64 read at Initialize; with the host's scale 1.0 and the default full resolution that is 1.0). **Position = client pixels = DIPs.**
* All handlers are thread-safe on the game side (the platform queue has its own critical section); you invoke them from the UI thread.

## 4. The TabTip bridge and `x104_inputpane_raise`
The shared controller (win32_host.c, `ARM32 osk:` log lines) is polled by `x104_osk_poll()` from `x104_input_ui_tick`. It is level-triggered (state from IFrameworkInputPane / InputPane / DWM cloak, debounce, retries, tap-to-reopen after the user closed it). Eligible only when `--osk=on`, or `--osk=auto` AND the last pointer was a finger: call `x104_note_pointer_source(TRUE, "touch")` on every touch pointer message (and `FALSE` on a real mouse click/move or a hardware key), `x104_osk_note_pointer_up()` when a finger lifts.
`x104_inputpane_raise(BOOL showing)` is called by `arm32_input_pane_raise` (win32_host.c edit) on the UI thread at the top of the loop: **publish the rectangle FIRST**, then invoke:
* showing: `float rect[4]; if (x104_osk_rect_client(rect))` -> OccludedRect = {rect[0], rect[1], rect[2], rect[3]} (client pixels = DIPs; the keyboard's HEIGHT is what `OnInputPaneShowing` 0x1DF714 reads through `InputPane::GetForCurrentView().get_OccludedRect()` -> `AppMain::SetKeyboardHeight(px)` 0x1DA5B4 -> `px * platform+0x40` -> `client+0x164` and `screen->vf30`; the client scales it again by the GUI scale 0x340D40: report DIPs and verify on screen); if the controller has no rectangle (blind signal) use a default of 40% of the client height and log it.
* hiding: OccludedRect = {0,0,0,0}.
Then `x104_event_invoke_guarded(&showing_or_hiding, sender = InputPane IInspectable view, args = IInputPaneVisibilityEventArgs view)`. Log `X104 input: InputPane Showing raised, occluded h=%d, handlers=%u` (also when there is no handler).

## 5. Win32 message translation (`x104_input_window_message`)
Return TRUE + `*result = 0` for messages you consumed; broadcast messages (WM_SETFOCUS, WM_KILLFOCUS, WM_ACTIVATE, WM_SIZE...) must return FALSE unless noted and only set pending flags (R1b). Keep all state in a file-scope struct (`x104_input_state`).
1. **Pointers, three delivery paths** (proven on the devices, see `arm32_touch_pointer_message`, `arm32_touch_wm_touch`, `arm32_legacy_touch_message`, `arm32_legacy_mouse_filter`, `arm32_input_attach_window` in win32_host.c - READ them, they hold the Surface RT lessons; they queue 1.2.8 items so do NOT call them; the resolved Win32 entry points `arm32_api.get_pointer_type/_info/get_touch_input_info/close_touch_input_handle` and `arm32_pointer_is_touch(id,&type)` are safe to use):
   * WM_POINTERDOWN/UPDATE/UP (0x246/0x245/0x247) + WM_POINTERCAPTURECHANGED (0x24C): id = `LOWORD(wParam)`, in-contact/cancel flags in `HIWORD(wParam)` (0x4 / 0x8000), screen position in lParam -> `ScreenToClient`. Device type from `GetPointerType` (2 touch, 3 pen, 4 mouse). Consume touch pointers (return 0 without DefWindowProc: that stops Windows' mouse emulation). Mouse/pen pointers: deliver as type Mouse/Pen with IsLeft = button state.
   * `WM_TOUCH` (0x240): `GetTouchInputInfo` (TOUCHINPUT 40 bytes, x/y in 1/100 px screen coords), DOWN 0x2 / MOVE 0x1 / UP 0x4, palm 0x80 ignored, `CloseTouchInputHandle`. **Windows RT 8.1 never sends WM_POINTER to this window (device log): the first WM_TOUCH while no touch WM_POINTER was seen switches to this path** (multi-touch).
   * Legacy: mouse messages whose `GetMessageExtraInfo() & 0xFFFFFF80 == 0xFF515780` are Windows' emulation of a finger: if neither pointer nor WM_TOUCH ever delivered touch, convert them into a single touch (id 0xFFFFFFF0); otherwise drop them (duplicates). Real mouse messages: left button DOWN/MOVE(while pressed)/UP -> Pressed/Moved/Released with device type Mouse, IsLeft TRUE (the game treats it as touch); right/middle: ignore (log once); hover moves without a pressed button: do not deliver. `SetCapture`/`ReleaseCapture` around a mouse press.
   * Each delivery: set the PointerPoint (id, device type, client position, left-pressed, in-contact, timestamp), `x104_event_invoke_guarded` on every Pressed/Moved/Released list (CoreWindow lists + every independent source), sender = the CoreWindow / source IInspectable view, args = the **IPointerEventArgs view**. Track pressed ids (max 12 simultaneously: the game has 12 slots); a Moved for an unknown id is delivered only while in contact; **always send Released for every Pressed (R13)**: on WM_POINTERUP, cancel flag, capture lost, WM_CANCELMODE, window deactivation, minimise (`x104_input_release_all_pointers`).
2. **Keys** WM_KEYDOWN/WM_KEYUP/WM_SYSKEYDOWN/WM_SYSKEYUP (**for the SYS variants: deliver exactly like the plain ones, then return TRUE with `*result = 0` so DefWindowProc never sees Alt / F10 and never enters menu mode; the ONE exception is Alt+F4 (VK_F4 with bit 29 of lParam set), which must return FALSE so DefWindowProc turns it into WM_CLOSE**; the boot additionally swallows an unclaimed WM_SYSKEYDOWN/UP/WM_SYSCHAR and SC_KEYMENU as a safety net, review finding: F10 reached the game but DefWindowProc also opened the menu loop) (VK in wParam; repeat count `lParam & 0xFFFF`, scan `(lParam >> 16) & 0xFF`, extended bit 24, WasKeyDown bit 30): deliver `KeyDown/KeyUp` with the `IKeyEventArgs` view. The game maps only: Backspace 8, Enter 0xD, Esc 0x1B, Space 0x20, PageUp/PageDown 0x21/0x22 (swapped by the game), arrows 0x25-0x28, F1-F12 0x70-0x7B, Shift 0x10/0xA0 (toggles a static byte at rva 0xDE2FEF; 0xA0 -> 0x10) as KEY events; **every other VK becomes a garbage TEXT event** (`(char)vk`, lowercased unless shift), so deliver only those VKs, letters A-Z (0x41-0x5A) and digits (0x30-0x39) and drop modifiers (Ctrl/Alt/Win/CapsLock...), OEM keys, VK_PACKET 0xE7 (touch-keyboard injection). While `HID[0x44]==1` (text mode) the game ignores key events entirely - keep delivering them anyway. **Esc (0x1B) is Back**: do NOT deliver it as a key; call `x104_app_raise_back_pressed()` (app unit) on the key-down (Alt+Left too); log the Handled result. Hardware key activity: `x104_note_pointer_source(FALSE, ...)` unless a finger is down or the keyboard is ours (OSK visible).
3. **Characters** WM_CHAR (UTF-16 units; join surrogate pairs): only in text mode (`focused == EditBox`): printable (>= 0x20, not 0x7F) inserts at the caret, replacing the selection; 0x08 deletes the selection or the character before the caret; 0x0D inserts the pair `L"\r\n"` (R14); other control characters ignored; respect MaxLength; then schedule the single TextChanged. Outside text mode ignore WM_CHAR (the key events already carried letters/digits). Update the caret from `Select()`.
4. **Focus/cursor/misc**: WM_SETFOCUS/WM_KILLFOCUS/WM_ACTIVATE(inactive)/WM_CANCELMODE/WM_CAPTURECHANGED(not ours) -> set `pending_release` (done in `x104_input_ui_tick`, then `x104_input_release_all_pointers("focus lost")` and KeyUp for pressed keys); WM_SETCURSOR (client area) -> cursor policy of 3.1, TRUE; WM_MOUSEWHEEL and others: not consumed.

## 7. Traps (facts and verdicts)
* `input_text.lambda_show` / `hide_keyboard`: FocusState is Programmatic (3) for both; `PreventKeyboardDisplayOnProgrammaticFocus=false` is set by the game.
* `input_text.text_changed`: Enter = adjacent `\r\n`; TextChanged asynchronously after put_Text; the CRLF-strip `put_Text` inside the diff sets the flag the outer handler clears; test Enter in chat on the device.
* The TextChanged handler injects into the static Keyboard vectors directly (no platform lock): fire it from ONE thread (the UI thread), never from the game's threads.
* Pointer `Moved` events with an unknown id insert a map node: don't send hover moves of an unpressed mouse.
* Hardware keyboard garbage (modifiers/OEM keys) - filter as in 5.2.
* `IAgileObject` on the CoreWindow; `get_CurrentPoint` is called several times per event; `get_KeyStatus` writes <= 12 bytes.
* The independent-source work items block in `ProcessEvents(2)`: your delivery does not depend on that thread (events are raised from the UI thread).
