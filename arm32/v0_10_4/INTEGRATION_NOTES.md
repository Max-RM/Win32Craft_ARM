## 3. What can NOT be verified offline (device-only)

1. **Loading**: the patched exe + three patched VC120 `_app` DLLs (invalid Authenticode) + app-local api-set/UCRT shims on Windows RT 8.1 / Win10 ARM32; 436 static constructors; `vccorlib` `InitializeData(2)` (MTA) on the CRT thread. -> `loadcheck.exe`.
2. **ARM calling convention** of what the PC test cannot see: `LONGLONG` (TimeSpan/tokens) in r2:r3, `double` in d0, `float`, `Size/Point/Rect` by value, 10-argument `D3D11CreateDevice`, `Platform::Agile` and C++/CX wrappers calling our objects (QI/AddRef/Release, HRESULT -> COMException translation). -> `start_selftest.bat` + the `Canvas.SetLeft(..., 3000)` and `timer ... interval = 000000000007a120 ticks (50 ms)` lines.
3. **Direct3D at feature level 9_1** (Tegra): device creation with the {9_1} list, the "reported 9_3" lie accepted by `getShaderModelSuffix`, the `_level_9_1` shader profile for all ~45 shaders (D3DCompile), 2048 texture cap, 32-bit index buffers, `ID3D11Device2` QI on RT 8.1, BGRA flag, the CreateBuffer/CreateTexture2D diagnostic wrappers.
4. **Presentation path B**: patching dxgi's `.rdata` vtable cells (24 CreateSwapChainForComposition, 34 SetMatrixTransform, 8 Present) and `CreateSwapChainForHwnd` with FLIP_SEQUENTIAL + STRETCH + ALPHA_IGNORE + 2 buffers on RT 8.1; whether the game's own factory shares the patched vtable (the code verifies and falls back to path A); `ResizeBuffers` on resize; Present from the render thread while the UI thread idles; DWM behaviour; tearing/frame pacing (`--vsync`, `--max-fps`).
5. **The real game's threading**: AppMain's non-recursive `critical_section` against the UI thread and the render thread; ConcRT's contended slow path (may call the real `RoGetActivationFactory`: logged); `MinecraftClient::init` (seconds of shader compiles) racing the first `SizeChanged` / `setSize`; 2-core starvation; init duration.
6. **Shutdown**: static destructors after WinMain returns, the game's Suspending handler (`DR::Trim`, client suspend), the 30 s exit guard.
7. **Input on real hardware**: WM_POINTER vs WM_TOUCH vs emulated mouse on RT 8.1, TabTip show/hide, keyboard rectangle -> `InputPane.OccludedRect` -> `setKeyboardHeight`, cursor handling, multi-touch slots.
8. **Audio** (XAudio2 probe, SoundSystemRT), **file I/O** under the data root (options.txt, worlds), path length (> 150 chars warns), **memory** figures the MemoryManager fake reports (limit 1 GiB when RAM >= 1.5 GiB, else 512 MiB: selects the game's texture tier).
9. **Online**: `Windows.Web.Http.*` is deliberately NOT faked (real runtime); "Play on Realms" is dead code that crashes (`WinRTRestRequestJob::vf2 0x10E9D4`).

## 5. Test plan for the device (in this order)

1. Copy `Minecraft_PE_0.10.4.40_ARM32_Win32Craft.zip` to the device, unzip to a plain ASCII, writable path (e.g. `C:\Games\MCPE0104`; not WindowsApps). Allow unsigned code if needed.
2. `loadcheck.exe` (only if anything fails to start: "missing DLL" / "entry point not found") -> `loadcheck.txt`.
3. `start_selftest.bat` -> message box. Expect "all checks passed"; in `win32craft.log` find `X104 selftest: ===== 43 passed, 0 FAILED, 0 skipped =====`. Any `[FAIL]` line names the ABI/contract problem; fix before anything else.
4. `start.bat`. Expect M0, M1a-M1f in the log; the window appears after OnLaunched (a few seconds), stays black/empty while ~45 shaders compile, then the menu. Wait up to ~60 s before judging. Note the time of `FIRST Present`.
5. If the window is black but the log shows `FIRST Present`: try `start_dcomp.bat` (path A), then `start_vsync.bat`. If no swap chain: send the log (the `X104 panel:` lines say which attempt failed). If shaders fail: `start_fl93.bat`; if the device creation fails the log has the HRESULT.
6. M2: tap through menus, create/open a world, move, place/break blocks, open chat/world name (keyboard), press Back/Esc, minimise and restore, resize the window, close with X. Note anything that freezes: the watchdog line `NO PROGRESS` + the last `X104` line before it is the lead.
7. Send back: `win32craft.log` (and `win32craft.log.old`), `loadcheck.txt` if used, and a photo/screenshot + what was tapped. If something crashed: the first `X104 ***` / `EXCEPTION` / `UNIMPLEMENTED` line.

PC-side re-verification after any change: `python tools\arm32\try_0104.py --selftest --integration` then `build_arm32.bat`, `python tools\make_0104_package.py`.

## 6. Known gaps, deliberately left alone, and review leftovers

* Not faked: `Windows.Web.Http.*` (real runtime; Realms crash is known and has no patch), Store purchases (`buy` cell patched to "return 0"), Resuming and `DisplayContentsInvalidated`/`DpiChanged` are never raised by the host (process is system-DPI-aware, 96 dpi / scale 1.0 reported, landscape only), `Window.Activated/Closed/SizeChanged` are accepted but never raised, `BackPressed` unhandled does NOT exit (use the close button / Alt+F4), only the left mouse button is used (the game is touch-only).
* Private IIDs in the host for interfaces the game never QIs: `IBackPressedEventArgs`, `IVibrationDevice` (a QI for the genuine IID would show up as `QI MISS`).
* Device loss is unrecoverable in the game (the host reports `DEVICE LOST` and exits through the app exit path).
* `--selftest-fakes` leaves a few host objects behind (pool items, one timer slot, one scheduled TextChanged): harmless; the numbering of `item #n` / `timer #n` shifts by what the selftest created.
* Low review findings that remain by design: the exit path waits at most 2 s for workers and never for the init job (the exit guard ends a stuck process after 30 s); `x104_present_pace` sleeps 1 ms per frame once the game exceeds 330 fps (log `renders uncapped`).
* Integration-pass changes to the units/core (all ARM-only, x86 unchanged): `X104_QS_ALLINPUT` 0x1CFF, `ProcessEvents` on the UI thread is a logged no-op (R1), async shutdown log buffer margins, `MsgWaitForMultipleObjectsEx` flag (unit review), app `AppMain+0xC` guard (unit review). Details: `HOST_DESIGN.md` 14b.
* The summaries of the panel, platform and input unit reviews were cut off when the previous run lost its connection; this pass therefore re-read those three files completely and checked them against the facts and the integration test. Their code paths that need a D3D device or the real exe (D3D11CreateDevice hook body, dxgi cell patching, Present stub, platform data-cell patches, XAudio2 probe) have only compile-time and offline byte checks (14b #10) - they are the first things to read in a device log.
* First device run (2026-10-18): menu, world rendering, touch and OSK work; **the world has no HUD / touch buttons** - cause not provable offline. Evidence, the decision chain in the game, and the new diagnostic option `--trace-game-state` (game-state snapshots + Direct3D draw tracer, log prefixes `X104 gstate` / `X104 d3dtrace`) are in `HUD_INVESTIGATION.md`.
